# 文档入库与生命周期指南

日期：2026-11-14。盘点基线：`architecture-refactor / 123b775`；只统计当时 Git 已跟踪文件，不含本指南及未跟踪试验。本文给出分类与处理建议，不授权删除、搬移、合并正文或重写 Git 历史。

## 1. 结论与交付目标

当前 `docs/` 有 **269 个跟踪文件、141 份 Markdown**：design 41 份、reviews 85 份、acceptance 9 份，其余6份为导航、CI、规范、契约说明和研究题单。reviews 共109个文件、acceptance 共108个文件，含 JSON、日志、图片与冻结 HTML。问题主要是**现行规则、历史状态、执行流水和机器输入混在一起**，不是所有文档都没有价值，也不是仅靠减少目录数量能解决。

最终源码仓库应让接手者能回答：怎么使用、怎么开发、系统当前如何工作、哪些行为必须保持、哪些平台已验/未验。日常主阅读路径只通往这些内容；历史过程通过提交、阶段摘要和必要证据追溯。安装包/Web 发布包是另一层：不在安装包里不等于不值得入 Git；放在 `public/` 的历史稿则可能随 Web 包发布，需要另行核对。

根 README 也应控制职责：概览、主要能力/限制、启动、文档入口即可。现有长篇竞品对比、架构展开与教程重复内容，后续可单独精简；其中体积、性能与外部工具能力的描述需有对应依据，不能当作本仓库验收结果。本轮不改这些产品介绍正文，只更新文档导航区。

建议保留当前目录骨架，不为了治理再建立一套文档平台：

```text
README.md / TUTORIAL.md / CHANGELOG.md / LICENSE
AGENTS.md                         # 项目协作入口，细则引用规范
docs/
  README.md                       # 按读者任务导航，不列每次执行流水
  design/                         # 现行架构与模块规则、少量有效决策；在途计划有退出条件
  contracts/                      # 机器可读契约及解释，保留调用路径
  development/                    # 开发、验证与本文的轻量管理规则
  ci.md                           # CI 使用与发布说明，随实际工作流更新
  acceptance/                     # 手动验收、发布支持范围、必要冻结基线
```

`reviews/`、`research/` 是现有过程材料存放处，暂时保留，不再默认每个小步都新增文件；收口后有价值的结论进入上述正文。历史通常交给 Git，不把全部旧文档再复制到一个永久增长的 archive 目录。确需保留某一里程碑档案时，仅建该阶段索引与必要记录。

## 2. 什么该入库

| 类别             | 处理原则                                                              | 例子与结束条件                                                                         |
| ---------------- | --------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 长期维护         | 规则或使用价值仍有效就保留，更新原文，不按日期复制新稿                | 教程、开发规范、当前模块设计、接口/配置契约、许可证                                    |
| 工程必需输入     | 即使放在 docs 中也按代码/测试资产保护，不以“文档过多”删除             | 被导入的 JSON、测试夹具、冻结比较基线；解除调用并验证迁移后才可处理                    |
| 阶段性入库       | 当前工作确实需要共同评审或交接，保留一份有效计划/记录，并写明关闭条件 | 迁移路线、能力探针、未验系统清单；任务收口后提炼规则和证据，不永久保留每步流水         |
| 不默认入库       | 可重生成、只服务单机、已废弃且没有独立约束价值、包含私密内容的材料    | 运行日志、全量测试输出、截图海量中间态、外部题单原件、失败尝试草稿、临时脚本和废弃原型 |
| 可合并或移除副本 | 同一职责、同一事实、同一生命周期才合并；先保留尚未迁出的独立结论      | 重复模式说明、已被替代的旧验收清单；不是把不同模块塞成一份巨型文档                     |

不按后缀或目录一刀切：关键原生 PDF/权限验证的原始记录可能不可替代；JSON 可能是运行输入；Markdown 可能是测试样本。反过来，一份很短的 review 也未必值得独立长期维护。

## 5. 每次怎样处理，才不会清掉需求或证据

1. **确认对象**：是说明、在途计划、历史结论，还是运行/测试输入？写出实际消费者，不能只看文件名。
2. **确定唯一去向**：标明哪份现行正文承接规则、哪份清单承接未决/未验项、哪份摘要或提交可追溯原始上下文。没有去向就先不删。
3. **迁出有效信息**：保留决策理由、适用平台、明确取消/失败边界、关键反例及未验条件。已失效假设保留历史身份，不混进现行规范。
4. **处理引用**：核对 README/其他Markdown、源码注释、测试、脚本、配置、动态 fetch 和公开资源路径；建立旧节→新节对应。已合并稿不再双向更新；必要过渡链接有退出条件，不永久积累空壳。
5. **保留证据可取性**：历史来源用确实存在的提交/标签和原路径；系统证据外迁有稳定位置和校验值。Git 历史不替代未入库的原始产物，也不自动长期保存外部附件。
6. **按影响验证再提交**：正文/导航只做文档与链接核对；涉及实际输入路径或运行资源时再做相关代码/夹具迁移及对应验证。分类建议不授权删除文件或变更门禁。

删除工作树中的历史文档不会缩小已有 Git 对象历史；本次目标是减少现行阅读与维护负担，不重写历史。不得把清理动作解释为消除缺陷、补齐系统证据或允许发布。

## 6. 以后怎样避免再膨胀

- 普通小步默认更新现行正文或提交说明，说明变更、实际验证与未验项即可；遵循[分析与验证规范](analysis-and-verification.md)，不默认另建实施报告、审查报告、复审报告各一份。
- 确需阶段文档时，在开头只补：职责、状态、替代去向/关联正文、退出条件。一个阶段一份可增量更新的摘要；原始证据按需要索引，不再把完整控制台输出粘到设计正文。
- 长期契约文件名倾向稳定；日期用于状态/证据，不每次修订复制文件。在途计划保留当前文件名即可，收口后按职责处理，不强制一次全仓改名。
- 新增研究题单先留本地或任务讨论；形成共享实施依据、独立约束或有价值决策后才选择性入库。临时辅助脚本遵循个人工具位置约定，不混进产品源码。
- 当前规范、未来选项、历史事实在导航和正文明确分开。文档头部与正文/代码不一致时先标识并核对，不按日期最新者自动覆盖已定规则。
- 阶段收口、需求被替代、引擎选型完成和发布准备时顺手处理相关文档；不要求每个提交全仓扫文档，也不新增专门治理服务或强制每周报告。

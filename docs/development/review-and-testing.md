# 审查与测试规范

更新：2026-11-01。适用于本项目后续开发与文档任务。本文明确验证范围，不修改现有 CI、分支保护或发行门禁；历史验收记录保留当时实际执行范围。阶段方案中的“每步审查验证”默认按本文执行，不解释为每步全仓审查或全量测试。用户明确要求完整审查或指定检查时，以该次要求为准。

## 1. 分工与基本原则

代码、文档、验收记录的审查和测试执行由 GPT-6 Luna（`gpt-6-luna`）子代理负责；主代理协调、实现修复并按授权提交。模型或子代理不可用时明确说明，不自行更换模型。分工不意味着每轮都必须全量扫描。

每轮验证前用简短说明列出：本轮需要证明的行为/约束、拟审查范围、能证明它的检查或测试子集。无需为普通小改动另建计划或等待额外批准。选择最低成本且足够的证据；没有必要时不增加测试，不写镜像实现的断言。

## 2. 增量审查

- 默认审查本轮 diff，并读取理解变更必需的直接调用方、依赖、状态归属、接口契约和相关测试；不重复阅读无关代码或所有设计文档。
- **跑测试之前先完成本轮代码审查**：读代码、逐条对契约与接口核对，再运行测试。测试输出只用来确认审查已预见的行为，而不是用来发现语法、类型与签名错误——那说明审查没做够，代价是陷在被动排错里。
- **凡"量由输入决定"的地方，都要有硬上界**（案例与做法见[PDF 内容核验的实现选择：问题与建议](../reviews/pdf-content-check-decision-2026-11-04.md)）：读文件、解压、展开区间、循环次数、递归深度、数组长度——这些的上界常常来自文件内容而非代码。逐处问一句"这个数由谁决定、最坏多大"，没有上界就补上。**偏移量也要统一**：相对偏移与绝对偏移混用会让游标倒退，同一段数据被反复处理，内存一路涨到进程被杀掉（2026-11-03 的 PDF 检查器就踩了这两个：区间展开与游标倒退）。
- **构建覆盖面要与改动范围一致**：默认构建不编译 feature 门控的模块或条件分支，"默认构建通过"不代表那些代码可编译。改动涉及 feature 时必须同时构建该 feature（例：`cargo build` 与 `cargo build --features pdf-probe` 都要过）。
- 修复后复审新增差异和原问题，补查受影响上下游；未变化且前提未失效的部分复用原结论。不得将部分审查称为全仓审查。
- 修改公共接口、共享状态、持久化结构、授权、资源生命周期或输出语义时，扩大到相关调用链和关联契约；无法界定影响时扩大审查，直到能确定验证范围。
- 文档审查区分措辞与行为要求：措辞只查相应章节、术语和链接；接口/架构变更还需核对相关实现及直接关联方案，不默认审查全部文档。
- 阻塞问题必须处理；CI通过不替代审查。非本轮引入的问题记录影响，不因“既有”而标记相关门禁通过，也不无授权扩大修复范围。

## 3. 按风险选择验证

| 改动 | 默认验证 | 扩大条件 |
| --- | --- | --- |
| 纯说明、注释、文档措辞 | 差异、相关术语/链接/示例和空白检查 | 文档改变行为契约时核对实现；不跑无关代码测试 |
| 局部纯逻辑 | 对应单测和必要负例；相关静态检查 | 影响公共转换或多个调用方时增加相关集成测试 |
| 类型/模块边界 | 项目适用的 typecheck、边界检查及相关单测 | 公共类型、生成配置或多构建目标受影响时覆盖相应目标 |
| UI交互/布局 | 对应组件/功能组测试；有视觉影响时检查实际渲染 | 输入、焦点、滚动、Tab或多组件状态变化时增加相关工作台E2E |
| 导入、源保存、预览/导出链路 | 相关单测/集成与功能组E2E，覆盖失败/取消/清理 | 共享核心、持久化或跨格式行为变化时扩大相关回归 |
| 依赖、锁文件、运行时、构建与CI配置 | 安装/解析/构建及受影响测试环境检查 | 影响覆盖多个功能组或范围不确定时全量自动验证；平台变化补对应环境 |
| feature 门控的代码或模块 | 该 feature 的构建 + 相关测试（默认构建不覆盖它） | 涉及多构建目标时覆盖相应目标 |

类型检查、lint、边界检查可能本身需要扫描全项目；允许运行它们，不等于要求全仓人工审查或全量E2E。若工具不支持可靠局部检查，运行必要的完整静态检查，不另造不等价的快捷检查。

Vitest的changed/related可辅助选择；Marklflow浏览器E2E通常通过URL访问应用，测试import图不能完整反映业务源码影响。按多Tab、导入、同步滚动、PDF/字节交付等用户流程选择测试，不能因自动选择为空就认定不需验证。UI变更不得只用静态检查代替交互/视觉证据。

## 4. 证据复用与重复执行

- 记录原验证对应提交或工作树差异、测试范围、命令、结果及必要环境。复用前比较后续改动：相关代码、依赖、配置、测试/夹具、产物和环境不变，或有充分依据证明不影响该结果，才可复用。
- 后续修改使相关前提失效时，只重跑受影响层级；无法确定失效范围时扩大。提交SHA改变但只新增无关说明，不自动使代码测试证据全部失效；同SHA但使用陈旧dist也不能复用。
- 区分“本次执行通过”和“引用此前通过结果”。不把旧结果改标为当前重新执行，不把Windows本地证据当Linux CI、浏览器交接当实际保存文件。
- 同一有效代码树已在CI通过的等价检查通常不需本地重复；若本地/目标平台本身是验证对象，或CI环境/产物不等价，仍需相应验证。
- 不因报告措辞、提交动作或测试后新增无关文档而重复全套测试；新代码变化、失败、环境变化或证据缺失足以影响结论时才补跑。
- 保留首次失败。重试通过不能抹去不稳定性；没有有效证据时说明缺口，不能以减少执行范围掩盖失败。

## 5. 全量验证触发条件

满足以下条件时运行对应范围的完整验证，不机械要求所有OS、所有手动验收每次重做：

- 重大架构重构或跨多个功能组的行为变化，定向验证无法充分证明整体仍可用。
- 公共核心、持久化格式/恢复、任务协议、依赖/构建/运行时变化，影响广泛或无法可靠界定。
- 多个小步累计到功能或阶段收口，需要验证组合行为；是否全量以累计影响决定，不因任意“小步完成”自动触发。
- 局部验证出现无法解释的跨模块失败，影响分析或定向测试不足以排除回归。
- 发布候选、明确要求全量的阶段门禁、CI/受保护分支规定，或用户明确要求完整审查与回归。

“全量”须说明含哪些检查、测试、构建目标及环境。全量自动测试不等于全仓人工逐行审查，也不等于系统保存、Word/WPS或跨OS包已验收。发布要求的人工证据和平台矩阵保留，不由局部验证豁免。

## 6. 报告与CI边界

普通任务用简短结果列出审查/测试范围、实际结果、复用证据及未验证项即可；不强制每次创建独立长报告。复杂阶段、重大缺陷、系统输出和发布证据按既有方案归档。

本规范不更改现有工作流：若CI仍运行完整check或E2E，继续尊重其结果；本地小步不必为形式对称重复执行。后续如要调整CI路径过滤或测试选择，应独立授权、审查和验证，保证必需检查有明确运行/合理跳过结果，不能绕过分支保护。审查完成不授予提交、推送、合并或发布权限。

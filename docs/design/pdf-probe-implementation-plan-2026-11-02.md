## 4. D1a 最小来源限制

生产代码，**不受 `pdf-probe` 控制**，D8 生产接入复用。

### 4.1 动作

1. 保留现有 async 命令签名，注入 owned `tauri::Webview`，在文件与对话框副作用**之前**执行来源限制。
2. 明确主界面与输出宿主的静态(window label, webview label)配对，真实调用者和可信创建路径为前提；不增加当前不需实例ID。受保护敏感命令默认拒绝，确需允许才列入，不自动授权新宿主。允许范围为**静态、默认拒绝**：未列入的窗口与独立 webview 一律受限。身份为 **label 级**，即窗口 label 与 webview label 的配对，不引入实例标识——实例级会使允许范围必须动态化，等同权限平台。
3. 判定逻辑收在一处（共享守卫函数），各敏感命令调用它。守卫塑造成**纯函数**：以允许范围与调用方身份为输入，返回允许或共享稳定拒绝码。不引入注册表、配置层或权限平台。**受保护命令集合**为当前 `files.rs` 的 5 个命令：`select_native_open`、`select_native_save`、`read_native_text`、`write_native_bytes`、`release_native_file`；`get_platform_info` 不在其中（它不受守卫限制，但按Q46承担D1a-6的调用方身份回报职责）。身份与命令是两个正交维度——允许范围管哪个身份，命令集合管哪个对象，守卫按命令安装。
4. 来源守卫使用一处共享稳定拒绝常量，语义唯一、与业务错误不混淆，不新增错误命名空间框架。现有UI可见路径映射友好提示，不露裸码/调用方/允许名单；探针按机器码，受控内部验收记录可保必要身份。
5. 输出宿主的身份由生产侧具名常量定义（label 与形态同源），允许范围引用该常量；D1b、D1c、D8使用生产单点身份定义与创建函数；输出身份不自动加入允许范围。宿主创建归D1b，D1c 复用该创建函数/身份/形态，每次创建独立实例而非共用实例。

   两条一致性证据：定向源码检查实现引用单点定义且无无意副本（不是编译器证明无重复字符串）；运行断言实际窗口/WebView身份等于预期。每次运行创建独立实例，不共用运行实例；生产创建路径不受pdf-probe控制。

### 4.2 断言

| # | 断言 | 判定依据 |
| --- | --- | --- |
| D1a-1 | 注入owned Webview且身份解析符合预期 | 类型检查通过；`Webview` 与 `WebviewWindow` 的解析行为与 D0-4 一致。**本断言在 D1a 只覆盖注入签名与主窗口身份取值接线，不代表真实IPC调用已验**：输出宿主在 D1a 时尚不存在，其对应部分由 D1b 的证据矩阵承担 |
| D1a-2 | 允许范围按真实身份映射表达，不假设 label 相等、不以枚举即允许 | 允许范围含窗口与 WebView 的身份对；同窗新增 WebView 不自动被允许 |
| D1a-3 | 允许范围的判定正确 | 主窗口身份对在允许范围内时守卫放行、范围外身份对返回共享稳定拒绝码，由 Rust 单元测试断言（守卫为纯函数，不依赖 Tauri 运行时或生产调用方）。端到端允许路径的运行期证据归 D1b-2 |
| D1a-4 | feature 关闭时来源限制仍生效 | 以默认 feature 集构建，上述单元测试仍通过，且守卫代码不在 `pdf-probe` 之后；仅证明编译边界与判定逻辑，入口接线由D1a-5另证，真实IPC拒绝归D1b |
| D1a-5 | 限制发生在副作用前 | 对守卫/命令入口定向检查：拒绝返回共享稳定码、后续文件/对话框副作用未执行；另核对五入口均调用守卫、身份取自原生注入、拒绝码正确传递；证据采用定向源码审查或可行入口级测试，不能用纯函数单测替代。接线检查按五个入口×四项（守卫调用／原生身份来源／拒绝返回路径／检查先于副作用）列清单，每项标源码或测试位置；源码证到返回值路径，实际IPC响应归D1b。主窗口及真实输出宿主IPC调用证据在D1b，不要求尚未创建的宿主在D1a实际返回拒绝 |
| D1a-6 | 允许范围写入的主窗口身份对与运行中实际值一致 | 运行中的完整(window label, webview label)由**既有非敏感命令 `get_platform_info` 注入 owned `tauri::Webview` 后回报**（按Q46）；不新增阶段或命令。`get_platform_info` 不属受保护命令集合，不受守卫限制，但承担身份回报职责；前端 `platformInfoSchema` 为strict解析（`src/core/platform/tauri/runtime.ts:3`），**加字段必须同步改schema与`TauriPlatformInfo`类型**，否则既有读取路径解析失败。D0配置/创建路径可作为初始依据，运行值用于校验，避免仅用同一常量自证；不提前接M4/M5生产文件交互。不一致先核实际取值路径与配置版本，再修正身份映射或允许范围；运行身份匹配不代表真实IPC隔离已验。本步不一致须排查修正后再退出，不留作D1b已通过前提 |

## 5. D1b 授权夹具与权限探针

仅测试路径受默认关闭的 `pdf-probe` feature 控制。**正常授权释放、来源检查与业务清理始终保留**，不得随 feature 一并消失。

### 5.1 日志基座（L1/L2，D1b 取证的前置）

D1b 的证据要能被机器校验，也要在交付宿主上看得见：Windows 的 GUI 应用没有控制台，stdout 会丢；而一份"人读一份 JSON"的证据也无法机器复核。故在取证之前先立日志基座：L1 是 Rust 侧，L2 是 web→Rust 回传。

**L1 Rust 日志基座**

| 项 | 决定 |
| --- | --- |
| 框架 | `tracing` 做门面、`tracing-subscriber` 做输出（`default-features = false`，开 `fmt`/`ansi`/`std`/`json`）。不引 `env-filter`（正则）与 `tracing-log` 桥 |
| 过滤 | `MARKFLOW_LOG` 解析全局级别；默认 debug 构建 INFO、release 构建 WARN |
| 形态 | 人读一行式为主（时间 级别 目标 字段=值）；`MARKFLOW_LOG_FORMAT=json` 切 JSON 行 |
| 主 sink | **文件**：`app_log_dir()/markflow.log`。**size 与 day 双约束轮转**（单文件 8 MiB 或跨日即轮转），归档 `markflow.log.YYYY-MM-DD.NNN`，只保留最新 10 份 |
| 次 sink | stdout（tee）。开发期的快反馈回路 |
| 写入 | 专用写线程 + 有界队列；队列满则丢行并计数。**UI 线程不得被日志阻塞** |
| 运行标记 | 每次进程启动写一行 `event=run_start run_id=… os=… arch=… app_version=… feature=…`。轮转后一个文件含多次运行，靠它圈出本次 |
| 凭据策略 | 开发构建输出完整 key，该行标 `secret=true`；**发布构建不输出完整 key**（编译期门控，非运行时开关）。日志不含文档内容与文件路径 |

**L2 web→Rust 日志回传**

| 项 | 决定 |
| --- | --- |
| 通道 | 新增 `log_event` 命令，web 侧事件经它进入同一套日志 |
| 边界 | **该命令只写日志，不铸任何授权**：D1b 的"无命令能铸造授权"这条实质性质不变。逐字意义上的"`invoke_handler` 不变"在此放宽为一个例外 |
| 防伪造 | **每条事件按发生地判定可信来源**：native 侧事件只认 `origin=rust`，web 侧事件只认 `origin=web`。两侧都写不出对方形状的事件——web 消息只进**不透明字符串字段**，绝不映射成 `event=` 这类结构化字段；Rust 侧事件也不写成 web 的形状 |
| 限流 | 单条长度上限 + 按窗口限频；超出丢弃并计数 |
| 身份 | web 行带调用方身份对，由 Rust 侧归属 |
| 探针页 | 补 DOM 步骤日志（页面侧叙事），与 DOM 报告一起被 Rust 读入日志 |

**证据形态**：D1b 的证据 = 日志文件，归档至 `docs/acceptance/pdf-probe/`，记录原始文件的 SHA-256。JSON 形态下六条断言由机器校验。

**证据按发生地分侧**：许多事件本来就发生在 web 侧（页面是否加载、页面发起了哪几次调用、页面侧有无异常），这些只有 web 侧知道，故 **web 侧事件是其领域的权威记述**，不是旁证。判定规则是：native 侧断言查 `origin=rust` 的行，web 侧断言查 `origin=web` 的行。

**两侧一致性是防伪造的真正着力点**：同一次调用在两侧各留一份记述（native 侧记守卫判定与拒绝码，web 侧记自己发起了什么调用、收到了什么结果），校验器比对二者是否相符。任何一侧伪造或谎报，都过不了这一关——这比"只信一侧"更强，因为它把两侧都变成了对方的对照。

**归档含完整 key 的开发日志为何安全**：能力是进程内的（`FileAccess` 是内存 `HashMap`），铸出 key 的进程退出即失效，**日志里的 key 在归档时必已是死的**。故归档原始日志即可，不剔除 `secret=true` 行，开发期不增加步骤。

### 5.2 动作

1. `pdf-probe` feature 默认关闭，显式启用；不以 `debug_assertions` 替代。
2. Rust 受限初始化铸造受控授权：**不经 IPC**，不新增前端铸造命令，**不新增任何能铸造授权的命令**。【TBD-14 已决：复用生产侧 `FileAccess` 授权形态；key 经探针页 URL 的查询串交付。详见 §5.1 与阶段记录】
3. 读、写两种角色分别签发（`files.rs` 按 `writable` 校验角色）。
4. 创建输出宿主作为探针载体：使用生产侧单点创建函数、身份定义与形态；D1c复用同一路径但每次创建独立实例，不共用运行实例。断言实际窗口/WebView身份与预期一致，不自动将输出身份加入允许清单。
5. 独立探针页：带脚本，与交付用样本分离；不为测试放宽生产 CSP。
6. 记录实际构建命令与有效 feature 集合；核 feature 关闭构建中测试入口确实不存在。
7. **L1/L2 先于取证落地**：日志基座可用后，探针的每一项观测都以日志行留痕；探针页的事件经 DOM 报告与日志回传两条通道汇入 Rust。

### 5.3 证据矩阵

证据来源：六条断言的判定依据均取自**日志文件**（JSON 形态），按**发生地分侧**：native 侧断言查 `origin=rust` 的行，web 侧断言查 `origin=web` 的行（web 消息在不透明字符串字段里，由校验器解析为其领域的记述）。探针页自身的 DOM 报告经 Rust 读入后同样以 `origin=rust` 落日志——那是 **native 侧对页面结果的读数**，与页面自己的记述（`origin=web`）互为对照，两侧相符才算数。

| # | 证据 | 判定依据 | 作废条件 |
| --- | --- | --- | --- |
| D1b-1 | 通道阳性 | 主窗口 `get_platform_info` 成功 | 阳性不成立则 D1b-3 与 D1b-4 一律作废 |

证据路径：D0-3只给源码/配置预期，D1b确认实际来源。若来源守卫执行，用共享稳定码作正向证据，不匹配Tauri消息；ACL确先拒绝时用绑定实际Tauri版本且可靠的权限识别方式，依据失效则拒绝性质未确认。不能凭D0预期宣称某层运行，不能用排除业务串取代正向识别，也不要求稳定码路径无任何平台调用依赖。具体层不明但性质已确认时仍按§8记录归因与复验限制。锁定版本下COM绑定只有webview2-com一条路线（windows 0.62.2不含WebView2绑定），实现不得与windows crate的COM类型混用。

### 5.4 退出条件

D1b-1至D1b-6成立，权限拒绝正向确认，探针有效；具体层归因允许未确认并保留§8复验限制，未知错误不能通过。

日志基座的退出条件（L1/L2 各自成立）：L1——守卫判定与探针生命周期均有日志行；全局级别可调；人读与 JSON 双形态可用；六条断言能从日志行机器校验。L2——web 侧事件进入同一套日志；**web 行不能伪造出可被读成 Rust 事件的行**；长度与频率有上限且丢弃可计数。

## 6. D1c 隐藏宿主与原生输出

### 6.1 动作

1. 输出宿主：**用与 D1b 相同的创建函数、同一常量与同一形态创建**（独立 label、`visible(false)` 的专用 WebviewWindow），复用其 WebView2 控制器；不并行建设其他宿主形态，不自动换宿主。每次运行各自创建一台，走同一路径而非共用实例。
2. 原生接口访问与转换、`PrintToPdf` 异步完成回调、COM 引用与回调生命周期、加载与基本清理。
3. 受控就绪检测：目标顶层导航成功且文档加载完成、`document.fonts.ready`、图片成功加载或解码、页面盒数量与尺寸核对。HTML `img` 与 SVG `image` 按实际 API 分流。**不使用固定睡眠，也不以 rAF 为必需就绪条件**；不开放作者脚本；须证明受控检测与 CSP 兼容。【待定 TBD-11：原生受控脚本执行是否受冻结 HTML 的 `default-src 'none'` 约束未核，若受限则就绪检测路径需另找】

5. 清理：成功、失败、超时、关闭均释放宿主与临时资源。超时后须先使原生任务不能再提交或写入目标，再清理临时文件；迟到回调不得报成功。

## 8. 失败归类与证据复用

| 失败类型 | 归类 | 说明 |
| --- | --- | --- |
| 权限拒绝性质无法证明或限制不满足 | 未能确认 / 阻塞 | 不算隔离通过，不是宿主形态问题 |
| 权限拒绝已证明，仅具体层归因未知 | 可限定范围通过D1b，归因单独未确认 | 记录全部相关前提，D7/D8不得缩窄复验，不强迫补层名 |
| 探针无效或阳性无效 | 未能确认 / 阻塞 | 阴性证据一律作废 |
| 环境或依赖缺失 | 未能确认 / 阻塞 | 不是路线证伪 |
| 清理失败 | 阻塞 | 须记录阻塞并停止后续接入，不能称基本清理通过 |
| 原生加载 / 接口 / 输出机制限制 | 当前形态不可行 | 须有明确可复现证据 |

**证据复用**：D1c/D1d 的 PDF 失败不自动作废 D1a/D1b 的来源与权限证据。仅在相关代码、配置、依赖、宿主身份与来源、调用路径等前提仍匹配时可复用；后续变化影响其结论须补受影响验证。不得简化为"Rust 代码还在即可复用"，也不要求一轮探针对未到达的所有层都给运行通过。

**D1b-3 失败的归因回指**：证据已记录实际拒绝层，据此回指，不把"未能确认"当作终点。

| 观察 | 结论/候选原因 | 下一步 |
| --- | --- | --- |
| 守卫对本应拒绝的实际输出身份返回允许 | 允许范围或身份提取待查 | 核实际身份、允许范围及取值路径 |
| 同一请求可靠对应共享拒绝码，且无业务效果 | 来源守卫拒绝有效；有可信运行对应证据则层已知 | 按现有其他对照与退出条件核验，不误记层未知 |
| 已有拒绝记录却另有操作成功 | 证据对应、入口漏接、结果传播或副作用先于拒绝待查 | 先核请求/命令/实例/版本一致性，再定位实现 |
| 请求未到守卫 | 原因待查；ACL/路由/通道均为候选 | 取得通道与阳性对照、注册路由及正向拒绝证据；不凭未调用认定ACL |

本段只补归因，不改 D1b-3 的通过条件。

**装配缺陷与隔离失败的区分**：探针自身也有状态（它铸授权、撤授权、加载页面），故探针没跑对与隔离不成立必须分开记，否则一次工具故障会被读成设计被证伪，把正确的设计推向错误的结论。以下对照表用于判读观测结果：

| 观测 | 归属 | 含义 |
| --- | --- | --- |
| 报告为空、页面未加载（窗口停在 `about:blank`） | **装配缺陷** | 探针没把页面挂上去，与隔离无关 |
| 主窗口读取返回 `unknown-file-key` | **装配缺陷** | 探针页在同一窗口加载了两次，第一遍已撤销受控授权 |
| 输出宿主读取返回 `unknown-file-key` | **装配缺陷** | 受控授权没铸进命令看到的那张表 |
| 输出宿主读取返回 `file-capability-mismatch` | **隔离失败** | 守卫没拦住，命令进到了角色校验 |
| 输出宿主读取正常返回内容 | **隔离失败** | 守卫完全没生效 |
| 输出宿主选择器被拒但屏幕弹出对话框 | **隔离失败** | 守卫落在对话框之后 |

装配缺陷只说明工具要修，不构成对设计的否定；隔离失败才是设计被证伪。

**证据冲突**：先核对同代码/依赖/feature/平台及探针有效性；以可复现结果修正适用范围内D0预期，在新证据注明“修正D0-x结论”，不覆盖历史。单次现象/无效探针不无条件优先。D7/D8复用层归因未知证据不得缩窄，按相关代码配置依赖/身份来源/调用路径整体补验；层已知可帮助选择范围，但不豁免相关前提检查。

### 13.8 日志基座的取舍记录（2026-11-03）

三处取舍值得留档，因为它们都不是唯一解：

1. **落点选文件而非 stdout**：Windows 的 GUI 应用没有控制台，stdout 在生产环境直接丢失；且 stdout 经管道时崩溃会丢尾巴，而崩溃正是最需要日志的时候。更关键的是，**日志文件才能像固化样本那样作为文件归档、哈希与复算**——终端输出是转述，文件是原物。
2. **轮转按 size 与 day 双约束**：单按日，一天的日志可能很大；单按 size，跨日不会切分，时间归属丢失。双约束 + 保留最新 10 份是常见做法；本实现自带写入线程，故不必引 `tracing-appender`（它只支持按时间轮转，且会带 `crossbeam-channel`/`parking_lot`/`time`）。
3. **开发构建输出完整 key、发布构建不输出**：按编译期门控（`debug_assertions`）而非运行时开关，生产保证不会被误开；输出时标 `secret=true` 使敏感行可辨。**归档含 key 的开发日志是安全的**：能力是进程内的，铸出 key 的进程退出即失效，日志里的 key 在归档时必已是死的——故不必为归档增加剔除步骤，开发期也不增加复杂度。

### 两项工程事实

**MSRV由1.98降到1.94，CI一致降版本。** 本机Rust 1.94.0低于原声明的1.98（原声明来自M1当时的本机1.98.1），`cargo build`因版本不足被拒；降到1.94后`cargo build`（225 crates）与`cargo test --locked`（6 passed／3 suites）通过。`.github/workflows/tauri-build.yml`的toolchain同步由1.98.1降为1.94.0，与Cargo.toml声明一致，MSRV下限在CI中得以验证。 本机Rust测试6项通过：files.rs共7个`#[test]`，其中`persist_failure_preserves_existing_file_and_cleans_temp_file`为`#[cfg(windows)]`，在macOS不编译——与M3记录的「7项Rust通过」为平台差异，非用例缺失。

**固化产物不是字节可复现的，但这不是缺陷也不需要解决。** 同一受控源两次生成字节数相同而SHA-256不同，原因是Paged.js写入635处随机UUID属性（`data-ref`、`data-split-to`、`data-split-from`等）。仓库既有产出身份模型**从不对产出字节做哈希**，而以输入哈希承担：`exportContent.ts:18`的`renderConfigVersion`为sha256({contract,theme,options,css,assets[source,sha256]})、`mdHash`为sha256(markdown)，`previewIdentity.ts:7`的预览缓存键即(documentId,previewKind,mdHash,renderConfigVersion)，对可能不完整的产出另用render nonce区分（`documentRepository.ts:50`）。故沿用同一模型：**`mdHash`与`renderConfigVersion`承担「同一输入」的稳定身份，文件SHA-256只作为该文件的完整性校验**；实测输入哈希跨运行一致、文件哈希每次不同，与既有模型吻合。不引入UUID归一化等自造手段，也不为哈希改生产代码。

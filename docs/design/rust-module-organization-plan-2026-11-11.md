# Rust 模块整理方案

日期：2026-11-11。分支：`architecture-refactor`。观察基线：`9352a53`；整理实施基线须在日志 LS1–LS3 完成后重新冻结。状态：仅规划，未实施。本文不修改现有产品语义、IPC 契约、依赖版本或发行要求。

## 0. 前置语义修正

先按[日志设计 §6.2](log-base-plan-2026-11-03.md)完成 LS1 → LS2 → LS3：非法 call_id 不影响业务；无关联页面事件挂 run；保留 8 MiB/UTC 跨日轮转、默认 14 天清理并取消数量/总量上限。每步单独审查验证提交。这些是明确授权的行为修正，不夹带进模块移动。

仅在三步代码与自动验证完成后进入 N0，再依次 N1、F1–F3、L1–L3、X。N0 冻结修正后的行为和接口；本方案下文“保持不变”均相对该新基线，而非保留旧的非法 ID 早退、无 span 或10份裁剪。真实 Windows 证据、平台目录和日志获取入口仍可列待补，不能因结构整理而改成完成。方案制定时的文档提交不构成实施；当前 LS1/LS2 已完成代码及自动验证，见[LS1记录](../reviews/log-ls1-2026-11-11.md)及[LS2记录](../reviews/log-ls2-2026-11-11.md)。LS3 未实施，N0 和后续模块整理尚未开始。

## 1. 目标与范围

按“中性命令契约 → files.rs → logging.rs”的顺序，减少职责混杂及业务对日志定义的依赖。使用现有 crate 内模块及私有函数组织，不引入通用框架、事件总线、任务引擎、Service/Repository 层或为拆分而建立 trait。目标不是文件行数达标，也不单独搬走测试制造文件变小的结果。

基线约 6900 行，包含注释和测试。logging.rs 2362 行、files.rs 2092 行；两者的末尾测试模块分别从约 1687、1280 行开始。行数只用于定位阅读成本，不作为验收指标。

本轮保留 config、hash、source_guard 以及现有 PDF 多模块边界。PDF 的文档/宿主流程、Tauri 桥接与 Windows COM 封装各有职责，print_host 虽薄也不合并。probe 仍受 pdf-probe feature 隔离。

## 2. 不变约束

- IPC 命令名称、注册面、参数名及大小写、可选 call_id、返回值、错误码、选择器取消口径和字段序列化保持不变；不要求前端迁移。
- Rust 持有路径与授权，前端只持有不透明 key；来源守卫、授权能力、释放时机、会话身份、文件引用及摘要基线保持不变。
- 原文件写回、新目标写入与 PDF 输出的语义保持分离；保留同目录临时提交、覆盖复核、原有大小限制和清理顺序。提交前复核不是跨进程原子 CAS，不新增此承诺。
- 日志 schema、字段、枚举、来源身份、调用关联、接收回执、限流与队列预算、健康计数、stdout 默认关闭、默认 INFO、执行等待及退出期限保持不变。
- 文件迁移会自然改变日志 at 源定位串、构建标识及代码行号；时间戳、随机 ID 和 tracing 内部 span id 本来也不固定。保持字段含义与关联关系，不要求这些动态值与旧运行逐字相等；相关测试应核对新的实际定位，不删除定位断言。
- 仍以冻结 HTML 为导出内容源；不引入截图、Chromium、Puppeteer，不升级 MathJax、不替换 Paged.js。
- 不改变锁持有范围、线程归属、同步/异步执行方式或 COM 发起/完成等待边界。阻塞风险与缓存/资源策略另立行为变更任务，不能夹带在文件移动中。
- 保留当前未完成项：真实 Windows 日志验收、平台日志目录和日志获取入口。结构整理不能把它们改成已完成。

## 3. 目标依赖与所有权

推荐结构如下；名称可在对应小步根据实际引用微调，但不得混入职责重写。

```text
src/
  commands.rs          原生命令枚举与稳定名称映射
  files/
    mod.rs             现有外部 Rust 路径的薄门面
    access.rs          授权、文件引用、摘要与绑定状态
    io.rs              读取、解码、条件提交及相关错误映射
    commands.rs        选择器/拖放接线、来源守卫及文件 IPC 适配
    pdf.rs             PDF 命令授权消费、流程调用与回执适配
  logging/
    mod.rs             原有公开入口与初始化/退出装配
    web.rs             页面载荷、消息词表、准入及限流
    record.rs          字段采集、记录编码与 tracing Layer
    spans.rs           run/command/page_call 的关联状态
    sink.rs            队列、写线程、stdout、轮转及现有保留机制
    health.rs          共享计数与快照
```

commands 不依赖 files、logging 或 Tauri 运行实例。files 和 logging 都依赖 commands；业务不再通过 logging 取得命令分类。WebEventKind、WebResult、消息类别与页面载荷仍属于日志通道，不能把所有词表都塞进中性 commands 模块。

files 适配层依赖 access/io 与日志公开入口；access/io 不反向依赖 Tauri 命令层。若现有方法需要共同的错误码或状态类型，先在 files 内就近共享，不提前建立全项目错误框架。PDF 适配继续调用原有 pdf_print，不复制 PDF 执行流程。

logging 的装配层连接各部件；web 和 record 共享发送口与健康状态，不各建发送通道。跨子模块仅开放必要的 pub(super)/pub(crate) 项，不把内部实现全部改成 pub。全局实例、队列、限流器和 span 表保持原有实例数量及生命周期。

files::… 与 logging::… 的现有外部 Rust 路径优先通过 mod.rs 的有限重导出保持稳定。中性契约的内部导入路径有意调整；旧 logging::WebCommand 如需过渡，只允许短期重导出，不能成为业务永久入口。

## 4. 小步实施路线

每个编号为一次独立的本地提交单位：实施 → Luna 定向审查与验证 → 提交。失败先定位、修复，不靠反复重试或减测获得通过。默认不推送。

| 单位 | 内容                                                                                                                 | 验收重点                                                                                                                                                            |
| ---- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| N0   | 冻结基线清单，记录命令注册、线上名字、参数/结果、守卫入口、日志事件/回执、相关测试与检查脚本位置；识别原有未提交文件 | 清单来自当前代码；记录证据原提交和环境；历史自动通过与 Windows 待验分开。不为冻结默认重跑全量测试                                                                   |
| N1   | 将 WebCommand 及 command_name 移至 commands.rs；修改 files/logging 引用及必要的契约检查脚本                          | 命令分类和名字仍只有一份；注册13/受保护10/例外3/页面可回传11为基线观察值，若实际变化先查原因；枚举 serde 名称、文件限额映射、守卫覆盖不变                           |
| F1   | 将 files.rs 转为 files/mod.rs，先提取 access 与 io；相关测试随职责归属移动                                           | 原有 files 外部路径可用；授权键/引用、摘要、错误码、读取限制、条件写和临时提交行为不变；不延长或缩短锁范围                                                          |
| F2   | 将选择器、拖放和文件命令接线提至 files/commands.rs，保留统一受保护入口；同步路径敏感的源码检查                       | 每条受保护命令仍先进入同一守卫与关联封装；Tauri 注册面和前端调用不变，不能通过删除扫描或放宽规则使检查通过                                                          |
| F3   | 将 PDF 命令及其授权消费、回执装配提至 files/pdf.rs，保留 files 门面                                                  | Windows 既有打印路径成败均释放；非 Windows 保持现有 unsupported 返回及授权状态。saved 判定、目标提交、临时文件和宿主清理不变；pdf_print/print_host/print_com 不重写 |
| L1   | 将 logging.rs 转为 logging/mod.rs，先分离 web 与 health，保留日志公开门面                                            | 消息词表、准入、限流和 accepted/dropped/rejected 不变；四种计数不混算；配置等待与页面非阻塞边界不变                                                                 |
| L2   | 提取 record 与 spans；保留同一发送口                                                                                 | 最终 JSON 的身份/命令/call_id、schema、转义和文本格式不变；身份隔离、迟到/重复/缺失诊断、span 生命周期不变                                                          |
| L3   | 提取 sink 与现有轮转/保留代码，收小 mod.rs 装配                                                                      | 同一个队列和写线程；文件主 sink、stdout 开关与故障处理、退出期限不变。保持 LS3 后的按天保留，不引入目录新功能或恢复数量/总量上限，不替换时间/JSON实现               |
| X    | 核对累计依赖、接口、源码检查及文档，归档验证证据                                                                     | 无业务依赖日志命令分类、无新增循环依赖/重复实例；所有接口基线一致；完成相应收口验证，系统未验项仍保留                                                               |

若某一步移动量超出可可靠审查范围，应在实施前拆成带后缀的小提交，写明依赖与同样的验收约束；不得把“保持行为”改成“顺便优化”。不要求把所有候选文件一次建齐：例如 sink 内的现有保留逻辑可以继续同文件，health 很小时也允许与装配同文件，前提是本步记录判断理由。

## 5. 验证与证据

本次仅设计文档变更：由 Luna 核对方案、现有实现边界和相关检查工具，不执行应用测试。以下是后续实施的门禁，不是本次已完成的验证。

后续每步先说明需证明什么，再按 AGENTS.md 和《分析与验证规范》选择对应档位。改 Rust 时执行仓库要求的 bun run check 与 bun run check:rust；相关功能组用于定位及定向审查，不替代该档位必需检查。N0 仅文档清单按文档范围检查，不默认重测历史已验基线。源码解析型工具会受文件布局影响，须同步调整并保留错误检出能力，不把“移动后找不到”当成没有命令或没有影响。

- N1/F2：命令准入、消息词表、native isolation、文件限额映射；相关机器检查测试与前端原生文件适配测试。`scripts/check-command-admission.ts` 目前硬编码读取 lib.rs/files.rs/logging.rs，N1/F2 需同步读取中性枚举和全部实际命令入口的新位置，保持注册/守卫/例外三方核对及解析失败显式报错。相关 `tests/unit/check-command-admission.test.ts` 随调整补验。
- L1 的路径检查：`scripts/check-message-vocabulary.ts` 目前硬编码读取 logging.rs；迁移后指向实际消息宏调用所在模块，仍从宏调用处解析，不误读定义，缺文件或无法解析时明确失败。`tests/unit/message-vocabulary.test.ts` 保留 LF/CRLF 及错误检出用例。native isolation 继续完整执行，不因其没有上述硬编码路径而省略。
- F1/F3：授权/读写/条件提交/释放测试，PDF 路径相关测试；Windows 默认构建与 pdf-probe feature 编译。真实系统 PDF 保存不由模块整理宣称重新验过。
- L1/L2/L3：消息端口、通道超时/回执、Rust 日志、关联校验器、轮转/故障测试。覆盖 LF/CRLF 的源码检查夹具，保持字段白名单及禁止敏感内容落盘的边界。
- X：按仓库收口档执行 bun run check:full；补 pdf-probe feature 的编译。其他 OS 只报告实际完成的目标编译/CI结果，不把 Windows 通过写成三平台通过。

当前原工作区有未跟踪 PDF 试验测试引用缺失脚本，可能阻塞全量类型检查。不得删除/修改这些文件以过门禁；先报告实际状态。必要时沿用跟踪文件快照验证，注明源码基线、全部本轮差异、锁文件/依赖/配置/夹具、环境、命令和结果，且明确不是原工作区全量通过。快照须包含全部本轮新增模块，不能仅 git ls-files 复制而漏掉尚未跟踪文件。未经确认不把不完整快照当成测试证据。

只有相关代码、依赖、配置、测试/夹具、构建和环境前提不变，或有充分不受影响依据时才复用证据；不得跨模块移动后无依据复用旧编译结果。保留首次失败。模块迁移过程中不修改日志 schema 来方便测试，也不新增只镜像文件路径或行数的测试。

## 6. 暂缓项与退出条件

暂缓更换日志库、手写 JSON/日期算法替代、阻塞池迁移、文件引用映射回收、跨进程锁协议及日志新功能（不含前置 LS1–LS3）。这些属于独立行为或技术选型任务，不是本方案的隐含后半段。

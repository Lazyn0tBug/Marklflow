## 0. 一句话

现在消息有**三种长法**、**三种消失策略**、**三种视觉** ⇒ ⇒ 而它们的差别其实是**语义**（归谁 ✓、要不要打断 ✓、要不要用户确认 ✓）⇒ ⇒ ⇒ 缺的是**"消息的形状"这一维的设计** ⇒ ⇒ ⇒ 不是样式没做好 ⇒ ⇒ ⇒ 是**分类维度漏了一项** ✓。

## 2. 问题（逐条带证据）

**P-1 形状按实现走，不按语义走。**
⇒ ⇒ 同一类语义（要用户知情的状态）在两个地方长成两个样子 ✓ ⇒ ⇒ 用户学不到"这类消息长什么样" ✓。

**P-2 确认策略是偶然的，不是定的。**
⇒ ⇒ 导入结果有"关闭"按钮 ✓，是因为它列了 N 条要读的东西 ✓（合理 ✓）；但**保存失败 10 秒后自己消失** ✓ ⇒ ⇒ 而保存失败恰恰是**最需要用户知情**的一条（内容还在工作区 ✓，用户不知道就会丢 ✓）⇒ ⇒ ⇒ **需要知情与动作的失败在用"最容易被忽略"的形状** ✓ ⇒ ⇒ ⇒ 这是四条里最要紧的一条 ✓。

**P-3 消息在工作区里没有样式区分。**
⇒ ⇒ 顶部两条是**文档流的一部分** ✓ ⇒ ⇒ `bg-neutral-900` 与状态栏同底色 ✓ ⇒ ⇒ 无边框无阴影 ✓ ⇒ ⇒ 读起来像工作区的一行内容 ✓ ⇒ ⇒ ⇒ 与右下角那个浮层**不是同一种东西** ⇒ ⇒ ⇒ 而它们本该是同一族 ✓。

**P-4 一个形状承担了两种语义。**
⇒ ⇒ 存储恢复（**持续状态** ✓）与操作错误（**一次性失败** ✓）共用那条横幅 ✓ ⇒ ⇒ ⇒ 存储恢复该跟着条件走 ✓、操作错误该按失败处理 ✓ ⇒ ⇒ ⇒ 现在只能二选一 ✓。

## 3. 需求（要达成的，验收可查）

| # | 需求 | 怎么算做到了 |
| --- | --- | --- |
| **R-1** | **形状由语义决定** ⇒ ⇒ 一条消息落在哪个形状有规则可查 | 能说出"这条为什么是横幅而不是浮层" ✓ |
| **R-2** | **确认策略是分类维度** ⇒ ⇒ 自动消失 / 手动关 / 处理完才走 ⇒ ⇒ **默认值跟着形状走** ⇒ ⇒ 不再逐处决定 | 不用逐条决定 ⇒ ⇒ 每类一个默认 ✓ |
| **R-3** | **一套视觉令牌** ⇒ ⇒ 消息一律**脱离工作区**：浮起 ✓ 不推挤内容 ✓ 底色与工作区不同 ✓ 边框与阴影一致 | 三个形状并排时看得出是一家 ✓ |
| **R-4** | **无障碍：语气与形状对应** ⇒ ⇒ `role="status"`（礼貌 ✓）与 `role="alert"`（打断 ✓）不乱用 ⇒ ⇒ 不该打断的不用 assertive | 屏幕阅读器不会为可忽略的事打断 ✓ |
| **R-5** | **不多一份事实的副本** ⇒ ⇒ 机器码 ✓、诊断 id ✓、文案仍由已有的那张表给出 ✓ ⇒ ⇒ 消息面不另存一份 | 词表与文案表各只有一处 ✓ |
| **R-6** | **轻量且无侵入** ⇒ ⇒ 见 §5 的判断规则 | 见 §5 ✓ |

## 4. 业界与开源的既有做法（借鉴的部分）

### 4.1 Material Design 3：snackbar / banner / dialog / inline 的分工

| 形状 | 规则 | 用于 |
| --- | --- | --- |
| **snackbar** | 临时出现在底部 ✓ 不打断 ✓ **不要求用户动作**就消失 ✓ ⇒ ⇒ 最多一个 ✓ ⇒ ⇒ 最多一个动作 ✓ ⇒ ⇒ **那个动作不能是"关闭"**（它会自动消失 ✓ ⇒ ⇒ 动作要留给用户真正想做的事 ✓） | 一次动作的完成确认 ✓ |
| **banner** | 重要且简短 ✓ **需要用户动作（处理或关闭）才消失** ✓ 非模态 ✓ 放在顶部 app bar 之下 ✓ | **条件持续为真** ⇒ ⇒ 例如离线 ✓ 订阅到期 ✓ 未保存的改动 ✓ |
| **dialog** | 打断 ✓ ⇒ ⇒ 直到用户回应 ✓ | 破坏性 ✓ 不可逆 ✓ 需要用户做决定 ✓ |
| **inline validation** | 绑在**某个字段**上 ✓ ⇒ ⇒ 条件消失它才消失 ✓ | 字段级错误 ✓ |

⇒ ⇒ **最有用的一条判据**（来自 02UI 的对比）：**"刷新一次之后，这个条件还成立吗？"** ⇒ ⇒ 成立 ⇒ ⇒ **banner**（它该一直在 ✓）⇒ ⇒ 不成立 ⇒ ⇒ **snackbar**（它可以定时走 ✓）。
⇒ ⇒ ⇒ 直接对上本仓那条病 ✓：保存失败的条件（内容没存进去 ✓）**刷新后依然成立** ✓ ⇒ ⇒ ⇒ 不该用会自己消失的形状 ✓。

### 4.2 Fluent 2（Microsoft）：MessageBar 与 Toast 分成两族

- **MessageBar**：**持续** ✓ 可带动作 ✓ 可成组（`MessageBarGroup` ✓）⇒ ⇒ 状态类消息 ✓；
- **Toast**：**短暂** ✓ ⇒ ⇒ 一次动作的回执 ✓。
⇒ ⇒ 与 Material 同构 ⇒ ⇒ ⇒ **"持续 vs 短暂"这一刀是业界共识** ✓。

### 4.3 VS Code：瞬时提示 ＋ 通知中心 ＋ 状态栏

- 一次性的问题 ⇒ **toast**（几秒后消失 ✓）；
- 但**用户必须处理**的问题 ⇒ **进通知中心** ⇒ ⇒ **留在通知列表里** ✓ ⇒ ⇒ 关掉 toast **不等于**问题解决了 ✓；
- ⇒ ⇒ 这条正是 P-2 的反面：**问题还在，就不该让它消失** ✓。
⇒ ⇒ ⇒ 本仓的对应物：**通知中心**那一层还没有 ✓ ⇒ ⇒ ⇒ 而"失败要留到用户处理"这件事，本仓现在也没有对应物 ✓ ⇒ ⇒ ⇒ 这是 R-2 想要的那一维 ✓。

### 4.4 WAI-ARIA APG：`role="alert"` 与 `role="status"`

- `role="alert"` ⇒ ⇒ **assertive** ⇒ ⇒ 立刻打断辅助技术 ✓；
- `role="status"` ⇒ ⇒ **polite** ⇒ ⇒ 等当前话说完再播报 ✓；
- ⇒ ⇒ 形状与语气要对应 ✓ ⇒ ⇒ **不该打断的别用 assertive** ✓ ⇒ ⇒ ⇒ 现在的横幅用了 `role="alert"` ✓ ⇒ ⇒ ⇒ 而它承载的是可忽略的存储恢复 ⇒ ⇒ ⇒ 语气偏重了 ✓。
⇒ ⇒ ⇒ 这条是**可查的** ✓：R-4 的验收就是"逐个形状说得出该用哪个 live region" ✓。

## 5. 造轮子还是用轮子（判断规则）

**沿用应用消息方案 §7.1 的那条规则** ✓：

> 替代品替代的是**通用能力**（Toast 的队列 ✓、计时 ✓、动画 ✓、焦点管理 ✓）且足够轻 ⇒ ⇒ 值得引 ✓，前提是**不带来新的视觉语言** ✓、**不多一份事实的副本** ✓；
> 替代品替代的是**本仓的契约**（机器码 ✓、隔离 ✓、归档 ✓、诊断 id ✓）⇒ ⇒ **不引** ✓。

⇒ ⇒ **按这条规则切本仓的四件事**：

| 本仓要做的事 | 性质 | 结论 |
| --- | --- | --- |
| **形状分类**（哪种消息长在哪、要不要确认） | **本仓的契约** ✓（与三条去向、机器码耦合 ✓） | **不引** ✓ ⇒ ⇒ 自写 ✓ |
| **视觉令牌与外观** | **本仓的视觉语言** ✓（Tailwind 自有约定 ✓） | **不引** ✓ ⇒ ⇒ 任何库都会带它自己的外观 ⇒ ⇒ ⇒ 除非它**无样式** ✓ |
| **通知的存放处与诊断 id** | **本仓的事实** ✓ | **不引** ✓ ⇒ ⇒ 已有那份 ✓ ⇒ ⇒ 库再存一份就是副本 ✓ |
| **计时 ✓、队列 ✓、进出场动画 ✓、焦点 ✓** | **通用能力** ✓ | **可能引** ✓ ⇒ ⇒ 这一层只有几十行 ⇒ ⇒ ⇒ 值不值取决于"轻量且无侵入"能不能满足 ✓ |

⇒ ⇒ ⇒ **引库的最大三个风险**（本仓已经踩过"多一份事实的副本"这个坑 ✓）：
① **视觉语言被替换** ⇒ ⇒ 本仓的形状与令牌就作废了 ✓；
② **要包一层 Provider** ⇒ ⇒ 与本仓的存放处并存 ⇒ ⇒ 两个 store ⇒ ⇒ 事实的副本 ✓；
③ **只能覆盖瞬时那一种形状** ⇒ ⇒ 横幅与面板内那两种**没有库可用** ✓ ⇒ ⇒ ⇒ 也就是说：**引库只能替掉四分之一** ✓。

⇒ ⇒ ⇒ 库那一层的候选与代价**待调研** ⇒ ⇒ ⇒ 调研回来后补进本文 §6 的 Q-6 ✓ ⇒ ⇒ ⇒ **先按"自写"推进** ⇒ ⇒ ⇒ 若调研结论是某个**无样式（headless）** 的库满足"轻量 ＋ 无侵入"⇒ ⇒ ⇒ 则只替掉计时与队列 ✓ ⇒ ⇒ ⇒ 分类 ✓ 文案 ✓ 令牌仍在本仓 ✓.

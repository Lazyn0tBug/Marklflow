## 0. 一句话

现在消息有**三种长法**、**三种消失策略**、**三种视觉** ⇒ ⇒ 而它们的差别其实是**语义**（归谁 ✓、要不要打断 ✓、要不要用户确认 ✓）⇒ ⇒ ⇒ 缺的是**"消息的形状"这一维的设计** ⇒ ⇒ ⇒ 不是样式没做好 ⇒ ⇒ ⇒ 是**分类维度漏了一项** ✓。

## 2. 问题（逐条带证据）

**P-1 形状按实现走，不按语义走。**
⇒ ⇒ 同一类语义（要用户知情的状态）在两个地方长成两个样子 ✓ ⇒ ⇒ 用户学不到"这类消息长什么样" ✓。

**P-2 确认策略是偶然的，不是定的。**
⇒ ⇒ 导入结果有"关闭"按钮 ✓，是因为它列了 N 条要读的东西 ✓（合理 ✓）；但**保存失败 10 秒后自己消失** ✓ ⇒ ⇒ 而保存失败恰恰是**最需要用户知情**的一条（内容还在工作区 ✓，用户不知道就会丢 ✓）⇒ ⇒ ⇒ **需要知情与动作的失败在用"最容易被忽略"的形状** ✓ ⇒ ⇒ ⇒ 这是四条里最要紧的一条 ✓。

**P-3 消息在工作区里没有样式区分。**
⇒ ⇒ 顶部两条是**文档流的一部分** ✓ ⇒ ⇒ `bg-neutral-900` 与状态栏同底色 ✓ ⇒ ⇒ 无边框无阴影 ✓ ⇒ ⇒ 读起来像工作区的一行内容 ✓ ⇒ ⇒ ⇒ 与右下角那个浮层**不是同一种东西** ⇒ ⇒ ⇒ 而它们本该是同一族 ✓。

**P-4 一个形状承担了两种语义。**
⇒ ⇒ 存储恢复（**持续状态** ✓）与操作错误（**一次性失败** ✓）共用那条横幅 ✓ ⇒ ⇒ ⇒ 存储恢复该跟着条件走 ✓、操作错误该按失败处理 ✓ ⇒ ⇒ ⇒ 现在只能二选一 ✓。

## 3. 本版目标

本版一次交付独立 CSS 入口、纯呈现组件和独立样例。现有界面逐处判断是否可在行为等价的前提下迁移。三种消息共用工作台右下消息区域，在同一容器内纵向排列，共享宽度、间距和主题。瞬时通知、持续状态条和操作结果区通过内容结构和动作区分，应用不按形状设置上下多个消息区域。

## 4. 业界与开源的既有做法（借鉴的部分）

### 4.1 Material Design 3：snackbar / banner / dialog / inline 的分工

| 形状                  | 规则                                                                                                                                                                   | 用于                                                      |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **snackbar**          | 临时出现在底部 ✓ 不打断 ✓ **不要求用户动作**就消失 ✓ ⇒ ⇒ 最多一个 ✓ ⇒ ⇒ 最多一个动作 ✓ ⇒ ⇒ **那个动作不能是"关闭"**（它会自动消失 ✓ ⇒ ⇒ 动作要留给用户真正想做的事 ✓） | 一次动作的完成确认 ✓                                      |
| **banner**            | 重要且简短 ✓ **需要用户动作（处理或关闭）才消失** ✓ 非模态 ✓ 放在顶部 app bar 之下 ✓                                                                                   | **条件持续为真** ⇒ ⇒ 例如离线 ✓ 订阅到期 ✓ 未保存的改动 ✓ |
| **dialog**            | 打断 ✓ ⇒ ⇒ 直到用户回应 ✓                                                                                                                                              | 破坏性 ✓ 不可逆 ✓ 需要用户做决定 ✓                        |
| **inline validation** | 绑在**某个字段**上 ✓ ⇒ ⇒ 条件消失它才消失 ✓                                                                                                                            | 字段级错误 ✓                                              |

⇒ ⇒ **最有用的一条判据**（来自 02UI 的对比）：**"刷新一次之后，这个条件还成立吗？"** ⇒ ⇒ 成立 ⇒ ⇒ **banner**（它该一直在 ✓）⇒ ⇒ 不成立 ⇒ ⇒ **snackbar**（它可以定时走 ✓）。
⇒ ⇒ ⇒ 直接对上本仓那条病 ✓：保存失败的条件（内容没存进去 ✓）**刷新后依然成立** ✓ ⇒ ⇒ ⇒ 不该用会自己消失的形状 ✓。

### 4.2 Fluent 2（Microsoft）：MessageBar 与 Toast 分成两族

- **MessageBar**：**持续** ✓ 可带动作 ✓ 可成组（`MessageBarGroup` ✓）⇒ ⇒ 状态类消息 ✓；
- **Toast**：**短暂** ✓ ⇒ ⇒ 一次动作的回执 ✓。
  ⇒ ⇒ 与 Material 同构 ⇒ ⇒ ⇒ **"持续 vs 短暂"这一刀是业界共识** ✓。

### 4.3 VS Code：瞬时提示 ＋ 通知中心 ＋ 状态栏

- 一次性的问题 ⇒ **toast**（几秒后消失 ✓）；
- 但**用户必须处理**的问题 ⇒ **进通知中心** ⇒ ⇒ **留在通知列表里** ✓ ⇒ ⇒ 关掉 toast **不等于**问题解决了 ✓；
- ⇒ ⇒ 这条正是 P-2 的反面：**问题还在，就不该让它消失** ✓。
  ⇒ ⇒ ⇒ 本仓的对应物：**通知中心**那一层还没有 ✓ ⇒ ⇒ ⇒ 而"失败要留到用户处理"这件事，本仓现在也没有对应物 ✓ ⇒ ⇒ ⇒ 这是 R-2 想要的那一维 ✓。

### 4.4 WAI-ARIA APG：`role="alert"` 与 `role="status"`

- `role="alert"` ⇒ ⇒ **assertive** ⇒ ⇒ 立刻打断辅助技术 ✓；
- `role="status"` ⇒ ⇒ **polite** ⇒ ⇒ 等当前话说完再播报 ✓；
- ⇒ ⇒ 形状与语气要对应 ✓ ⇒ ⇒ **不该打断的别用 assertive** ✓ ⇒ ⇒ ⇒ 现在的横幅用了 `role="alert"` ✓ ⇒ ⇒ ⇒ 而它承载的是可忽略的存储恢复 ⇒ ⇒ ⇒ 语气偏重了 ✓。
  ⇒ ⇒ ⇒ 这条是**可查的** ✓：R-4 的验收就是"逐个形状说得出该用哪个 live region" ✓。

## 5. 模块边界

| 模块          | 本版职责                                                                                                                                                                                                                                                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 独立 CSS 入口 | 提供瞬时通知卡片、持续状态条和操作结果区的结构样式，共享底色、文字、语气、边框、间距和焦点令牌。提供默认值和主题覆盖接口，CSS 可独立加载，组件样式不依赖工作台全局类或样式入口。沿用工作台 neutral 灰阶与 teal 强调色，适配应用根节点的明暗主题。三种形状共享底色、边框和圆角层级，浮层适度使用阴影。CSS 仍提供默认值及覆盖接口。 |
| 纯呈现组件    | 提供上述三种 React 组件。接收标题、正文、视觉语气、详情和必要的动作回调，生成可访问的控件和结构。关闭、展开与否和播报触发由外部提供。组件默认使用可访问的控件和结构且不主动播报，调用方可显式提供适当的 role 或 aria-live 语义，也可沿用外层播报区域，同一消息只使用一个播报入口。视觉语气不决定播报紧急度。                      |
| 现有应用接入  | 保留现有调用方的消息归属、可见条件、队列、计时和状态变化。目标位置统一在右下消息区；现有入口的位置迁移依第 6 节单独判断。沿用现有消息文案、机器码及诊断 ID。适配处把已有数据和回调交给呈现组件。                                                                                                                                  |

同仓库提供明确的 CSS 和组件入口。样式与组件无需加载 Marklflow 会话、通知存储、日志或 Tauri。外部动作通过回调协作，无需单独发包或建立第二个消息 store。

**内核地板与构建（2026-11-07 定）**：本应用**不特地兼容老内核** ⇒ ⇒ 地板取"**当前特性所支持的最低版本**" ⇒ ⇒ 被依赖的只有 `light-dark()`（主题靠它 ✓）⇒ ⇒ 地板 = Chrome 123 ✓ Safari 17.5 ✓ Firefox 120 ✓ ⇒ ⇒ 其余特性（`color-mix()` ✓ `:has()` ✓ `text-wrap` ✓ `@starting-style` ✓ `scrollbar-gutter` ✓）都是**渐进增强** ✓ ⇒ ⇒ 不支持时整块丢弃、功能不丢 ✓ ⇒ ⇒ 它们**不抬地板** ✓ ⇒ ⇒ 低于地板的版本不在支持范围内 ✓ ⇒ ⇒ **不写兜底** ✓。**压缩器也要换** ✓ ⇒ ⇒ 只写 `build.cssTarget` 不够 ✓ ⇒ ⇒ 那个只说"降到哪个版本" ✓ ⇒ ⇒ **降级规则仍在** ✓ ⇒ ⇒ Lightning CSS 把 `light-dark()` 降级成 `var(--lightningcss-light,X)var(--lightningcss-dark,Y)` ✓ ⇒ ⇒ 那两个变量从没被定义 ✓ ⇒ ⇒ 值无效 ✓ ⇒ ⇒ 边框、底色、内边距全失效 ✓ ⇒ ⇒ **开发服务器不做这个转换** ⇒ ⇒ 样页对、构建产物错 ✓ ⇒ ⇒ 只看样例必然漏 ✓ ⇒ ⇒ 版本再新也救不了被改写的值 ✓ ⇒ ⇒ **要换的是压缩器本身** ✓ ⇒ ⇒ `build.cssMinify: 'esbuild'` ✓ ⇒ ⇒ 它只压缩、不改写新特性 ✓ ⇒ ⇒ 构建产物里 `light-dark()` 与 `color-mix()` 都是原样 ✓ ⇒ ⇒ 断言量的是应用里那张卡片的**真实底色** ✓ ⇒ ⇒ 改坏了它就红 ✓。

**样式入口的具体约定（2026-11-07 定）**：选择器一律 `mf-message*` 前缀 ⇒ ⇒ 不引用宿主任何类；令牌一律 `--mf-message-*` ⇒ ⇒ 模块给默认值 ⇒ ⇒ 宿主覆盖令牌或改 `color-scheme` 即换主题 ⇒ ⇒ 不另建配色体系；全部规则收在 `@layer mf-message` ⇒ ⇒ **层序由 Tailwind 定** ⇒ ⇒ 应用样式入口用 `@import "./presentation/messages/messages.css" layer(components);` 引进它 ⇒ ⇒ 它落在预检之上、工具类之下 ⇒ ⇒ 预检压不过它、工具类仍能微调它 ⇒ ⇒ **不要自己写层序声明** ⇒ ⇒ Tailwind 的插件会把它整条丢掉（实测：在 `@import` 前后都丢 ✓）⇒ ⇒ 层只能这样挂，不能靠声明改；**样式入口只有一个主人** ⇒ ⇒ 组件入口不 import 它 ⇒ ⇒ 两处都引会出两份副本（实测 ✓）⇒ ⇒ 独立样例自己引（实测 ✓）；形状与语气用 `data-shape` / `data-tone` 表达 ⇒ ⇒ 视觉归样式、组件只出结构 ⇒ ⇒ 纯 HTML 样例能被同一份 CSS 正确渲染；`light-dark()` 与 `color-mix()` **直接用** ✓，`@starting-style` 与 `:has()` 也直接用 ✓ ⇒ ⇒ **一律不写兜底** ✓ ⇒ ⇒ 不支持的内核拿到的就是一份没有颜色的消息 ✓ ⇒ ⇒ 这是接受的代价 ✓（不特地兼容老内核 ✓）⇒ ⇒ 隔离靠命名空间与令牌 ✓（Tauri 的 macOS 走 WKWebView、Linux 走 WebKitGTK ⇒ ⇒ `@scope` 那类"整块丢弃"的做法不作为隔离手段 ✓）。

**视觉约定（2026-11-07 下午定）**：卡片**不局促** ✓ ⇒ ⇒ 宽 26rem ✓、内边距 .875rem ✓、字号 .8125rem ✓、圆角 .75rem ✓、行高 1.55 ✓ ⇒ ⇒ 尺寸都走令牌 ✓ ⇒ ⇒ 宿主要改改令牌即可 ✓。底面**半透明** ✓ ⇒ ⇒ `rgb(252 252 253 / .94)` / `rgb(26 26 28 / .94)` ✓ ⇒ ⇒ 底下工作台透一点上来 ✓ ⇒ ⇒ 不再是一块死黑 ✓。边是**发丝** ✓ ⇒ ⇒ `color-mix(in oklab, 墨色 14%, transparent)` ✓ ⇒ ⇒ 不用实色线 ✓。阴影**柔** ✓ ⇒ ⇒ 两层 ✓ ⇒ ⇒ 托住层次、不压出重量 ✓。**层序** ✓ ⇒ ⇒ 区域**在对话框之下** ✓ ⇒ ⇒ 对话框是模态的、它占着屏幕 ✓ ⇒ ⇒ 消息不能盖住对话框的按钮 ✓ ⇒ ⇒ 在顶栏之上 ✓ ⇒ ⇒ 走 `--mf-message-z` 令牌 ✓ ⇒ ⇒ 宿主改令牌即可 ✓。**退场** ✓ ⇒ ⇒ 组件只说"我正在退场"（`data-leaving` ✓）⇒ ⇒ 渐隐 + 往下沉一点 ✓ ⇒ ⇒ **谁决定它什么时候没在外面** ✓ ⇒ ⇒ 收走的时刻晚于动画 ✓ ⇒ ⇒ 定时消失的那条也是这么走的 ✓ ⇒ ⇒ 不是"啪"地没了 ✓ ⇒ ⇒ 历史实现为动画 180ms、等待 200ms 后收走（`MESSAGE_LEAVE_MS`）；当前实现按第 10 节以 WAAPI 观察 CSS 过渡完成后收口，移除这两份时长的人工同步。

## 6. 现有界面的迁移门槛

先核对右下通知、顶部状态和导入结果、导出面板内提示的现有行为。本轮只修改设计。后续样式与呈现接入先选择能保持关闭和计时、文案与动作、键盘焦点及播报语义的部分。现有顶部入口或面板内提示若移入右下区域会改变操作语义，则保留现有入口，待后续业务迁移；目标布局仍以第 3 节为准。通知外层仍订阅原列表并负责计时，卡片只绘制内容和转发关闭。迁移后移除被替换的重复样式或呈现结构。若需改归属、状态或操作语义才能接入，该处留待后续。保存失败的消失策略是**有意**的行为变更（改为待确认，见第 8 节）⇒ ⇒ 不属于行为等价的迁移 ⇒ ⇒ 不适用上面的门槛 ⇒ ⇒ 它随接入一并实施并单独记录。

**本轮迁移结果（2026-11-07）**

| 现有入口                  | 处置                       | 理由                                                                                                                     |
| ------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 右下通知面                | **已迁移** ✓               | 多条并存 ✓ · 各自可关 ✓ · 10 秒计时仍在通知列表那层 ✓ · 四种语气 ✓ · 播报仍是 `status` ✓ ⇒ ⇒ 行为等价 ✓                  |

| 保存失败                  | **已迁移，且有意改行为** ✓ | 改为待确认 ✓ ⇒ ⇒ 不定时消失 ✓ ⇒ ⇒ 等用户认了它 ✓（第 8 节 ✓）                                                            |
| 顶部存储恢复/操作错误横幅 | **保留** ✓                 | 它是四条不同语义合并的一条（P-4）⇒ ⇒ 拆开要改归属 ⇒ ⇒ 不拆开塞进持续条就要重排文案 ⇒ ⇒ 两者都属于业务迁移 ⇒ ⇒ 本版不动 ✓ |

## 10. CSS 定义退场、WAAPI 观察完成（2026-11-12，已接入，系统验收待补）

### 10.1 范围与职责

仅替换消息呈现生命周期机制，不改变消息分流、归属、文案、现有停留时长、待确认规则、右下共用区域、主题及播报语义。保存失败仍不自动消失，导入结果沿用已有自动隐藏资格。当前 notices.ts 将所有带 category 的通知视为待确认，而不只是 save-failed；本轮保持该规则，不根据视觉语气重新分流。不引入动画或 Toast 库，不建立通用任务平台或消息中心。

- 业务层决定自动隐藏资格及停留期限；关闭消息不改变保存、导出等操作结果。
- 独立呈现适配 Hook 管理计时、过渡观察、完成与清理，仅接收元素引用、隐藏资格、时长和完成回调，不导入 store、会话或平台端口。通知列表、导入结果及开发样例按原语义复用。
- 纯呈现组件只生成结构、状态标记和回调。CSS 独立入口定义 opacity/transform、时长、缓动及减少动态效果；JS 不写动画样式，不调用 animate() 编写另一套关键帧。
- React 管理 shown → hiding → removed。复用 data-leaving 表达 hiding，不另增全局 .is-hiding。完成时由所属列表移除数据、React 卸载节点，不直接 remove() React 管理的 DOM。
- WAAPI 仅观察 CSS 已生成的过渡及其真实时序，替代本节原先的 transitionend/transitioncancel 收口草案和 CSS 时长列表解析；不并存两套正常完成机制。

### 10.2 AbortController 与取消边界

每个消息呈现实例拥有独立控制器，effect 重建创建新实例，旧回调不得影响新实例。支持 signal 的 DOM 监听传入 signal；setTimeout、requestAnimationFrame 仍需显式注册 clearTimeout/cancelAnimationFrame 清理。AbortController 不会自动取消 Animation.finished Promise；所有完成及拒绝回调须检查 signal 和实例有效性。

| 事件                           | 行为                                                                                                  |
| ------------------------------ | ----------------------------------------------------------------------------------------------------- |
| 到期或手动关闭/确认            | 幂等进入 hiding，取消停留计时和未执行的入场 rAF；保留过渡观察和期限兜底，完成后才移除数据             |
| 重复关闭、到期与点击近时序发生 | 同一实例仅进入一次 hiding、仅完成一次，不重新启动退出效果                                             |
| 组件卸载、消息所属页面真正销毁 | abort 清理全部实例监听、计时器及 rAF；使待完成 Promise 回调失效，不等待动画，不回调所属列表或更新状态 |
| 仅切换文档 Tab、消息区仍存活   | 不视为销毁，不增加全局路由监听或清空规则                                                              |

手动关闭不能提前使退出观察失效。观察器卸载不主动 cancel CSS 过渡，CSS 状态及 DOM 生命周期决定其终止；不把外部动画资源据为己有。完成入口先标记完成并清理所有实例资源，再回调列表。Promise 即使稍后返回，也不得重复完成。

### 10.3 React 提交与过渡过滤

由 React 提交 data-leaving 后，在 useLayoutEffect 中对目标卡片调用 getAnimations()，观察已提交样式产生的 CSS 过渡；不在 setState 后立即读取旧 DOM。shown 阶段是否需要读取初始计算样式，须结合真实组件挂载顺序复核：独立夹具读取了一次，但尚未证明生产必须如此。getAnimations 与计算样式读取仍可能要求同步更新样式，不宣称没有样式计算或性能一定更好。

只选取 CSSTransition，要求 effect 的 target 为目标卡片、无伪元素，并且 transitionProperty 属于退出白名单 opacity/transform。使用元素自身 getAnimations()，不启用 subtree；显式 target 过滤保留，排除子元素、伪元素和无关属性（如 background-color）。不等待卡片上所有动画，不让装饰或无限动画阻塞退出。

捕获本次退出的匹配对象，等待其 finished 全部结算（Promise.allSettled）：全部 fulfilled 为正常完成；存在 rejected 表示取消，但仍等待其他已观察退出过渡结算。signal 失效则不完成。该批次只服务一次退出，不实现动画运行中动态重配或持续重采集；运行中样式变化的有限收口由取消与期限兜底保障。

无匹配退出过渡时直接完成，包括零时长、无目标属性变化和减少动态效果产生零时长的情况；前提是读取发生在正确提交时点，不能以空数组掩盖时机错误。主路径验收必须证明正常完成来自 finished，而不是只检查 DOM 最终消失。

### 10.4 引擎时序兜底与 rAF

由已观察对象 effect.getComputedTiming().endTime 取得引擎时序，不再手写解析 CSS transition-property/duration/delay 列表，不维护固定 200ms 删除延迟。常规正向、默认速率的 CSS 过渡是实施范围：从观察时刻起，以各对象 endTime 的非负最大值加集中定义的小幅调度余量设置有限保守期限。它可能略长于实际剩余时间，但不是精确进度计时，不增加 currentTime/playbackRate 换算。缺失或非有限时序采用集中定义、有限的异常默认期限；暂停不能使等待无限延长。不支持动态变速、倒放或退出动画运行中动态重配。独立夹具已验证默认速率、接近起点捕获的 endTime 加余量及暂停后兜底；本轮接入另用真实过渡时序返回非有限值并暂停的故障注入用例，验证有限的异常默认期限。

finished 为正常收口，期限只防止暂停、未结算或异常样式变化使节点永久残留。期限与停留计时均纳入 abort 清理，超期不证明动画正常完成。后台或休眠只保证恢复 JS 调度后收口，不承诺精确墙钟删除。

prefers-reduced-motion 由 CSS 去掉位移并允许零时长；无过渡则直接完成退出，不缩短原有停留期限。退场禁用点击且内部动作不能继续通过键盘执行；删除时沿用既有焦点恢复规则，仅处理该消息所属焦点，不从编辑器夺焦点。页面销毁不主动恢复焦点。

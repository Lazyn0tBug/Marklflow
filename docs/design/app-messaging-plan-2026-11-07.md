# 应用消息方案：分类、去向与记录（2026-11-07）

状态：**设计稿，未实施**。本文不修改代码，也不宣称任何阶段已通过。
关联：[日志基座](log-base-plan-2026-11-03.md)（词汇、通道与取信规则）、[分析与验证规范](../development/analysis-and-verification.md)（验证范围）、[本地文档支持设计](local-document-support-2026-11-05.md) §9（原生侧失败码）。
本文原名《问题通知机制》⇒ 范围长大后改名：它管的不只是错误，而是**应用的三条消息去向**（一次告知、表面状态、操作回执）与它们的记录方式。

## 0. 决策摘要

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 要不要统一 | **要**，但统一发生在**应用层**，不是在测试里另立一套 | 三层各行其是：原生侧有机器码、应用侧**什么都没有**、测试侧只报派生症状。缺口在应用层 |
| **分类维度** | **三条去向**：**一次告知**（通知）／**表面状态**／**操作回执** | 成功与失败是**结果**，不是去向 ⇒ ⇒ 每一类里都有成功与失败 ⇒ ⇒ "失败通知机制"这个名字从一开始就盖窄了 |
| 成功要不要进统一方案 | **通知面要能承载成功**（导出成功已经是 `tone:'success'` ✓）；但**操作的成败是回执** ⇒ 由操作者自己显示 ⇒ 不另发通知 | 同一件事不说两遍 ⇒ 回执给调用者，通知给用户一次 |
| 通知面的形状 | **多条并存 · 可关闭 · 语气四种**（success/info/warning/error） | 现在是**单个状态** ⇒ 后一条盖掉前一条 ⇒ ⇒ 与 `App.tsx` 那个 `\|\|` 短路同源 |
| 模态 | **不用 `alert()`** | 打断正在做的事；且它把**原始异常文本直接弹给用户** ⇒ ⇒ 与"原始文本不进用户面"冲突 |
| 机器码 | **只属于失败** | 成功的分流由 `operation_result` 的 result 枚举与回执承载 ⇒ ⇒ 不必再造成功码 |
| 状态与回执 | 各归各位，**不经过通知面** | 预览渲染不出来是**面板自己的状态** ⇒ ⇒ 明确写清，免得以后被"统一"掉 |
| 用不用新机制 | **不用**。基座已有 `log_event` 通道、`page_error` 事件与封闭的字段白名单 | 通道是通的、词汇是定好的，缺的只是应用往里报 |
| 捕获点 | 三处：**React 错误边界**（渲染期）、**`window.onerror`**、**`unhandledrejection`** | 渲染期错误现在会**白屏**：用户不知道、日志里没有。边界顺带把它降级成局部失败 |
| 出口 | **一个**报告函数 ⇒ 三个消费方：用户可见提示 / 原生日志 / 浏览器控制台 | 一处捕获，多处消费；不再有"某个出口知道、另一个不知道" |
| 原始异常文本 | **不进日志**（基座 §5.2 的硬约束）⇒ 只留在浏览器控制台 | 日志不含异常原文，避免间接泄露 |
| 桌面端因此的诊断力 | **只有"类别 + 诊断 id"** ⇒ 桌面端问题的原文拿不到 | 这是隐私约束换来的**取舍**，不是疏漏；要更强需要单独的脱敏设计（另议） |
| 类别词表 | 扩 `WebErrorCategory`（基座那个封闭枚举），新增应用类别 | 不新增载荷形状 ⇒ 基座"封闭枚举 + 白名单"的原则完整保住 |
| 测试侧 | e2e 读浏览器自身的 `pageerror` 事件（**与应用消费的是同一个事件源**） | 立刻可用，不依赖应用侧；应用侧接上后两者不冲突 |
| 落在哪 | 测试侧那一步可以现在做；应用侧属于**日志基座那条线**（生产接入与可监测性） | 横切面，不属于大纲，也不属于文档资产 |

## 1. 现场事实

### 1.1 三层现状

| 层 | 现在怎么做 | 缺什么 |
| --- | --- | --- |
| 原生侧失败 | **机器码**（见本地文档支持设计 §9 的清单）⇒ 前端按码分流、按码映射文案 | — |
| **应用侧未捕获错误** | **什么都没有**：没有错误边界、没有 `window.onerror`、没有 `unhandledrejection` ⇒ 一个 ReferenceError ⇒ **白屏**，用户不知道，日志里也没有 | 捕获、分类、通知 |
| 测试侧 | e2e 报的是**派生症状**（"等不到 textarea" 超时 60 秒）⇒ 真实错误（`ReferenceError`）被掩盖 | 指到根因 |

### 1.2 基座已经给了一半

[日志基座](log-base-plan-2026-11-03.md) §4–§5 已经定义：

- **通道**：`log_event` 命令（web → Rust）⇒ "只写日志，不铸任何授权"；
- **载荷是封闭白名单**（`deny_unknown_fields`）：`{event, call_id?, command?, result?, error_category?, bytes?}` ⇒ **未知字段或未知事件一律拒收**；
- **事件枚举**：`page_ready` / `call_started` / `call_finished` / **`page_error`**；
- **类别字段** `error_category`：**只传类别，不传原始异常 message**；
- **准入**：写日志有身份判定（正常路径仅主窗口）⇒ 页面不能自报身份获得允许；
- **限流**：每个身份对 20 条/秒、进程内 100 条/秒；请求 ≤ 4 KiB；
- **结果**：`accepted` / `dropped` / `rejected`（accepted **不表示已落盘**）。

⇒ **通道是通的、词汇是定好的。缺的只是应用往里报。** 探针已经在用这条通道（`tests/fixtures/architecture/pdf-probe-client.ts`），生产应用一次都没用过。

### 1.3 浏览器构建没有日志出口

`src/core/platform/web/` 下**没有日志端口** ⇒ 前端只有两处零散的 `console.error`（`ExportModal.tsx`、`storage.ts`）⇒ 于是浏览器构建里，除了控制台，什么都留不下 ⇒ e2e 也就只能读控制台。

### 1.4 应用已经有一个提示面

`App.tsx` 有 `loadError` / `actionError` / `storageWarnings` 三个状态 ⇒ 渲染成一条 `<aside role="alert">`。⇒ 用户可见的通知有地方放，但那是**存储恢复**的面 ⇒ 未捕获错误不该挤进那条（语义不同、样式不同、恢复按钮也不该出现）。

## 2. 语义模型：三条去向

### 2.1 三条去向：一次告知、表面状态、操作回执

成功与失败是**结果**，不是去向 ⇒ ⇒ 去向是"这东西归谁、放多久" ⇒ ⇒ 分三类：

| 去向 | 是什么 | 放多久 | 谁来渲染 | 成功也在这一类里吗 |
| --- | --- | --- | --- | --- |
| **一次告知**（通知） | 一次动作的告知 | 一阵，可关闭 | **通知面**（一处） | **在** ⇒ 导出成功已经是 `tone:'success'` ✓ |
| **表面状态** | 某个表面自己的状态 | 随表面 | **那个表面** | **在** ⇒ 预览就绪、同步状态"已同步" ✓ |
| **操作回执** | 操作的结果，给调用者 | 一次调用 | **操作的调用方** | **在** ⇒ 导出回执 `completed` ✓ |

⇒ 三类**不合并** ⇒ 合并就会出今天这些病：一个状态顶掉另一个（`App.tsx` 的 `||` 短路、通知的单个状态）⇒ ⇒ 同类里也不重复：导出的成功是**回执**（导出面自己显示）⇒ 不另发一条成功通知 ⇒ **同一件事不说两遍** ✓。

⇒ **机器码只属于失败** ✓：成功的分流由 `operation_result` 的 result 枚举与回执承载 ⇒ ⇒ 不必再造成功码 ✓。

### 2.2 一处捕获，三个消费方

```
捕获（三处）   React 错误边界  │  window.onerror  │  unhandledrejection
   └─ 分类     category（封闭枚举）＋ 诊断 id
        ├─ 用户      可见提示：类别 ＋ 诊断 id ＋ 一句可行动的话
        ├─ 原生日志   page_error 事件（桌面端 ⇒ log_event ⇒ 基座）
        └─ 浏览器    console（原始文本留在这里；Web 构建与开发期可见）
```

⇒ 三个消费方看的是**同一次捕获** ⇒ 不会出现"用户看到了、日志里没有"或"日志里有、用户不知道"。

### 2.3 什么算"一个问题"

- **一次捕获 = 一个问题实例**：渲染期的一个错误边界触发、一次 `error`、一次 `rejection`。
- **去重键不是实例，是来源**：键 = (类别, 来源标识) ⇒ 来源标识是"哪个错误边界/哪个脚本" ⇒ ⇒ 一个渲染循环会产生**很多**实例，但只报一条 ⇒ ⇒ 若按实例去重，循环就会刷屏（违反 P-3）✓。
- **诊断 id**：短、稳定、**可复述**（如 `e-7f3a`）⇒ 用户能在报障时念出来；它是**本次运行内**的关联，不是跨运行的指纹（跨运行需要原文或脱敏摘要，而两者都被基座排除了 ⇒ 见 §2.4）。
- **限流两层**：应用侧先限（同一个问题只报一次、每秒至多 N 条），基座再限（20/100 每秒）⇒ 应用侧的限流是为了不浪费基座的额度。

### 2.4 原始文本的去处：只进控制台

基座 §5.2 明确：**`page_error` 只传错误类别，不传原始异常 message**；日志"不含文档正文、完整本地路径或任何授权凭据，包括查询串、**异常**与 DOM 报告的间接泄露"。

⇒ 于是原始异常文本**只留在浏览器控制台**。桌面端没有控制台（基座 §1 的动因之一）⇒ **桌面端出问题时，日志里只有"类别 + 诊断 id"** ⇒ 定位要靠复现。

⇒ 这是**取舍**，写在这里是为了别被当成疏漏：换来的是"日志不含异常原文"这条硬约束完整保住。要更强（桌面端日志里有可诊断的原文），需要**单独的脱敏策略**设计（异常文本里的路径/正文/凭据要怎么处理），那是另一个题目，本文不做。

### 2.5 应用自身的失败：另一条出口

前面讲的是**未捕获**的错误（崩溃那条路）。应用**自己**处理的失败——导出没成功、保存写不进、存储记录损坏、预览渲染不出来——今天散在五处，各说各的：

| 现状 | 位置 | 问题 |
| --- | --- | --- |
| 三个状态挤一条横幅 | `App.tsx` 的 `loadError` / `actionError` / `storageWarnings`，用 `\|\|` 短路 | **一个盖掉另一个** ⇒ 信息丢失 |
| 一个字符串状态承载多种语义 | 五处 `setActionError(拼接的中文句子)` | 后来的覆盖前面的 ⇒ 没有码 ⇒ 不能分流、不能统计 |
| 模态弹窗 | `App.tsx` 的保存失败、`ExportModal.tsx` 的导出失败 | 打断正在做的事；且**把原始异常文本直接弹给用户** ⇒ 与 §2.4 冲突 |
| 同一错误报三份 | `ExportModal.tsx`：`console.error` ＋ `alert()` ＋ `onNotice` | 三份文案可能不一致 |
| 只有控制台 | `storage.ts`、`byteDelivery.ts` 的 `console.warn` | 用户完全不知道 |

⇒ **应用自身的失败走另一个出口**（`reportFailure`）⇒ 与未捕获错误**共用一份报告形状**（§3.1）⇒ ⇒ 但**不共用通知面**：状态与回执各归各位（§2.1）⇒ ⇒ 预览渲染不出来是**面板自己的状态** ⇒ **留在预览里** ⇒ 不是通知 ⇒ 明确写在这里，免得以后被"统一"掉。

⇒ 应用层失败也要**码**（§3.6）⇒ 否则它们没法被分流、没法被统计。

## 3. 契约

### 3.1 报告的形态

应用侧提交给端口的形状（**端口内部的实现再决定怎么落到线上**）：

```ts
export interface ProblemReport {
  /** 封闭类别枚举：与基座的 WebErrorCategory 共用同一个词表 ✓。 */
  category:ProblemCategory;
  /** 诊断 id：短、稳定、可复述 ✓。 */
  diagnosticId:string;
  /** 原始文本：只进控制台，不进日志 ✓（基座 §5.2）。 */
  detail?:string;
}
```

⇒ 落到基座通道时**只发** `{event:'page_error', error_category:category}` ⇒ **`diagnosticId` 与 `detail` 都不进载荷** ⇒ 因为白名单里没有这两个字段 ⇒ ⇒ 于是诊断 id 要另找地方留（见 §8 的 N4）⇒ 或者**干脆不发**（基座日志只需要类别）⇒ ⇒ **本文的结论：通道里只发类别** ⇒ 诊断 id 属于**用户可见的那条提示**与**控制台**，不进日志 ✓。

### 3.2 捕获点怎么接线（React 19 的根选项与 window 事件会重叠）

React 19 的根可以带选项：`createRoot(container, {onUncaughtError, onCaughtError})` ⇒ ⇒ 渲染期的错误由**根选项**接住（分类 `render`）⇒ 局部降级仍需一个**错误边界**（根选项只报告，不降级）⇒ 其余用 `window.onerror` 与 `unhandledrejection`。

**重叠必须消掉**：一个逃出 React 树的错误会**同时**触发 React 的根选项与 `window.onerror` ⇒ ⇒ 报两次 ⇒ ⇒ 处理：React 的根选项报告后，把该错误对象记进一个 `WeakSet`（本次运行内）⇒ `window.onerror` / `unhandledrejection` 遇到已记过的就跳过 ⇒ ⇒ 一次问题只出一份报告 ✓（P-3）。

### 3.3 类别枚举

**词表在基座那边** ✓（[日志基座](log-base-plan-2026-11-03.md) §5.2.1 ✓ ⇒ 基座 §9 说基座拥有词汇 ✓）⇒ ⇒ **这里不重复那张表** ✓ ⇒ ⇒ 只说应用这边怎么用它 ✓：

- **在基座的 `WebErrorCategory` 上扩展** ⇒ **同一个词表、同一套封闭枚举** ⇒ ⇒ **不新增载荷形状** ✓（`deny_unknown_fields` 不变 ✓）。
- **四个族** ✓：通道类（基座原有 ✓）、原生文件类（`files.rs` 给出 ✓）、应用自身类（§3.5 ✓）、捕获类（未捕获的错误从哪来 ✓）。
- **一族一种拼写** ✓：全是 kebab ✓ ⇒ ⇒ 同一个字段里不会混着两种写法 ✓。
- 类别是**枚举** ⇒ 前端与 Rust 两侧必须同步 ⇒ 改基座时两侧一起改（基座已有的"两处必须同步改"先例 ✓）⇒ ⇒ **`scripts/check-message-vocabulary.ts` 兜底** ✓ ⇒ ⇒ 两侧对不上就红 ✓。

⇒ 类别是**码** ⇒ 文案另有一张表（§3.5 ✓）⇒ ⇒ 码与文案不在一处 ✓（改文案不影响分流 ✓）。

### 3.4 三个出口

| 出口 | 做什么 | 不做什么 |
| --- | --- | --- |
| 用户可见提示 | 一条独立的提示（不挤进存储恢复那条）：类别 ＋ 诊断 id ＋ 一句可行动的话 | 不显示原始堆栈；不假装能自动恢复 |
| 原生日志 | 经 `log_event` 发 `page_error` + 类别 | 不发原文、不发诊断 id、不发堆栈 |
| 浏览器控制台 | 原始文本（`console.error`），带诊断 id | 不当作证据（控制台不是归档） |

⇒ 端口放在 `src/core/platform/` 下、**两个实现**（`tauri/` ⇒ `log_event`；`web/` ⇒ 控制台）⇒ 与既有的平台端口同构 ⇒ **应用层不直接碰 `console` 或 `log_event`** ⇒ 这条要进边界检查（`scripts/check-module-boundaries.ts`）。

### 3.5 应用层失败的类别词表

与原生侧**同一套规则**（机器码 ＋ 人读文案两层 ✓，码只在失败时出现 ✓）：

| 机器码 | 含义 | 文案 | 谁报 |
| --- | --- | --- | --- |
| `export-failed` | 导出没成功 | 导出失败，请重试 | 导出面 |
| `export-blocked` | 该平台/该产物不支持 | 这个产物在此平台无法导出 | 导出面 |
| `save-failed` | 草稿落盘失败 | 保存失败，内容仍在工作区 | 工作台 |
| `storage-corrupted` | 存储记录损坏 | 部分记录已损坏，原始数据已保留 | 启动流程 |
| `preview-unavailable` | 预览渲染不出来 | 这一份预览没能生成 | 预览面（**这是状态** ⇒ 见 §2.1 ⇒ 留在预览里 ✓） |
| `import-rejected` | 导入被拒 | 这个文件没能导入 | 导入面 |

⇒ **机器码只属于失败** ✓（§2.1）⇒ 成功不另造码 ✓。

### 3.6 隔离

- 报告**不铸任何授权** ⇒ 沿用基座"只写日志"的性质 ✓。
- 页面不能自报身份获得允许 ⇒ 沿用基座的准入 ✓。
- **报告通道自身失败不再报告自身**（基座 §4 的"失败不再调用 log_event 记录自身失败" ✓）。

## 4. 通知面的规格

通知面承载**一次告知**：成功与失败都在里面（§2.1）⇒ 用**语气**区分 ⇒ ⇒ 机器码只在失败时出现（§2.1）⇒ ⇒ 形状沿用现有的 `ExportNotice {message, tone}`（`ExportModal.tsx:26` ✓ 它已经有四种语气 ✓）⇒ ⇒ 但要从"导出专用"变成**应用通用**。

- **多条并存**：现在是**单个状态**（`App.tsx` 的 `exportNotice`）⇒ 后一条盖掉前一条 ⇒ ⇒ 与 `App.tsx:148` 那个 `||` 短路同源 ⇒ ⇒ 改成一个列表 ⇒ 各自可关闭 ✓。
- **可关闭**：关闭后不重复出现（同一个诊断 id 只提示一次）⇒ 不打断正在做的事 ✓。
- **语气四种**：`success` / `info` / `warning` / `error` ✓（沿用 ✓）。
- **内容**：失败 ⇒ **类别 ＋ 诊断 id ＋ 一句可行动的话**（如"重新加载窗口"）⇒ **不显示原始堆栈**（§2.4）✓；成功 ⇒ 一句话即可（不必带码）✓。
- **不用 `alert()`**：两处模态（保存失败、导出失败）都要退场 ⇒ ① 打断正在做的事；② **把原始异常文本直接弹给用户** ⇒ 与 §2.4 冲突 ⇒ ⇒ 改为可关闭的通知，文本走"类别 ＋ 可行动的话" ✓。
- **渲染期错误由错误边界局部降级**：出错的那块显示"这一部分没能显示"，**其余部分照常** ⇒ 不会因为一个坏组件而白屏 ⇒ ⇒ 这是**表面状态**（§2.1）⇒ 留在那块里，不进通知面 ✓。
- **预览渲染不出来留在预览里**（`preview-unavailable` ⇒ 表面状态 ✓）⇒ 明确写清，免得以后被"统一"掉 ✓。
- **存储恢复提示单独一条**：它是**状态**（工作区有一批损坏记录）⇒ 与"一次告知"不同类 ⇒ 不合并 ✓。

## 5. 测试侧

- e2e 读浏览器自身的 `pageerror` 事件 ⇒ **与应用消费的是同一个事件源** ⇒ 应用侧还没接上时，测试侧已经能用 ⇒ 不是两套机制，是同一个信号的两个消费者。
- 失败信息里带**原始错误** ⇒ 测试失败直接指向根因，不再是"等不到某个元素"。
- **不因为页面有错误就判失败**：有若干用例**故意**触发错误（来源拒绝、诊断、坏图）⇒ 页面错误只**报告**，是否失败由用例自己断言 ⇒ ⇒ 机制放在共享位置，不放在每个用例里。

### 5.1 业界怎么做的（参考路线）

这条路上已经有成熟形态 ⇒ 我们不是自创：

| 项目 | 机制 | 与我们的差别 |
| --- | --- | --- |
| **Cypress** | `cy.on('uncaught:exception')` ⇒ **默认让测试失败**（除非回调里 `return false` 吞掉）⇒ 失败输出里带**异常原文** | 我们多一个开关：**不判失败**（P-7 ⇒ 有意触发错误的用例） |
| **WebdriverIO** | `browser.on('uncaughtException')` ⇒ 同类 | 同上 |
| **Playwright** | `page.on('pageerror')` | **默认判不判失败：待验**（§5.3） |
| jsdom（单元环境） | 未捕获异常直接让该测试失败 | 单元层已经是"失败即现形" ⇒ 只有浏览器层需要这套 |

⇒ ⇒ ⇒ 与这些路线**只差"判不判失败"这一个开关** ⇒ ⇒ ⇒

### 5.2 机制放在哪：可行路线与代价

| 路线 | 状态 | 代价 |
| --- | --- | --- |
| **① 共享 fixture 模块**（`tests/e2e/fixtures.ts`） | **可行**（Playwright 的标准做法）⇒ 已在工作区，**未跑过全量** | 每个用例改一行 import |
| ② 配置层 `use` 覆盖 `page` fixture | ✗ **框架明确拒绝**（运行时：`Fixture "page" cannot be overridden in the configuration "use" section. Only fixtures registered with { option: true } can be set in the config.`）⇒ ⇒ 类型也不接受 ⇒ ⇒ **这条路是死的** ⇒ | — |
| ③ `globalSetup` 包装 `browser.newContext` | **技术上可行**，与"每个用例的 page"脱节 ⇒ 取巧 ⇒ **未验** | — |
| 自定义 reporter | **不是替代**：reporter 只看测试结果，**页面事件它看不到** ⇒ 它能做的是**呈现**已收集到的内容 ⇒ ⇒ 它是呈现层，不是收集层 | — |

⇒ ⇒ ⇒ **本步选 ①**：标准做法、不靠类型断言、失败信息与归档同出一处 ⇒ ⇒ ⇒

### 5.3 已验的事实（2026-11-06 实测）

| 事实 | 结果 | 影响 |
| --- | --- | --- |

| `globalSetup` 包装 `browser.newContext` | **未验** | ③ 仍是备选，但取巧 ⇒ ⇒ 本步不选 ⇒ ⇒ ⇒ |

## 6. 验收

| 编号 | 断言 |
| --- | --- |
| P-1 | 应用启动失败时，页面不是白屏：要么错误边界降级后的提示，要么一条明确的启动失败提示 |
| P-2 | 一个未捕获错误 ⇒ 原生日志里有一条 `page_error`，**带类别、不带原文、不带堆栈** |
| P-3 | 同一个问题重复发生（渲染循环）⇒ 日志里只有一条，应用侧不刷屏 |
| P-4 | 报告通道自身失败（载荷被拒、超频）⇒ 应用不因此崩，也不递归报告 |
| P-5 | 用户可见的提示给出类别与诊断 id，**不含原始堆栈** |
| P-6 | e2e 在页面抛错时，失败信息里能看到原始错误 |
| P-7 | 故意触发错误的用例（如来源拒绝）仍按自己的断言判定，不被"页面有错误"误伤 |
| P-8 | Web 构建下同样的问题落在控制台，且不依赖原生侧 |
| P-9 | 通知面**多条并存** ⇒ 后一条不盖掉前一条；每条可关闭 |
| P-10 | 保存失败与导出失败**不再用模态弹窗** ⇒ 不打断正在做的事；用户看不到原始堆栈 |
| P-11 | 应用自身的失败带机器码 ⇒ 可分流、可统计；与原生侧的码同一套规则 |
| P-12 | 预览渲染不出来仍显示在**预览里** ⇒ 是表面状态，不是通知 |
| P-13 | 三条去向不混：操作的成败是**回执**（操作者自己显示）⇒ 不另发一条成功通知 |

## 7. 不做

- 不做崩溃上报服务、不做远程收集、不做看板与告警（基座 §2 明确不在范围）。

### 7.1 为什么手写：依赖取舍

这套东西看着像通用能力，但三类成熟替代品各撞一条本仓约束 ⇒ ⇒ **手写是结论，不是偏好** ✓：

| 类别 | 代表 | 为什么不用 |
| --- | --- | --- |
| 崩溃上报服务 | Sentry、Bugsnag、Rollbar | ① 基座 §2 明写"不做崩溃上报服务"；② 它多一条**外发网络通道** ⇒ 与隔离模型冲突；③ 它的核心价值（**跨运行指纹聚合**）恰好被基座禁止 ⇒ 指纹要原文，而原文不进日志（§2.4）⇒ 等于最有用的那部分用不上 |
| 日志库 | pino、winston、tauri-plugin-log | 替代不了：原生侧的归档、按运行分文件、span、**身份闸门**、JSONL 校验器是本仓自己的隔离层 ⇒ 换库只会多一份事实的副本（[本地文档支持设计](local-document-support-2026-11-05.md) §3.4 "一个事实一处存放"） |
| Toast 组件库 | react-hot-toast、sonic、react-toastify | 通知面要"多条并存 + 可关闭 + 四种语气 + 不打断"⇒ 队列/超时/关闭是几十行 ⇒ 换来的是**一套新的视觉语言**（本仓的视觉是自有约定）⇒ 且它们自带 DOM 与样式 ⇒ 与 §4 打架 |

**平台自带、但我们故意不用的两个**（写下来是为了免得以后再查一遍）：

- `navigator.reportError(err)`（Chrome 111+）：平台标准的"上报一个**已处理**错误"入口 ⇒ 正好对上 §2.5 的需求 ⇒ 但它把报告交给**浏览器的上报管道**（一条网络通道）⇒ 与隔离模型冲突 ⇒ 不用。
- `Error.cause`：**采纳** ✓ ⇒ 报告的形状借它 ⇒ 原始异常挂在 `cause` 上 ⇒ 控制台打原始文本、日志只记外层 ⇒ "原始文本只进控制台"这条规则在代码里显式可见 ✓。

**形状不是自创，是收敛到业界同一套** ⇒ 免得以后重新发明：

| 子问题 | 参考形态 | 本文对应 |
| --- | --- | --- |
| 捕获 | Sentry 浏览器 SDK（`window.onerror` ＋ `unhandledrejection` ＋ ErrorBoundary ＋ 指纹分组 ＋ 面包屑）；React 19 的根选项 `onUncaughtError` / `onCaughtError` | §2.2、§3.2 |
| 原始异常的挂法 | ES2022 的 `Error.cause` | §2.4、§3.2 |
| 通知面 | Sonner（shadcn 现用）、react-hot-toast、Notistack 的共同形状：**队列 ＋ 有限时长 ＋ 可关闭 ＋ 四种语气 ＋ 可堆叠** | §4 |
| 测试侧 | Cypress 的 `uncaught:exception`、WebdriverIO 的 `uncaughtException` | §5.1 |

**判断规则**（以后有人提"用某某库吧"时的答案）：

> 替代品替代的是**通用能力**（Toast 的队列、错误边界的样板）且足够轻 ⇒ 值得引，前提是**不带来新的视觉语言、不多一份事实的副本**；
> 替代品替代的是**本仓的契约**（机器码、隔离、归档、指纹）⇒ 不引。

⇒ 按这条规则回看手写的四处：**机器码词表与文案表**（跨运行时共享的事实 ⇒ 本仓只能有一份 ⇒ 用库反而多一份副本）、**捕获与分类**（平台的 `window.onerror` 与 React 19 的根选项已经是信号源 ⇒ 零依赖）、**通知面**（几十行，换来与本仓视觉一致）、**测试侧**（Playwright 自带 `pageerror`）⇒ ⇒ 四处都不是"通用能力"，都是本仓的形状 ⇒ ⇒ **手写是对的** ✓。

**唯一可以"不手写"的**：错误边界的样板（`react-error-boundary`，~2KB）⇒ ⇒ React 19 的根选项给的是**捕获**，局部降级仍要边界组件 ⇒ ⇒ 倾向**仍手写**（一个 class 组件，十几行 ⇒ 我们的降级是"这一部分没能显示"⇒ 极简 ⇒ 引库会带来 reset 语义的差异 ✓）。
- 不把原始异常文本写进日志（基座 §5.2 的硬约束）。
- 不做跨运行的错误指纹与去重（需要原文或脱敏摘要，见 §2.3）。
- 不引入前端监控 SDK。
- 不改基座的通道、准入与限流语义。

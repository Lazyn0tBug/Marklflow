## 0. 决策摘要

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 要不要统一 | **要**，但统一发生在**应用层**，不是在测试里另立一套 | 三层各行其是：原生侧有机器码、应用侧**什么都没有**、测试侧只报派生症状。缺口在应用层 |
| 用不用新机制 | **不用**。基座已有 `log_event` 通道、`page_error` 事件与封闭的字段白名单 | 通道是通的、词汇是定好的，缺的只是应用往里报 |
| 捕获点 | 三处：**React 错误边界**（渲染期）、**`window.onerror`**、**`unhandledrejection`** | 渲染期错误现在会**白屏**：用户不知道、日志里没有。边界顺带把它降级成局部失败 |
| 出口 | **一个**报告函数 ⇒ 三个消费方：用户可见提示 / 原生日志 / 浏览器控制台 | 一处捕获，多处消费；不再有"某个出口知道、另一个不知道" |
| 原始异常文本 | **不进日志**（基座 §5.2 的硬约束）⇒ 只留在浏览器控制台 | 日志不含异常原文，避免间接泄露 |
| 桌面端因此的诊断力 | **只有"类别 + 诊断 id"** ⇒ 桌面端问题的原文拿不到 | 这是隐私约束换来的**取舍**，不是疏漏；要更强需要单独的脱敏设计（另议） |
| 类别词表 | 扩 `WebErrorCategory`（基座那个封闭枚举），新增应用类别 | 不新增载荷形状 ⇒ 基座"封闭枚举 + 白名单"的原则完整保住 |
| 测试侧 | e2e 读浏览器自身的 `pageerror` 事件（**与应用消费的是同一个事件源**） | 立刻可用，不依赖应用侧；应用侧接上后两者不冲突 |
| 落在哪 | 测试侧那一步可以现在做；应用侧属于**日志基座那条线**（生产接入与可监测性） | 横切面，不属于大纲，也不属于文档资产 |

## 1. 现场事实

### 1.1 三层现状

| 层 | 现在怎么做 | 缺什么 |
| --- | --- | --- |
| 原生侧失败 | **机器码**（见本地文档支持设计 §9 的清单）⇒ 前端按码分流、按码映射文案 | — |
| **应用侧未捕获错误** | **什么都没有**：没有错误边界、没有 `window.onerror`、没有 `unhandledrejection` ⇒ 一个 ReferenceError ⇒ **白屏**，用户不知道，日志里也没有 | 捕获、分类、通知 |
| 测试侧 | e2e 报的是**派生症状**（"等不到 textarea" 超时 60 秒）⇒ 真实错误（`ReferenceError`）被掩盖 | 指到根因 |

### 1.2 基座已经给了一半

[日志基座](log-base-plan-2026-11-03.md) §4–§5 已经定义：

- **通道**：`log_event` 命令（web → Rust）⇒ "只写日志，不铸任何授权"；
- **载荷是封闭白名单**（`deny_unknown_fields`）：`{event, call_id?, command?, result?, error_category?, bytes?}` ⇒ **未知字段或未知事件一律拒收**；
- **事件枚举**：`page_ready` / `call_started` / `call_finished` / **`page_error`**；
- **类别字段** `error_category`：**只传类别，不传原始异常 message**；
- **准入**：写日志有身份判定（正常路径仅主窗口）⇒ 页面不能自报身份获得允许；
- **限流**：每个身份对 20 条/秒、进程内 100 条/秒；请求 ≤ 4 KiB；
- **结果**：`accepted` / `dropped` / `rejected`（accepted **不表示已落盘**）。

⇒ **通道是通的、词汇是定好的。缺的只是应用往里报。** 探针已经在用这条通道（`tests/fixtures/architecture/pdf-probe-client.ts`），生产应用一次都没用过。

### 1.3 浏览器构建没有日志出口

`src/core/platform/web/` 下**没有日志端口** ⇒ 前端只有两处零散的 `console.error`（`ExportModal.tsx`、`storage.ts`）⇒ 于是浏览器构建里，除了控制台，什么都留不下 ⇒ e2e 也就只能读控制台。

### 1.4 应用已经有一个提示面

`App.tsx` 有 `loadError` / `actionError` / `storageWarnings` 三个状态 ⇒ 渲染成一条 `<aside role="alert">`。⇒ 用户可见的通知有地方放，但那是**存储恢复**的面 ⇒ 未捕获错误不该挤进那条（语义不同、样式不同、恢复按钮也不该出现）。

## 2. 语义模型

### 2.1 一处捕获，三个消费方

```
捕获（三处）   React 错误边界  │  window.onerror  │  unhandledrejection
   └─ 分类     category（封闭枚举）＋ 诊断 id
        ├─ 用户      可见提示：类别 ＋ 诊断 id ＋ 一句可行动的话
        ├─ 原生日志   page_error 事件（桌面端 ⇒ log_event ⇒ 基座）
        └─ 浏览器    console（原始文本留在这里；Web 构建与开发期可见）
```

⇒ 三个消费方看的是**同一次捕获** ⇒ 不会出现"用户看到了、日志里没有"或"日志里有、用户不知道"。

### 2.2 什么算"一个问题"

- **一次捕获 = 一个问题实例**：渲染期的一个错误边界触发、一次 `error`、一次 `rejection`。
- **去重键不是实例，是来源**：键 = (类别, 来源标识) ⇒ 来源标识是"哪个错误边界/哪个脚本" ⇒ ⇒ 一个渲染循环会产生**很多**实例，但只报一条 ⇒ ⇒ 若按实例去重，循环就会刷屏（违反 P-3）✓。
- **诊断 id**：短、稳定、**可复述**（如 `e-7f3a`）⇒ 用户能在报障时念出来；它是**本次运行内**的关联，不是跨运行的指纹（跨运行需要原文或脱敏摘要，而两者都被基座排除了 ⇒ 见 §2.3）。
- **限流两层**：应用侧先限（同一个问题只报一次、每秒至多 N 条），基座再限（20/100 每秒）⇒ 应用侧的限流是为了不浪费基座的额度。

### 2.3 原始文本的去处：只进控制台

基座 §5.2 明确：**`page_error` 只传错误类别，不传原始异常 message**；日志"不含文档正文、完整本地路径或任何授权凭据，包括查询串、**异常**与 DOM 报告的间接泄露"。

⇒ 于是原始异常文本**只留在浏览器控制台**。桌面端没有控制台（基座 §1 的动因之一）⇒ **桌面端出问题时，日志里只有"类别 + 诊断 id"** ⇒ 定位要靠复现。

⇒ 这是**取舍**，写在这里是为了别被当成疏漏：换来的是"日志不含异常原文"这条硬约束完整保住。要更强（桌面端日志里有可诊断的原文），需要**单独的脱敏策略**设计（异常文本里的路径/正文/凭据要怎么处理），那是另一个题目，本文不做。

## 3. 契约

### 3.1 报告的形态

应用侧提交给端口的形状（**端口内部的实现再决定怎么落到线上**）：

```ts
export interface ProblemReport {
  /** 封闭类别枚举：与基座的 WebErrorCategory 共用同一个词表 ✓。 */
  category:ProblemCategory;
  /** 诊断 id：短、稳定、可复述 ✓。 */
  diagnosticId:string;
  /** 原始文本：只进控制台，不进日志 ✓（基座 §5.2）。 */
  detail?:string;
}
```

⇒ 落到基座通道时**只发** `{event:'page_error', error_category:category}` ⇒ **`diagnosticId` 与 `detail` 都不进载荷** ⇒ 因为白名单里没有这两个字段 ⇒ ⇒ 于是诊断 id 要另找地方留（见 §8 的 N4）⇒ 或者**干脆不发**（基座日志只需要类别）⇒ ⇒ **本文的结论：通道里只发类别** ⇒ 诊断 id 属于**用户可见的那条提示**与**控制台**，不进日志 ✓。

### 3.2 捕获点怎么接线（React 19 的根选项与 window 事件会重叠）

React 19 的根可以带选项：`createRoot(container, {onUncaughtError, onCaughtError})` ⇒ ⇒ 渲染期的错误由**根选项**接住（分类 `render`）⇒ 局部降级仍需一个**错误边界**（根选项只报告，不降级）⇒ 其余用 `window.onerror` 与 `unhandledrejection`。

**重叠必须消掉**：一个逃出 React 树的错误会**同时**触发 React 的根选项与 `window.onerror` ⇒ ⇒ 报两次 ⇒ ⇒ 处理：React 的根选项报告后，把该错误对象记进一个 `WeakSet`（本次运行内）⇒ `window.onerror` / `unhandledrejection` 遇到已记过的就跳过 ⇒ ⇒ 一次问题只出一份报告 ✓（P-3）。

### 3.3 类别枚举

在基座的 `WebErrorCategory` 上扩展（**同一个词表、同一套封闭枚举** ⇒ 不新增载荷形状）：

| 类别 | 含义 | 来源 |
| --- | --- | --- |
| `no_tauri_internals` / `invoke_rejected` / `invalid_payload` / `rate_limited` / `timeout` / `unknown` | 通道与调用类问题（**已存在** ⇒ 探针在用） | 基座现有 |
| `render` | React 渲染期错误 | 新增 |
| `unhandled` | 未捕获的脚本错误（`window.onerror`） | 新增 |
| `rejection` | 未处理的 Promise 拒绝 | 新增 |
| `startup` | 应用初始化期的错误（工作台起不来） | 新增 |
| `storage` | 草稿与存储层的失败 | 新增 |
| `worker` | 后台 worker 的失败 | 新增 |

⇒ 类别是**枚举** ⇒ 前端与 Rust 两侧必须同步 ⇒ 改基座时两侧一起改（基座已有的"两处必须同步改"先例 ✓）。

### 3.4 三个出口

| 出口 | 做什么 | 不做什么 |
| --- | --- | --- |
| 用户可见提示 | 一条独立的提示（不挤进存储恢复那条）：类别 ＋ 诊断 id ＋ 一句可行动的话 | 不显示原始堆栈；不假装能自动恢复 |
| 原生日志 | 经 `log_event` 发 `page_error` + 类别 | 不发原文、不发诊断 id、不发堆栈 |
| 浏览器控制台 | 原始文本（`console.error`），带诊断 id | 不当作证据（控制台不是归档） |

⇒ 端口放在 `src/core/platform/` 下、**两个实现**（`tauri/` ⇒ `log_event`；`web/` ⇒ 控制台）⇒ 与既有的平台端口同构 ⇒ **应用层不直接碰 `console` 或 `log_event`** ⇒ 这条要进边界检查（`scripts/check-module-boundaries.ts`）。

### 3.5 隔离

- 报告**不铸任何授权** ⇒ 沿用基座"只写日志"的性质 ✓。
- 页面不能自报身份获得允许 ⇒ 沿用基座的准入 ✓。
- **报告通道自身失败不再报告自身**（基座 §4 的"失败不再调用 log_event 记录自身失败" ✓）。

## 4. UI 规格

- 渲染期错误由**错误边界局部降级**：出错的那块显示"这一部分没能显示"，**其余部分照常** ⇒ 不会因为一个坏组件而白屏。
- 非渲染期错误（`window.onerror` / `unhandledrejection`）：一条独立的提示 ⇒ 位置沿用现有的 `<aside role="alert">` 那一带，但**单独一条**，不与存储恢复提示合并（语义不同、可操作性不同）。
- 提示内容：**类别 ＋ 诊断 id ＋ 一句可行动的话**（如"重新加载窗口"或"该文档的预览未能生成"）⇒ 不显示原始堆栈。
- 提示**可关闭**，关闭后不重复出现（同一个诊断 id 只提示一次）⇒ 不打断正在做的事。

## 5. 测试侧

- e2e 读浏览器自身的 `pageerror` 事件 ⇒ **与应用消费的是同一个事件源** ⇒ 应用侧还没接上时，测试侧已经能用 ⇒ 不是两套机制，是同一个信号的两个消费者。
- 失败信息里带**原始错误** ⇒ 测试失败直接指向根因，不再是"等不到某个元素"。
- **不因为页面有错误就判失败**：有若干用例**故意**触发错误（来源拒绝、诊断、坏图）⇒ 页面错误只**报告**，是否失败由用例自己断言 ⇒ ⇒ 机制放在共享位置，不放在每个用例里。

## 6. 验收

| 编号 | 断言 |
| --- | --- |
| P-1 | 应用启动失败时，页面不是白屏：要么错误边界降级后的提示，要么一条明确的启动失败提示 |
| P-2 | 一个未捕获错误 ⇒ 原生日志里有一条 `page_error`，**带类别、不带原文、不带堆栈** |
| P-3 | 同一个问题重复发生（渲染循环）⇒ 日志里只有一条，应用侧不刷屏 |
| P-4 | 报告通道自身失败（载荷被拒、超频）⇒ 应用不因此崩，也不递归报告 |
| P-5 | 用户可见的提示给出类别与诊断 id，**不含原始堆栈** |
| P-6 | e2e 在页面抛错时，失败信息里能看到原始错误 |
| P-7 | 故意触发错误的用例（如来源拒绝）仍按自己的断言判定，不被"页面有错误"误伤 |
| P-8 | Web 构建下同样的问题落在控制台，且不依赖原生侧 |

---

## 7. 不做

- 不做崩溃上报服务、不做远程收集、不做看板与告警（基座 §2 明确不在范围）。
- 不把原始异常文本写进日志（基座 §5.2 的硬约束）。
- 不做跨运行的错误指纹与去重（需要原文或脱敏摘要，见 §2.3）。
- 不引入前端监控 SDK。
- 不改基座的通道、准入与限流语义。

## 8. 迁移步骤

每步一个提交、行为可验证；后一步依赖前一步的出口。

| 步骤 | 内容 | 退出依据 |
| --- | --- | --- |
| **N1 测试侧通知** | e2e 在页面抛错时把原始错误带进失败信息。放在共享位置（配置或共享 fixture），不逐个用例加 | P-6；故意触发错误的用例不受影响（P-7）；全套 e2e 仍全绿 |
| **N2 日志端口** | 应用层有一个统一的"报告"出口，两个实现：`tauri/` ⇒ `log_event`；`web/` ⇒ 控制台。应用层不直接碰 `console` 或 `log_event` | 端口有单测（两个实现的行为差异有断言）；**边界检查要真的拦住"应用层直连 console / log_event"**（现在 `check-module-boundaries.ts` 与 `check-source-policy.ts` 都不管 `console` ⇒ 规则若不落进检查就会烂掉） |
| **N3 捕获与分类** | 错误边界 + `window.onerror` + `unhandledrejection` ⇒ 分类 ⇒ 经端口报告；去重与本地限流 | P-1、P-2、P-3、P-4 |
| **N4 用户可见的提示** | 独立的提示面：类别 ＋ 诊断 id ＋ 一句可行动的话；渲染期错误由边界局部降级 | P-5、P-1 |
| **N5 与基座对齐** | 把新增类别写进基座的封闭枚举与 §5.2 的词汇表；Rust 与前端两侧同步；校验器放行 | 基座 §8 的 L2 退出条件重跑；载荷形状仍满足 `deny_unknown_fields`；归档形态核对 |

**顺序说明**：N1 独立且立刻有用 ⇒ 可以先做；N2→N3→N4 是一条链 ⇒ 属于日志基座那条线（生产接入与可监测性）⇒ 建议排在那里，不混进大纲或文档资产。

**N5 的前置**：类别枚举跨 Rust 与前端两侧 ⇒ 两侧必须一起改 ⇒ 基座已有"两处必须同步改"的先例 ⇒ 不要单侧先改。

### 审查记录

2026-11-07 初稿后的自查（按分析与验证规范 §2 的顺序：先看设计与契约，再核对代码）：

- **契约与代码核对**：通道的载荷结构、封闭枚举、身份准入、限流与字节上限，逐条对照 `src-tauri/src/logging.rs` 的 `WebEventPayload` / `WebEventKind` / `WebErrorCategory` 与 §4 的准入限流 ⇒ 一致 ✓。
- **发现一处缺口**：探针在用的 `WebErrorCategory` 是**通道类**类别（`invoke_rejected` / `rate_limited` …）⇒ 应用的**问题类别**无处安放 ⇒ 若新开字段就破坏 `deny_unknown_fields` 的白名单原则 ⇒ 故定为**扩同一个枚举**（§3.2）⇒ 这使 N5 成为必需的一步，不是可选的润色 ✓。
- **发现一处取舍需要明说**：基座禁止日志带异常原文，而桌面端没有控制台 ⇒ 桌面端的诊断力只剩"类别 + 诊断 id" ⇒ §2.3 已把它写成取舍而非疏漏 ✓。
- **三处需要落进实现的细节**（审查时才发现）：① 去重键必须是**来源**而不是实例，否则渲染循环会刷屏；② React 19 的根选项与 `window.onerror` 对同一个逃出 React 树的错误**会各报一次**，要用"已报告"集合消掉；③ "应用层不直连 console"这条规则**现在没有任何检查拦着** ⇒ N2 要把它落进边界检查，否则规则会烂掉。
- **未验证**：N1–N5 都未实施 ⇒ 本文不构成任何阶段的通过证据 ✓。

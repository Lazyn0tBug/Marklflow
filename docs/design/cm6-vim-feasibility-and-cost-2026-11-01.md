# CodeMirror 6 + Vim 编辑器迁移可行性与代价方案

日期：2026-11-01。状态：独立讨论稿，尚未决定迁移。代码核对基线：`architecture-refactor / 00a8ce2fb778c192a780928f259063c71895c667`。本文只讨论可行性、设计取向、成本和未决问题，不制定实施步骤、提交单位、阶段依赖或版本排期，不授权安装依赖或修改代码。

## 1. 判断与适用条件

如果产品确定需要实用的 Vim 模式，CodeMirror 6（CM6）加成熟 Vim 扩展是值得验证的选择。对当前项目，这是一次中等偏大的编辑器子系统迁移，而不是加几个快捷键。收益在于获得可扩展的编辑基础设施，代价主要是多 Tab 历史、编辑事务及同步滚动的重新适配和验证。

CM6 是选用 `@replit/codemirror-vim` 的前提，不是所有 vi 支持的必然前提。少量 vi 风格键位仍可在 textarea 上实现，但自行补齐模式、操作符、文本对象、计数和撤销组合容易形成长期维护负担。本文倾向成熟扩展，不承诺完整 Vim/Neovim 等价。

新增依赖属于可由 Bun 统一安装、打包交付的前端依赖，不要求用户另装 Vim、Node 或系统库，符合发布后可用目标。具体版本、传递依赖和严格 TypeScript 兼容性尚未验证，本文不锁定版本。

## 3. 候选技术组合与边界

候选为 CM6 的 state/view、命令与 Markdown 语言能力，加 `@replit/codemirror-vim`。采用哪些包及是否使用 React 包装库尚未决定；倾向薄 React 生命周期适配，避免每次渲染重建 EditorView。按需组合扩展，不能把示例的全套功能默认带入产品。

CM6 的语法解析只服务编辑辅助，不替换现有 Markdown→冻结 HTML 的权威映射；两者方言差异应在编辑提示与实际输出之间明确，不让编辑高亮结果成为导出源。HTML 唯一正文映射与输出源、源保存例外、MathJax/Paged.js 版本和 Web/Tauri 交付语义均不因此改变。

编辑区倾向交给 CM6 的语法高亮和装饰机制；Shiki 用于预览/输出代码块。CSS Custom Highlight API 仅在确有独立需求时保留，不能强加给 CM6 编辑 DOM。当前生产编辑区是否已接入相关高亮不作推定，此处是候选职责划分。

Web 与 Tauri 使用同一编辑组件，不各建一套。平台差别通过现有应用操作和文件能力适配，不让 Vim 扩展直接接触原生路径或 IPC。

## 4. 最主要的架构代价

### 内容、事务与撤销

倾向由每个 Tab 的 CM6 状态管理文本、选区和文本编辑历史，会话继续管理 DocumentRecord 修订、草稿状态、激活文档及预览引用。CM6 的文本对象是编辑工作副本，业务接受的 DocumentRecord 仍是渲染和导出输入；两者必须有明确同步边界，不能成为两个独立可写来源。

当前会话历史是完整文档快照，因此不能直接宣布 CM6 history 全面替代。主题、渲染配置、元信息是否参与撤销，以及它们与文本撤销的顺序，属于必须先确定的产品语义。可选择保留独立非文本历史或统一应用命令语义，但不能让两个 undo 同时回放同一文本变更；本文不预设新增通用命令平台。

输入、粘贴、Vim 操作符、工具栏格式化与外部整文替换都要区分来源。用户操作应合理分组；会话回显不能再次进入文本历史或触发重复 revision。一次撤销是新的业务修订，不能把业务 revision 倒退到历史值；迟到的保存结果仍不得清除新修订状态。

### 多 Tab 状态与资源

每个 Tab 需要独立保留文本历史、选区和阅读位置。可以保留各 Tab 的 EditorState 并复用一个可见 EditorView，但 Vim 扩展是否还有绑定在视图或全局的状态需要核实，不能宣称 EditorState 已包含全部 Vim 状态。

模式、搜索、寄存器、宏、标记的共享范围必须明确；不应未经验证把所有状态持久化。关闭 Tab 应释放编辑状态和监听，不能因保留历史无限增长。预览产物缓存仍属于现有缓存，不与 EditorState 合并。重启恢复文本不等于恢复撤销历史，首版是否需要持久历史尚未决定。

### 布局与三视图同步

继续以源码字符位置/逻辑行及视口内偏移作为同步基础。CM6 的行块、软换行和可见区域测量需要适配现有大纲定位、编辑器中心章节高亮、HTML 反向定位与 Tab 恢复。不能假设所有不可见行都有 DOM 节点，也不能仅按滚动比例恢复。

分栏、最大宽度、隐藏恢复、字体就绪只改变布局，不改变 Markdown、渲染配置版本、预览缓存键或 A4 分页。Vim 的逻辑行移动与视觉行移动应区分；光标自动进入视口时，如何驱动 HTML 同步及防回环需要明确。折叠等额外功能不自动纳入本次范围。

## 5. Vim 产品语义

普通编辑为默认，Vim 模式通过现有设置弹窗启用，展示当前模式。候选范围是 Normal/Insert/Visual、常用移动、操作符、文本对象、计数、搜索和撤销；寄存器、宏、重复命令等支持度以扩展核验为准，不承诺本地 vimrc、插件、终端或 shell 命令执行。

`:w` 必须遵循源保存语义，不能接成导出，也不能把只完成草稿持久化说成原文件已写回。Web 和未关联文档需要准确反馈或引导保存目标；`:q` 调用现有关闭/未保存保护，不能直接销毁 Tab；`:wq` 只能在所要求的保存实际完成后关闭。未完成相应应用端口时，应明确命令不可用，不模拟成功。

Escape、搜索、浏览器快捷键与桌面菜单可能冲突，处理应局限编辑器焦点范围；对话框开启时不拦截其键盘操作。中文 IME 组合期间不得将输入按普通模式命令解释；真实输入法、辅助技术和键盘导航需实测，不能用合成事件替代完整结论。

## 6. 成本、收益与机会成本

| 成本项                   | 相对程度   | 说明                                                        |
| ------------------------ | ---------- | ----------------------------------------------------------- |
| 编辑组件与工具栏         | 中         | 编辑 DOM/事务改变，Markdown 内容处理仍复用                  |
| 撤销与多 Tab             | 高         | 当前完整 DocumentRecord 历史与 CM6 文本历史存在语义交界     |
| 同步滚动与位置恢复       | 高         | 已完成 textarea 相关测量需替换并回归三视图                  |
| UI 外观、行号、软换行    | 中         | 功能可由成熟扩展承担，但需保持开发工具风格和现有偏好        |
| 包体、内存与启动         | 未测       | 新增代码/状态有成本，替代旧测量可能获益，净效果不能提前保证 |
| 测试与验收维护           | 中至高     | textarea 定位器和事件假设需改；业务断言继续保留             |
| 解析、Worker、缓存、导出 | 低直接改动 | 原则不重写，但要验证编辑桥接不重复调度、不污染快照          |

长期收益可能包括减少自行维护基础编辑能力、统一扩展机制和提供更完整的 Vim 体验。短期收益不足以抵消全部迁移工作；若只要几个快捷键，投入可能不合理。迁移会占用当前文件绑定、桌面交付及验收收口的人力，应作为独立产品决策，而不是顺带塞进导出或 Tauri 迁移。

当前没有可靠的工时、代码行数、包体或性能估计。上述相对程度是基于代码边界的分析，不是测试结果；未经样例集成与测量，不给出压缩百分比、毫秒承诺或完成日期。

## 7. 可行性判断仍缺少的事实

讨论需要回答：扩展在严格 TS/Bun/React19 下是否可用；文本历史与完整文档撤销如何协调；Vim 状态跨 Tab 的实际归属；中文 IME 与 WebView 的行为；普通模式是否保持现有交互；三视图同步能否继续按逻辑位置工作；大文档、很多打开 Tab 和长行的真实开销；新增依赖许可证与锁定范围。

这些是可行性判据，不是实施阶段：不能满足历史、源文精确性、逻辑位置恢复、输入或 HTML 输出边界时，不应仅因 Vim 按键可运行就接受迁移。可接受的判断包括采用、调整支持范围或延期；不要求当前立刻替换 textarea。

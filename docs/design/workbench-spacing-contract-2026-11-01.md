# 工作台间距契约：视图留白 / 内容边距 / 行号列

日期：2026-11-01；状态：**已实施**（同日复核：取值改用现代单位制，类名更正，§3 的边缘构成更正）；基线 architecture-refactor / d4257ee。
关联：[HTML 兼容性设计基线](html-compatibility-baseline.md) §16.4（容器、单位与布局坐标）、[导出输出层方案](export-outputs-formula-and-print-plan-2026-10-30.md)。
本文件记录**设计要求**；实施结果与验证记录见 §10。

## 0. 决策摘要

| 项             | 决定                                                                                                                                                | 理由                                                                                                 |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 视图留白 v     | **0.75rem / 1.125rem / 1.5rem 三档**（默认根字号下即 12 / 18 / 24px），按**面板自身宽度**分档；是**最小**间隙，实际间隙 = max(v, 居中余量/2)，见 §3 | 两个面板宽度可调，各自的留白应跟自己的可用宽度匹配；阶梯而非连续缩放，拖拽窗口时不抖动、跨屏档位一致 |
| 代码边距 m     | **1ch**（字体相对、固定）                                                                                                                           | 编辑器正文内缩；字符相对 ⇒ 字号放大随之放大，无需档位表，且永不成为视觉主角                          |
| 行号列         | 宽度 = **f(行数位数)**，独立于 v 与 m，不随窗口变                                                                                                   | 功能件不是空白边距；位数驱动 ⇒ 三位数的文件不再留一条 3rem 空档                                      |
| 文档内容边距   | **不变**：`--mf-content-padding: clamp(1rem,4cqi,3.5rem)`，随纸宽                                                                                   | 属于纸的属性，随纸走；导出继承同一份 CSS                                                             |
| 导出物的内边距 | 不在本次范围                                                                                                                                        | 本次讨论的是工作台外壳层；导出由文档层与页边距决定                                                   |

### 单位约定

| 量             | 单位      | 理由                                                                                                                                                          |
| -------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 视图留白 v     | rem       | 跟随根字号：用户放大系统字号时留白同步放大，不会在大字号下显得拥挤                                                                                            |
| 代码边距 m     | ch        | 跟随代码字体：正文字号变了，内缩按字符数保持不变                                                                                                              |
| 文档内容边距   | rem + cqi | 上下限用 rem（与根字号一致），中间值用 cqi（随纸宽）                                                                                                          |
| 面板分档阈值   | rem       | 与留白同一坐标：根字号变化时分档与留白同步，不会出现「留白按 rem、阈值按 px」的错位；取值在 CSS 的 `--mf-pane-min` / `--mf-split-handle`，JS 解析后注入纯模块 |
| 行号列宽度     | ch + rem  | 位数部分跟代码字体宽度，余量（0.5rem）跟根字号                                                                                                                |
| 界面层固定尺寸 | rem       | 字号、控件高度、提示宽度跟根字号：大字号用户拿到成比例的界面，而不是零散的固定值                                                                              |

px 只在**引用第三方实测值**时出现（如 VS Code 的 `editor.padding`），不作为本契约的取值单位；页面几何（纸张、页边距）仍用绝对单位，那是纸的物理属性。

三类 px 是例外，各有各的理由：**发丝线**（1px 边框）是物理细线，rem 会让它随字号变粗；**用户可设的内容宽度**（800 / 1024 / 1280 / 1440px）是界面上写给用户看的数；**实测值**（编辑器行高、行号列位置、光学偏移）由测量得出，本就是 px。

## 1. 现场观察与问题

2026-11-01 在多台显示器上目测工作台，发现两个视图的留白**行为不一致**：

- 编辑器两侧的空白来自**内容列在面板内居中**产生的余量 ⇒ 窗口变窄时两侧**一起收窄**、保持对称；
- HTML 视图左侧的空白来自一段**写死的 3rem 视图留白** ⇒ 窗口变窄时**不收窄**（肉眼几乎看不出），右侧则**几乎为 0**（只剩滚动条）。

⇒ 同一件事（面板边缘到内容的间隙）由三套机制产生：居中余量、固定留白、无 ⇒ 因此行为对不上。左右不等本身不是问题（行号列与纸的边距本就不等宽），**问题在于"同一种空白"没有同一种规则**。

## 2. 分层职责

| 层           | 归属         | 规则                                                                                                |
| ------------ | ------------ | --------------------------------------------------------------------------------------------------- |
| 视图留白 v   | 应用外壳     | 面板边缘到内容列之间的**最小**间隙；实际间隙 = max(v, 居中余量/2)，两侧对称，因为内容列在面板内居中 |
| 内容边距 m   | 编辑器       | 代码正文在文本框内的内缩；1ch                                                                       |
| 行号列       | 编辑器功能件 | 与空白无关，独立计算                                                                                |
| 文档内容边距 | 文档层       | 正文在纸上的内缩；随纸宽缩放                                                                        |

## 3. 每条边缘的构成（目标态）

```
编辑器  [间隙][行号列 f(位数)][m] 正文 [m][滚动条][间隙]
HTML    [间隙][纸缘][文档边距] 正文 [文档边距][纸缘][滚动条][间隙]
```

「间隙」= **max(v, 居中余量/2)**，居中余量 = 面板宽 − 内容列宽（内容列封顶 1024）。

- 内容列在面板内**居中** ⇒ 左右对称、随窗口一起收窄；
- v 加在居中盒子内，作为**最小间隙**：给居中元素加对称内边距时，居中余量恰好减半，两边抵消 ⇒ v 只在内容列撑满面板时才显形（面板宽 ≤ 内容列宽 + 2v）。
- 因此「v + 居中余量/2」这种写法**几何上不成立**（v 与余量重复计数，两侧之和会超过面板宽）⇒ 本节用 max() 形式取代初稿的画法。
- 代价：面板比内容列宽时，可见间隙由居中余量主导，**档位变化看不出来**。这是取舍——一致性（两个视图同一套规则）优先于档位可见性。

⇒ 四条边缘的**空白部分**都由「间隙 + 内容边距」产生 ⇒ 同一套规则 ⇒ **行为一致**（同步收窄、同步对称）；左右不等只来自功能件（行号列）与文档层（纸的边距），这两者本就不该同宽。

⇒ 内容宽度**不要求**两视图相等：两个面板宽度可调，只有完全相等时才谈得上等宽。

## 4. v 的档位与分界

- 档位：**0.75rem / 1.125rem / 1.5rem**
- 分界按**面板自身宽度**（不是窗口宽度）：

| 面板宽度            | v        |
| ------------------- | -------- |
| < 43.75rem          | 0.75rem  |
| 43.75rem – 68.75rem | 1.125rem |
| ≥ 68.75rem          | 1.5rem   |

- 实现：面板本身成为尺寸容器（`container-type: inline-size; container-name: mf-pane`），带留白的元素位于其内，用 `@container` 分档。
- 两个面板可以处于不同档（分栏时面板窄 ⇒ 小档；单栏时 ⇒ 大档）⇒ 这是设计意图，不是缺陷。
- 不用连续缩放的理由：阶梯在拖拽时不会逐帧抖动，跨屏时档位一致。
- 43.75rem / 68.75rem（即默认根字号下的 700px / 1100px）是**起点值**：分界属于观感判断，实施后按目测微调即可（测试按同一规则计算，不锁死分界数值）。阈值用 rem 是为了与留白同一坐标：根字号变化时两者同步。
- 档位只在**内容列撑满面板**时可见（面板宽 ≤ 1024 + 2v）；面板更宽时可见间隙由居中余量主导，档位不可见（§3）。

## 5. m = 1ch

- 编辑器文本框的内缩 = 1ch（"0" 的宽度，含垂直方向）；行号列的水平内缩与之对齐。
- 业界依据：代码编辑器的正文内缩普遍在「半个到一个字符宽」量级 —— VS Code 的 `editor.padding` 只给上下各 0.25rem（第三方实测值，此处保留 px 标注），水平完全靠装订线让位；Monaco / CodeMirror 同理。字体相对 ⇒ 放大字号时随之放大，无需额外档位。
- 连带影响：编辑器几何缓存键已包含 padding（`src/components/workspace/sourceScroll.ts` 的 `editorGeometry`），内缩变化后自动重算；**行号列的上下内边距须跟随文本框**（顶部已由 `geometry.paddingTop` 同步，底部需补齐）。
- **风险**：内缩由 `p-3`（0.75rem）变为 1ch 会改变软换行的折行位置 ⇒ 滚动同步锚点随之变化 ⇒ 实施后必须目测长段落与长代码块的同步是否仍对齐（§9 步骤 7）。

## 6. 行号列

- 宽度 = 位数驱动的连续式：`calc(Nch + 0.5rem)`，N = 行数位数。行号列用 0.75rem 等宽字体（1ch ≈ 0.45rem）：2 位约 1.4rem、3 位约 1.85rem、4 位约 2.3rem ⇒ 明显窄于原来的 3rem。
- 不随窗口变；随字号微变（ch 相对）⇒ 满足「独立计算、不能固定死」。
- 上下内边距跟随文本框的 paddingTop。

## 7. 与导出的边界

- 本次改动只涉及工作台外壳层 ⇒ **导出 HTML / PDF / DOCX 的内边距不受影响**：导出 HTML 的页面留白来自导出规则，PDF/DOCX 来自页边距，文档层的内容边距（cqi）保持不变 ⇒ 导出仍是「预览 = 导出」的那一份 CSS。
- v 按面板宽度分档，而导出的宽度由打开它的窗口决定 ⇒ 二者本就不同源，这是有意的边界。

## 8. 测试契约：测量后计算，不锁死数值

断言应为「测出来的量」与「按规则算出来的量」相等，而不是与某个字面量相等：

| 断言         | 测量               | 计算                                                                                             |
| ------------ | ------------------ | ------------------------------------------------------------------------------------------------ |
| 视图留白     | 面板宽度、面板内缩 | 按 §4 的分界算出档位，再断言内缩等于该档位                                                       |
| 代码边距     | 字体的 "0" 宽度    | 断言文本框内缩等于 1ch                                                                           |
| 行号列       | 行数位数           | 断言列宽等于按位数算出的宽度                                                                     |
| 文档内容边距 | 纸宽               | 断言仍在 (0, 3.5rem] 区间且随纸宽变化                                                            |
| 单位制       | 根字号             | 改根字号后重算，断言间距随之缩放（写死 px 不会缩放）⇒ px 与 rem 在默认字号下等值，只有这条能分辨 |

工作方式：**目测在前，测试在后** —— 视觉问题先目测定方向，测试只保证最终正确性。

1. `src/index.css`：移除 `--spacing-gutter`；新增 `.mf-view`（v 的三档 + 容器查询）与 `.mf-source-inset`（1ch）。

4. `src/components/editor/Editor.tsx`：文本框内缩 1ch；行号列按位数计算宽度；上下内边距跟随文本框。
5. `tests/e2e/workbench-padding.spec.ts`：按 §8 重写为测量 + 计算。
6. `docs/design/html-compatibility-baseline.md` §16.4：摘要指向本文件（**已完成**）。
7. 门禁：`typecheck` / `lint` / `unit` / `e2e`；并**目测**软换行与滚动同步是否仍对齐（编辑器内缩变了）。

| 容器         | `ResizablePanes.tsx` 的两个面板加 `mf-pane`（`container-type: inline-size`）                                         |
| 视图留白落点 | `ReadingPreview` / `A4PagePreview` 的滚动容器改挂 `mf-view`；`Editor` 的居中容器挂 `mf-view`                         |
| m            | 文本框 `p-3` → `mf-source-inset`（`padding: 1ch`）                                                                   |
| 行号列       | `w-12` → `calc(Nch + 0.5rem)`，N = 行数位数；加 `data-line-numbers` 作为测试钩子                                     |
| 行号列内边距 | 顶部沿用 `geometry.paddingTop`，底部补 `paddingBottom`（否则行号列的滚动高度比文本框多几个 px）                      |
| 文档内容边距 | `clamp(1rem,4cqi,3.5rem)`；窄屏 `1rem`                                                                               |
| 旧 token     | `--spacing-gutter` 删除                                                                                              |

实测（1440 / 1920 窗口，两栏，面板 588 / 828px）：视图留白 12px / 18px（四边同值）；代码内缩 8.43px（1ch）；行号列 29.67px（3 位数）；文档边距 22.56px / 31.68px。

截图核对（2293×420，窗口更宽、面板 1141px、内容列 1024px）：两个视图的可见间隙都是 57–61px，来源是居中余量而非 v；行号列 30px、代码内缩 8px、纸面文字到纸边 38px（`4cqi`）⇒ 与 §3 的规则一致。

验证：`bun run typecheck` / `bun run lint` / `bun run test:unit` / `bun run test:e2e`。**e2e 必须先 `bun run build`**：Playwright 的 webServer 是 `vite preview`，跑的是 `dist/` 构建产物，不重建就会测到旧代码。

已知偏差：`workbench-tabs` 的「changed math configuration」在改动前的基线上同样失败 ⇒ 既有失败，非本次引入。

附带修复（规格竞态，非应用缺陷）：`source-import.spec.ts` 的「新建文档」步骤原本用 `await ready(page)` 当屏障，但预览的 ready 状态属于**旧**文档，与「新文档已激活」没有因果关系 ⇒ 该规格此前靠时序侥幸通过（填入的内容恰好落在新文档上）。本次改动让主线程在那一刻空了一点，暴露出该竞态 ⇒ 改为等待新文档的标签 `aria-selected="true"`（标签出现与 `currentDocId` 切换是同一次提交，是可靠屏障）。应用侧未改：`addDocument` 故意先落盘再打开，写失败就不开文档。

## 11. 明确不做

- 不把文档层的内容边距改成 1ch（那是纸的属性）。
- 不给导出物引入随窗口变化的留白。
- 不让行号列参与空白边距的计算。
- 不为「两栏文字等宽」做补偿（面板宽度可调，等宽不是目标）。

## 0. 决策摘要

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 文件通道 | 只有 `files.rs` 的受守卫命令，**不引入 JS 插件通道** | 插件命令的授权靠能力清单，而本项目的隔离层是 Rust 来源守卫；加第二道闸会让隔离结论与已验收证据分叉 |
| 打开的文件是否可写 | **可写**。用户选中文件即表达编辑意图；写能力只在用户显式触发保存时使用 | "读写角色分离"改为约束**不同的文件**（只读选择的文件不会被写），而不是同一文件的两种操作 |
| 文件引用 | **原生侧维护的"规范名 → 随机 token"映射**，会话内有效；不做路径摘要 | 路径熵低，摘要可被字典枚举还原；字符串规范化在大小写不敏感文件系统上会误折叠两个不同文件 |
| 引用的用途 | **归属与聚焦**：认出"这个文件是不是已经开着"，并决定它对应哪份内容；同步永远按原生侧保存的实际路径执行 | 前端 token 不参与寻址，避免"用标识推路径"这条错误路径 |
| 内容归属 | **原生端按文件引用归属**，不按内容摘要 | 一个文件恒对应同一份内容；文件内容变了也不改归属，只是变成"磁盘已变化"（§5.2） |
| 文件访问 | **访问由操作系统授予，原生侧只遵从** ✓ ⇒ ⇒ 应用层没有"权限""角色"这些概念 ✓ ⇒ ⇒ 应用层只说"写到这个文件"，成不成由原生侧回答 ✓ | 授权不是应用层的事：用户在系统对话框里选中文件的那一刻，访问就已经给了 |
| 绑定的存放 | **会话内状态**，不进 `DocumentRecord.meta`，不持久化 | 文档记录会作为载荷外传，本机路径不该跟着走 |
| 未同步的判定 | `lastSyncedRevision`：打开时按"草稿内容与文件当前内容是否相同"定（相同 = `document.revision`，不同 = null），同步成功后置为 `document.revision`；未同步 = `document.revision !== lastSyncedRevision` | 与既有 `DocumentSession.savedRevision`/`dirty` 同形，不新造第二套"脏"语义 |
| 本地资源 | **不在本文**，见《本地资源支持设计》 | 相对图片的解析、目录授权、预算与资产快照是另一件事；混在这里会让文档的重心偏离"打开与保存本地文件" |
| 文档与磁盘的关系 | **一个上下文，两个面**（file 文件 / sync 同步）+ **具名转移** | M4/M5/M6 是三个功能依次叠上去，于是绑定成了字段袋、规则逐条追加。改成按面分组后，一次转移 = 一组字段的变化，可审、可测；**resources 面等 M6 实施时再加**——应用层不留用不上的概念（《概念裁剪》§1 ✓） |
| 文档存在哪里 | **草稿（IndexedDB）是唯一的存放处，自动持久化，永远只有一份**。本地文件是这份草稿的一个**同步目标** | 本地文件不是"另一种存储"，而是同一份草稿的镜像。于是"保存"在两端是同一个动作，桌面端只是多一步同步 |
| 界面上的状态 | **两个维度** ✓：草稿维度（已更新 / 已保存）与同步维度（无目标 / 已同步 / 未同步 / 同步失败）✓ ⇒ ⇒ 两行措辞各说各的 ✓ | 本地文件支持是 Web 端草稿的延伸 ✓ ⇒ ⇒ 草稿在两端都是唯一的存放处 ✓ ⇒ ⇒ 它的状态可以、也应该表达 ✓ ⇒ ⇒ 只是不能与文件的同步状态混着说 ✓ ⇒ ⇒ 界面唯一要报的**失败**是**保存文件错误**（同步失败）✓ |
| 另存为 | 写新文件 + **新文档**，与旧文档无关 | 旧文档继续同步它自己的文件；新文档从一开始就是"已同步" |
| 同步 | **只有同步**，两个方向（草稿→文件 正向 / 文件→草稿 反向），**不做行级冲突解决** | 冲突消解是三个选择：**覆盖**（正向，草稿胜出）、**放弃**（反向，文件胜出）、**取消**（两边都不动）。覆盖按 G4 使用一次性确认并由 Rust 提交前复核 |
| 磁盘内容的摘要 | **只存原生侧**（它拥有路径与字节）。应用侧连摘要值都拿不到，只问一句"还是上次同步的那一版吗" | 两份摘要必须同步，同步失败就变成误判；而问一句是非，比拿一个值再比较更不容易出错 |
| 跨运行时原语 | **每个运行时一份实现，一个事实一处存放**：应用侧 `src/core/platform/crypto.ts`；原生侧提升为共享 hash 模块 | 摘要现在有两份实现（TS 的 `sha256Hex`、Rust 里私有的 `file_sha256`），再加一份就是第三份 |

M4（打开与拖放接会话）与 M5（原文件保存）的**产品语义、状态模型、访问模型、UI 规格、验收条目**。不改写既有契约，只在其上补足实现前必须定下的设计。

本地资源（M6）不在本文，见《本地资源支持设计》。本文只保留与它共享的一处：**隔离边界里的目录授权条款**（§10）。上下文此刻只有 file 与 sync 两个面（§4.1、§4.3），`resources` 面与 `refresh-assets` 转移等 M6 实施时再进上下文；状态区的待处理资源计数同属那边。

### 1.3 不变量

1. 应用层不持有路径。路径只在原生侧；前端只拿不透明 key、文件引用 token 与展示用字符串。
2. 绑定是**会话内状态**，不是文档数据。不进 `DocumentRecord.meta`，不落盘。
3. 草稿自动持久化不覆盖同步目标；同步到文件只能是显式动作。
4. 不新增隔离层。文件能力仍只经 `files.rs` 的受守卫命令。
5. 不引入第二个文件通道（JS 插件、Node fs、原生扩展）。
6. 取消不是失败；失败不改上下文、不清未同步提示。
7. Web 和 Tauri 共用打开、导入与保存的应用流程。普通 Web 文件选择载入工作区副本，保存只落草稿。Tauri 可附加原文件绑定并由 Rust 写回。
8. 文档正文里的引用串**不因本地解析而被改写**。同步到文件的是源快照，不是渲染结果。

## 2. 语义模型

### 2.1 四个用户动作

| 动作 | 作用对象 | 与磁盘的关系 | 是否改变工作区 |
| --- | --- | --- | --- |
| **打开** | 本地磁盘上的 `.md` / `.markdown` / `.txt` / 可编辑 `.html` | 经共用导入流程载入为草稿。Tauri 原生入口可在成功后将该文件设为**同步目标**，Web 普通文件选择只载入副本 | 新增文档或聚焦已有文档 |
| **保存** | 当前文档 | **落草稿**（所有文档都一样）；有同步目标时再**同步一步** | 否 |
| **另存为** | 当前文档 | 写出到新路径，并**新建一个文档**绑定它；旧文档不受影响 | 新增文档 |
| **导入** | 以副本载入的外部载荷（含自包含 HTML） | **不建立**同步目标 | 新增文档 |
| **导出** | 面向受众格式的产物（HTML / DOCX / PDF / MD / ZIP） | 写产物文件，不写源 | 否 |

关键区分：**草稿是唯一的存放处**，自动持久化；文件只是同步目标。没有同步目标的文档（导入的、Web 端的草稿）保存时只有落草稿一步。

**另存为产生的是另一个文档**：新文件绑定新文档，新文档一开始就是"已同步"；旧文档继续同步它自己的文件（或没有同步目标），两边互不影响。HTML 输入限于含有效源载荷的自包含 HTML。

### 2.2 草稿持久化与原文件同步

草稿只有一份。工作台分别记录本次草稿持久化与原文件写回结果（§6.1）。状态区**分两行**分别表达两个维度：**草稿维度**（已更新 / 已保存）与**同步维度**（下表四种）✓ ⇒ ⇒ 两行措辞各说各的 ✓ ⇒ ⇒ 一行说草稿、一行说文件 ✓。

**草稿维度为什么还在** ✓：**本地文件支持是 Web 端 IndexedDB 草稿的延伸** ✓ ⇒ ⇒ 草稿在两端都是唯一的存放处 ✓ ⇒ ⇒ 它的状态可以、也应该表达 ✓ ⇒ ⇒ 只是不能与文件的同步状态混着说 ✓ ⇒ ⇒ 因此写"草稿已更新 / 草稿已保存" ✓ ⇒ ⇒ 不写没有主语的"已更新 / 已保存" ✓。

草稿保存的成败仍通过**本次操作反馈**表达 ✓ ⇒ ⇒ 常驻那一行说的是**状态** ✓ ⇒ ⇒ 两者不重复 ✓。

| 状态 | 含义 |
| --- | --- |
| 无同步目标 | 这个文档不与任何文件同步（导入的、Web 端的草稿） |
| 已同步 | 草稿与同步目标一致 |
| 未同步 | 草稿比同步目标新（当前修订 ≠ 上次同步的修订） |
| 同步失败 | 上一次同步没成功（原生侧写入失败等）。冲突里选"取消"不算失败——文档只是仍处于未同步 |

草稿持久化失败时提示草稿未保存，原文件写回未尝试。草稿已保存而原文件写回失败时，提示「草稿已保存，原文件未写回」。

### 2.3 未同步的判定

上下文记录 `lastSyncedRevision`：上次与文件一致时的文档修订。

- **打开时**按"草稿内容与文件当前内容是否相同"定：相同 ⇒ 置为 `document.revision`（此刻一致）；不同 ⇒ 记 null（此刻不一致），按未同步显示；
- **同步成功后**置为 `document.revision`；
- 判定：`document.revision !== lastSyncedRevision` ⇒ **未同步**。

重新关联后无法证明一致时记 null，按未同步显示。

这与既有 `DocumentSession.dirty = document.revision !== savedRevision` 同形，只是基线从"应用草稿"换成"同步目标"。不另设 dirty 布尔量。

## 3. 访问与文件引用

### 3.1 Tauri 原生文件通道

原生文件能力只经 `files.rs` 的受守卫命令：

| 命令 | 作用 | 角色 |
| --- | --- | --- |
| `select_native_open` | 系统文件选择器 + 签发句柄 | 读 + 写 |
| `select_native_save` | 系统保存对话框 + 签发句柄 | 读 + 写 |
| `read_native_text` | 按 key 读文本（限 50MiB，严格 UTF-8） | 读 |
| `is_native_synced` | 按 key 问一句：**这个文件还是上次同步的那一版吗**。原生侧用它保存的摘要回答，摘要值不出原生侧（§3.4） | 读 |
| `write_native_bytes` | 按选择器授予的目标写字节（限 100MiB，同目录临时提交）。原文件同步使用下列受保护入口 | 写 |
| 同步写入入口（G4） | 按句柄和冻结请求提交。普通写回匹配原生同步基线，确认覆盖匹配原生记录的一次性确认与冲突版本 | 写 |
| `release_native_file` | 放掉句柄 | — |

**原文件同步写入由 Rust 复核。** 原生问答用于选择交互分支，写入权限与磁盘版本由提交入口核对。原文件写回不得经通用字节写入入口绕过 G4。

`print_native_pdf` 同在此文件、同受守卫，但属 PDF 交付路径，约束见导出契约，不在本文范围。

**冲突检测必须在原生侧完成。** §6.1 要问的是"文件还是上次同步的那一版吗"，这条判断若放在应用侧（先把摘要读上来再比）就等于让摘要值跨过原生侧 boundary，与 §3.4 相悖。所以原生侧提供的是一句问答（`is_native_synced`），应用侧既拿不到摘要，也不需要自己比。

**不引入 JS 插件通道。** 插件命令（文件读写、对话框）的授权由应用能力清单承担，而本项目的隔离层是 Rust 来源守卫；引入插件通道等于再加一道闸，且新增的那道正是本仓已判定"不构成隔离"的 ACL 层（探针阶段记录 D0-3）。

### 3.2 访问的形态（操作系统授予，原生侧遵从）

**访问不是应用层的概念** ✓ ⇒ ⇒ 用户在系统对话框里选中文件的那一刻，操作系统就把访问给了 ✓ ⇒ ⇒ 原生侧只**遵从** ✓ ⇒ ⇒ 应用层没有"权限""角色"这些词 ✓ ⇒ ⇒ 应用层只说"写到这个文件"，成不成由原生侧回答并给出原因码 ✓（§9 ✓）。

- **句柄**是原生侧给的不透明 key ✓：与路径无算术关系 ✓ ⇒ ⇒ 前端拿它无法反推路径 ✓ ⇒ ⇒ 前端也不能自己命名路径 ✓（§10 第 6 条 ✓）。
- **写能力来自"用户选中即表达编辑意图"** ✓ ⇒ ⇒ 打开时签发的句柄**具备读与写两种能力** ✓ ⇒ ⇒ 写只在用户显式触发保存/另存为时使用 ✓ ⇒ ⇒ 建立句柄本身不写任何字节 ✓。约束由"同一文件的读写分离"改为"**不同文件**之间的分离"——只读选择的文件不会被写 ✓。
  - 原生侧改动：`FileAccess::path(key, writable)` 的角色判定由"必须相等"改为"要写必须可写；要读时可写蕴含可读"（当前实现 `grant.writable != writable` 会把可写句柄挡在读路径外）。
- **句柄在进程内有效** ✓ ⇒ ⇒ 进程结束即失效，不落盘 ✓。
- **不用了就放掉** ✓：走 `release_native_file` ✓ ⇒ ⇒ 立即禁止新操作并作废该句柄下的待确认和排队操作 ✓。最终提交准入指 Rust 在同目标串行边界内完成末次复核后、调用替换前登记的状态。该登记与放掉使用同一裁决。工作台发起重新关联时立即取消尚未提交的覆盖确认，由 Rust 使对应确认标识失效。若已有写入请求发出，等待其实际回执后再切换绑定并放掉句柄。若独立的放掉或失效先发生，Rust 按下述规则处理。放掉先发生时，尚未进入最终提交的写入取消并清理临时文件。写入先进入最终提交时，允许完成并返回原目标的实际结果，放掉在该操作结束后回收内部资源。

### 3.3 文件引用（会话内）

**引用是什么**

- 引用 = **这个文件的规范名的会话内别名**，由原生侧签发，随进程消亡。规范名由操作系统给出（canonicalize：解析符号链接与相对分量）；**规范名一致就是同一个文件**。
- 引用唯一回答一个问题：**这个文件是不是已经开着**（§5.2、§5.3）。
- 规范名本身不出原生侧。前端拿的是随机 token，不是路径（§1.3 #1）。token 是随机的，不是规范名的摘要。
- 引用**不是能力**。访问句柄才是能力（读、写、会失效）；引用只是"同一个"的标记。

**为什么不做路径摘要**

- 路径熵低（家目录 + 少数文件名），摘要可被字典枚举还原，等于把"路径不出原生侧"削弱成"需要暴力枚举才能反推"；
- 字符串规范化规则在大小写不敏感文件系统上会误折叠（`A.md` 与 `a.md` 在 Linux 是两个文件，在 Windows/macOS 常常是同一个），而跨平台规范化规则又被本设计明确拒绝制定。

**两条寿命**

- 访问句柄：能力，随进程失效，放掉即失效。
- 文件引用：别名，随进程失效；**放掉句柄不注销引用**——引用要活过访问的结束，否则关掉标签页再打开同一个文件就找不到 IndexedDB 里那份内容（§5.2 ✓）。

**不承诺什么**

**这些不是应用层要承诺的事** ✓ ⇒ ⇒ 跨会话由 §13 一条声明（本期不做）✓ ⇒ ⇒ 跨改名、跨替换、大小写折叠都是原生侧"规范名由操作系统给出"的结果 ✓ ⇒ ⇒ 应用层不承诺、也不需要知道 ✓ ⇒ ⇒ 说到底：**改名不等于留着旧概念** ✓（《概念裁剪》§2 ✓）。

**将来的方向（只定方向，不定实现）**

- 本地持久化一份绑定记录：原生侧 `绑定 id → 规范名`，应用侧 `绑定 id → 文档 id + 修订基线`。
- 跨会话的"是不是同一个文件"由原生侧比较规范名得出，应用侧不碰路径。
- **这条路不需要 OS 级文件身份**（`st_dev + st_ino` / 卷序列号 + 文件索引）。只有需求升级为"文件被改名或被替换后仍要认出"时才需要，而编辑器不做这件事。§13「不做跨重启的绑定恢复」仍然成立。
- 本地那份与 Web 那份的关系（同步、镜像、还是单写）届时再定。

**实现状态**：M4a-3 已实施（§17.2）——`FileAccess` 的"规范名 → token"映射与 `SelectedFile.reference`；M4b-5a 把词面一并换掉（§17.2 ✓）。

> 术语消歧：本文的"**文件引用**"与来源守卫语境下的"**宿主身份**"（window/webview label 配对）不是同一维度。宿主身份决定"哪个 webview 在说话"，文件引用决定"这是哪个文件"。

### 3.4 跨运行时原语：一处实现、一处事实

摘要、字节比较、预算记账这类跨运行时用到的原语，**每个运行时只留一份实现，同一个事实也只存一处**。

| 原语 | 应用侧 | 原生侧 |
| --- | --- | --- |
| 字节摘要 | `src/core/platform/crypto.ts` 的 `sha256Hex`（SubtleCrypto，回落 hash.js）——资产校验已经在用它 | `sha2` 已是依赖；把 `pdf_print.rs` 里私有的 `file_sha256` 提升为共享模块（如 `src-tauri/src/hash.rs`），供 PDF 留证与文件摘要命令共用 |
| 磁盘内容的摘要 | **不存**，也拿不到值。只问一句"还是上次同步的那一版吗" | 随句柄保存（它拥有路径与字节） |
| 字节比较 | 不做 | 提交前的复核与冲突判定都在原生侧 |
| 预算记账 | 只声明上限 | 剩余预算由原生侧算（只有它知道读了多少），应用侧把剩余量作为参数传下去（《本地资源支持设计》§6） |

规则：**应用侧不留原生侧拥有的事实的副本。** 副本要同步；同步一旦失败，它会以"误判冲突"或"误判未变化"的形式出现在用户眼前——§6.1 的同步判定与 §5.2 的"磁盘已变化"判定都建立在这类事实上。

## 4. 文档绑定模型

### 4.1 文档-文件上下文

一个文档与磁盘的关系，是**一份上下文**，不是一袋字段。上下文分两个面：文件（file）、一致性（sync）。**没有 resources 面**——M6 还没实施，应用层不留用不上的概念（《概念裁剪》§1 ✓）。

```ts
interface DocumentFileContext {
  documentId: string;
  file: {
    reference: string;         // 文件引用：规范名的会话内别名（原生侧随机 token，§3.3）
    handle: string;            // 访问句柄（原生侧给出；读与写都用它）
    displayName: string;       // 文件名（原生侧给出）
    displayPath?: string;      // 人类可读的定位串（可选，仅展示）
    sourceFormat: 'markdown' | 'editable-html';
  };
  sync: {
    lastSyncedRevision: number|null;  // 上次与文件一致时的修订；无法证明一致时为 null
    conflict: null | {                // 同步时发现文件已被外部改动
      kind: 'diverged';
    };
  };
}
```

- 存放位置：应用层会话状态，**不持久化**。
- `displayPath` 是展示串，不是标识符，不可用于寻址，也不再回传原生侧。
- **上下文里没有摘要**：磁盘上是什么由原生侧回答（§3.4）。
- `sync.conflict` 落在数据上，"文件已被外部改动"才有确定的状态；覆盖与放弃会解决冲突。取消保留两边内容和未同步状态，下次保存重新检查（§6.1）。

### 4.2 为什么不进文档

`DocumentRecord` 会作为载荷被携带（导入的自包含 HTML 里就有完整文档记录），导出时也会把资产清单整体嵌进产物。把路径或 key 写进去，等于让本机路径随文档离开这台机器，也让"源附件里的路径"看起来像访问凭据。（`documentSchema` 的 `meta` 是 passthrough，额外字段会被保留——所以挡住它的不是 schema，是载荷会外传这件事。）

### 4.3 转移

上下文的每一次变化都是一次**具名转移**。每个转移写明读什么、写什么、哪些不变量保持。

| 转移 | 读 | 写 | 不变量 |
| --- | --- | --- | --- |
| `save` | 当前源快照 | 草稿落 IndexedDB（**所有文档都一样**） | 草稿永远只有一份；不因有无同步目标而分叉 |
| `open` | 选择结果 | 归属按文件引用（§3.3）：命中已有内容则展示那一份，否则以文件当前内容新建；file 就位；`sync.lastSyncedRevision` 按草稿内容与文件当前内容是否相同定（§2.3） | 打开不同步（§5.1）；打开不覆盖草稿；两者一致时不显示未同步（§2.3） |
| `sync` | 当前源快照 | 同步到文件；成功后 `sync.lastSyncedRevision` = 写出的冻结修订 | 失败不改草稿，只报**保存文件错误**；同步期间的新编辑仍算未同步 |
| `pull` | 文件的当前内容 | 反向同步：草稿取文件的版本；`sync.lastSyncedRevision` = 该版本 | 只在草稿自上次同步后未改动时发生（§6.1） |
| `resolve-conflict` | `sync.conflict` | 三选一：覆盖（正向，草稿胜出）/ 放弃（反向，文件胜出）/ 取消（两边都不动） | 覆盖后 `lastSyncedRevision` = 写出的冻结修订；放弃后草稿取文件的版本并同步基线；取消后仍是未同步，下次保存还会问 |
| `save-as` | 选择结果、冻结的源快照 | 写出新文件并**新建文档**绑定它 | 旧文档不受影响；新文档初始即已同步（§2.1） |
| `re-associate` | 选择结果 | file 更新；无法证明与某个文档修订一致时 `sync.lastSyncedRevision = null` | 不读盘覆盖草稿；关联不算同步（§2.3） |

上下文的**七条转移**都在上表。`refresh-assets` 属 resources 面，M6 实施时随那个面一起进上下文（《本地资源支持设计》§8 ✓）。

换文档时上下文的 `documentId` 变了 ⇒ 两个面全部重置（§2.2、§5.2）；侧栏页签切换不换文档，上下文保留。

## 5. M4：打开与拖放接会话

### 5.1 流程

```
用户触发打开或导入
  → Web 浏览器选择器或拖放 / Tauri 原生选择器或拖放
  → 平台适配提供所选项及读取能力，Tauri 另提供会话句柄与文件引用
  → 共用 SourceImport 批次（Tauri 读原生文件时调用 read_native_text）
       逐个文件：读文本（各端自己的读端口解出文本：原生侧在 files.rs，
                浏览器侧在 readSourceFile）→ 扩展名/NUL/源文上限校验
                → schema 解析 → 资产校验 → open（新增或聚焦）
  → 逐项处理：仅有原文件关联意图且有原生句柄时，成功后建立绑定
  → Tauri 放掉未被采用的句柄
```

- 打开与导入共用批次、校验和会话接入。区别在于是否采用原文件绑定。重复打开同一原文件按文件引用聚焦，不同引用不得因内容相同而合并绑定。普通 Web 导入沿用现有工作区去重规则。
- **来源不同就是不同的文件** ✓ ⇒ ⇒ 文件系统不认"同名同 hash" ✓ ⇒ ⇒ 任何编辑器也不认 ✓ ⇒ ⇒ **内容相同不得用来合并来源不同的文件** ✓ ⇒ ⇒ 原生路径上**引用是唯一的合并依据** ✓ ⇒ ⇒ 两个不同的原生文件即使同名同内容，也是两个文档、两个绑定 ✓ ⇒ ⇒ 原生路径**不用**内容哈希那条代理 ✓。
- **归属按引用，不按内容** ✓ ⇒ ⇒ 一个文件恒对应同一份内容 ✓ ⇒ ⇒ 再次打开同一个文件，展示 IndexedDB 里存的那一份 ✓ ⇒ ⇒ 不新建 ✓ ⇒ ⇒ 文件内容在应用外变了也不改归属 ✓ ⇒ ⇒ 那时提示"磁盘上的文件已变化"（§5.2）✓ ⇒ ⇒ 草稿不被覆盖 ✓。
- Web 端没有文件引用 ✓ ⇒ ⇒ 那条"同名 + 内容"只能是**代理** ✓ ⇒ ⇒ 它可能把两个内容相同的不同文件并成一个 ✓ ⇒ ⇒ **这是 Web 端能力缺席的代价** ✓ ⇒ ⇒ 明确记为已知近似 ✓ ⇒ ⇒ 原生路径不适用这条代理 ✓。
- 校验与内容去重复用 `SourceImport` 已有的实现，**不在 UI 侧另写一套**。
- 原生读取的字节上限（50MiB）与 Web 端 `SourceImport` 的上限（`50 * 1024 * 1024`）字节一致，两端不会因为来源不同而给出不同的可导入集合。
- **字节层的验证在各自那一侧** ✓ ⇒ ⇒ **Tauri 形态下原生侧完全承担读写的验证** ✓ ⇒ ⇒ 前端一个字节都不碰 ✓ ⇒ ⇒ 调用者准入在 `source_guard.rs` ✓ ⇒ ⇒ 判文件内容的在 `files.rs`（大小 ✓、普通文件 ✓、严格 UTF-8 ✓、剥 BOM ✓、写入的上限与拒绝链接 ✓）⇒ ⇒ **命令契约不动** ✓ ⇒ ⇒ 浏览器构建自己验自己的那份 ✓（没有原生侧可依靠 ✓）⇒ ⇒ 两端因此各有一处解码 ✓ ⇒ ⇒ 但规则一致 ✓。
- **将来**：文件层的规则可以住进一个 crate，两个目标各编译一次（原生侧 Rust、浏览器侧 wasm），两种形态共用一份；**暂不考虑设计与实现** ✓。
- 批次内某一项失败不影响其他项。
- 打开**不**自动触发同步，也不改变草稿状态。

**三类 key 的处置**：绑定采用的保留；去重命中（未建新绑定）的立即释放；导入失败的立即释放。

### 5.2 聚焦与"磁盘已变化"

同一 `fileIdentity` 已有绑定时：**聚焦该标签页**，不新建文档，不覆盖磁盘内容，不清未同步提示。

聚焦时向原生侧问一句：**这个文件还是打开时的那份吗**。原生侧用句柄里保存的摘要回答，应用侧不留副本（§3.4）。

- 是 ⇒ 直接聚焦；
- 否 ⇒ 提示"磁盘上的文件已变化"，由用户决定是否重新载入；**不静默覆盖**内存中的修改。

**归属命中、但绑定已释放**时（上一次的绑定随标签页关闭而释放）：**展示 IndexedDB 里存的那一份**，不新建、不覆盖草稿，并建立新的绑定（§4.3 的 `open` 转移）。此时两份内容都在应用手上 ⇒ ⇒ 直接比较草稿内容与文件当前内容 ⇒ ⇒ 相同则基线 = 草稿修订（§2.3）⇒ ⇒ 不同则基线 = null ⇒ ⇒ 按未同步显示 ⇒ ⇒ 是否重新载入由用户决定。

"未同步"与"磁盘已变化"是两个独立条件：前者来自修订比较（应用侧），后者来自原生侧的问答（§3.4），或在归属命中时来自两份内容的比较。

### 5.3 去重的优先级

现有 `SourceImport` 的去重是"同名 + 内容 SHA-256"（`documentKey`），HTML 路径完全不去重。这与文件引用是**两个维度**，需要定优先级：

1. **原生端按引用归属**：同一 `reference` ⇒ 同一份内容（同一文档 id）✓ ⇒ ⇒ 绑定还在就聚焦那个标签页 ✓ ⇒ ⇒ 句柄已放掉就展示 IndexedDB 里那一份并重新绑定 ✓ ⇒ ⇒ **不按内容摘要归属** ✓ ⇒ ⇒ 磁盘内容变了也不改归属 ✓（§5.1 ✓）。
2. **内容哈希降为二级，且仅限 Web 端**：同名同内容 ⇒ 复用同一文档 id（既有行为，保留）⇒ ⇒ **原生端没有这一条** ✓ ⇒ ⇒ 原生端由引用决定一切 ✓（§5.1 ✓）。
3. **HTML 路径**：不走去重，按 §5.1 正常新建（可编辑 HTML 的内容键与文件引用不可比）。

实现落点：`SourceImportPorts` 增加一个引用端口（或在 `open` 端口旁增加 `focus` 端口），`ImportItemResult` 增加"磁盘已变化，需确认"这一态。`src/application/workspace/sourceImport.ts` 因此**在改动面内**。

### 5.4 拖放

拖放与文件选择进入**同一个** `SourceImport` 批次，不另开一条路径。拖放同样只拿到句柄与引用，不拿路径。

拖放产生的文件引用必须与选择器一致（同一原生来源），否则"拖进来的是刚才打开的那个文件"这种去重会失效。

### 5.5 重新关联

父计划 M4 的验收含"重新关联入口"。定义：

- 入口：**顶栏的重新关联** ✓（桌面端 ✓）⇒ ⇒ 对当前草稿显式发起，由原生选择器取得新句柄。正常打开命中同会话有效绑定时按 §5.2 聚焦已有 Tab。若重新关联所选文件已绑定另一文档，聚焦原文档并放掉新句柄。
- 重新关联与"打开"是两件事：**打开**是让这个文件对应它自己的那份内容（§5.1）；**重新关联**是让当前这份草稿指向另一个文件。
- 重新关联**不读盘覆盖草稿**：草稿内容保持不变，只把绑定指回该文件；建立句柄本身不算同步。
- 取消 / 失败不改变草稿、修订或编辑状态。
- 用会话内 `reference` 检测重复绑定。进程重启后原句柄失效，本期范围按 §13 处理。

## 6. M5：同步

### 6.1 同步是保存的第二步

保存对所有文档都是同一个动作：**落草稿**，然后（有同步目标时）**同步一步**。草稿自动持久化、永远只有一份；同步失败不影响草稿。

**一次保存 = 一个源快照**：草稿与文件写的是同一份字节，两者不会差一个按键。

**顺序：先草稿，后同步。** Web 和 Tauri 调用同一应用保存入口。保存服务先持久化冻结草稿。成功且存在原文件绑定时才调用 Rust 写回端口。草稿失败时结束本次保存，写回结果记为未尝试。

同步的完整流程：

1. 冻结文档 ID、修订、待写源字节与当前上下文的 identity（§4.3）。对同一目标串行处理。每次同步记录绑定实例标识，回填结果前核对文档 ID 和绑定实例；失效结果只报告原目标的实际结果，不能更新当前上下文。
2. 落草稿（IndexedDB）。**这一步对所有文档都一样**，没有同步目标的文档到此结束。
3. 有同步目标时，向原生侧问一句：**这个文件还是上次同步的那一版吗**（`is_native_synced`，摘要不出原生侧，§3.4）。
   - **是** ⇒ 正向同步：Rust 在提交前复核原生记录的同步基线，匹配时才提交冻结字节（同目录临时文件 + rename）。若发现磁盘变化，按新的冲突结果重新分流。成功后 `sync.lastSyncedRevision` = 写出的冻结修订。
   - **否**，文件被外部改过 ⇒ 分两种：
     - **草稿自上次同步后没有改动**（`document.revision === lastSyncedRevision`）⇒ 这不是冲突，是一次更新：**反向同步**——把文件的当前内容读回草稿，`lastSyncedRevision` 随之更新。
     - **草稿也改过** ⇒ 冲突，建立 `sync.conflict` 并提示。**三个选择**：
       - **覆盖**（正向同步，草稿胜出）：提交本次确认标识及冻结的写回请求，按 G4 复核。写入成功后 `lastSyncedRevision` = 写出的冻结修订；
       - **放弃**（反向同步，文件胜出）：草稿的本地改动被丢弃，草稿取文件的版本；`lastSyncedRevision` 随之更新；
       - **取消**：两边都不动。草稿保留本地改动，文件保留外部改动，文档仍是"未同步"，下次保存还会再问。
4. 写入失败（原生侧报错、句柄失效、目标消失）⇒ 报**保存文件错误**，草稿不动，绑定不变。

**G4 覆盖确认与提交前复核。** Rust 在发现冲突时记录实际打开对象的文件系统身份（如卷与文件 ID，或设备与 inode）及原始字节摘要，两者共同表示观察到的磁盘版本。用于 Tab 去重的路径 token 独立于此。相同路径换成另一个对象时按替换处理，即使字节相同。无法可靠核对对象身份时拒绝原文件写回。Rust 返回不透明的一次性确认标识。确认绑定到授权、目标身份及本次冻结请求，原生侧核对待写字节与原请求一致。应用把它关联到文档 ID、绑定实例和待写修订。用户取消或开始重新关联时立即撤下确认，Rust 同时注销该标识。Rust 校验并消费标识后只尝试提交一次，失败亦不得复用。普通写回和确认覆盖都在同目标串行边界内，临时写入完成后、最终替换前复核授权、目标身份和相应磁盘版本。目标再次变化时清理临时文件，返回结构化的新冲突结果，等待用户重新确认。无效确认与授权失效分别返回稳定原因码。删除或无法确认目标身份时按失效处理。Rust 保留摘要，回执仅报告实际结果。

条件复核缩短了检查与替换的间隔。外部进程仍可能在最后复核后修改目标，验收以提交前复核为准。草稿与文件仍按正向、反向同步处理，冲突保持覆盖、放弃和取消三个选择。

> **待退化（2026-11-09 审查）** ✓：复核只需比较**目标当前摘要**与**授权里记的那一份** ✓ ⇒ ⇒ 两者原生侧都有 ✓ ⇒ ⇒ 前端不传期望摘要 ✓ ⇒ ⇒ 对象身份（卷与文件 ID / 设备与 inode）可以去掉 ✓ ⇒ ⇒ 一次性确认令牌（签发、消费、失效、不可复用）也可以去掉 ✓ ⇒ ⇒ 用户选"覆盖"之后的写入是无条件的 ✓ ⇒ ⇒ 与本文档修订记录里"覆盖是无条件的"一致 ✓ ⇒ ⇒ 与 `is_native_synced` 是同一原语的两处调用 ✓ ⇒ ⇒ 本段按此改写后再进入 M5 ✓。

**搁置**：冲突里"把草稿另存到第三个文件、两边都留下"这个出口本期不做（§13）；本期只有上面三个选择。

写入内容随源格式而异：Markdown 文档写原始 Markdown 字节，不写渲染结果；可编辑 HTML 文档写其源载荷，不写 Markdown 覆盖。

**字节保真（已知限制）**：原生读取会剥掉 UTF-8 BOM，编辑器的值把 CRLF 规范化为 LF，因此同步出去的文件是**无 BOM 的 LF**。对原本是 CRLF 的 Windows 文件，这是一次全文件差异。本期不保真换行风格，也不弹提示——但这条要写进设计，别在验收时当缺陷。

每次保存分别记录冻结修订的草稿结果和原文件写回结果。草稿结果区分成功、失败。写回结果区分无绑定（不适用）、未尝试、已写回、冲突待决定、取消及失败。冲突后选择反向同步时记录其结果并更新同步基线，不能记作已写回。已写回结果只确认实际提交的修订与绑定。草稿成功但写回未完成时，反馈同时说明草稿已保存及原文件状态。Web 无绑定时草稿成功即保存成功。两项结果沿用现有状态与回执表达；**常驻状态区分两行表达**（§2.2、§8.4）：草稿维度与同步维度各说各的，操作反馈说"刚才那一次"，常驻行说"现在是什么状态"。

### 6.2 另存为

另存为**产生另一个文档**：

1. `select_native_save`（带建议文件名，文件名规则复用导出契约的完整名与扩展名）。
2. 用户取消 ⇒ 无新句柄，无任何状态变化。
3. 写出成功后**新建一个文档**绑定该文件，初始 `lastSyncedRevision` = 写出的修订（即已同步），并切换过去。**旧文档不受影响**：它继续同步它自己的文件（或没有同步目标），两边互不相关。

**跨目录的相对引用（已知限制）**：正文里的相对图片引用（如 `![](images/a.png)`）在源快照语义下**不被改写**。另存到另一个目录后，这些引用在新位置会失效。写入的 .md 仍然只含相对引用，路径语义由新目录决定。

因此另存为必须提示这一点，并提供两个可选项（本期只提示，不自动处理）：

- 接受：新目录下的相对引用按新位置解释（可能裂图）；
- 或先在原目录另存，再手动搬运资源。

把资源一并写出（定义资源目录布局）或把引用改写为绝对/内联，属于后续能力，本期不做（§13）。

另存为是显式选择新源文件目标的操作，成功后按 §2.1 创建并绑定新文档。本期另存为的原文件绑定由 Tauri 提供。Web 继续通过导出下载源文件副本，下载不会建立可写回的本地绑定。导出由独立导出流程交付冻结产物，包括 Markdown 源输出，均不建立或改变当前文档的绑定和同步基线。

### 6.3 显式动作与快捷键

快捷键（`Ctrl/Cmd+S` 保存、`Ctrl/Cmd+Shift+S` 另存为、`Ctrl/Cmd+O` 打开）**只触发与按钮完全相同的动作**，不构成第二条路径，也不允许绕过"没有同步目标时保存只落草稿"的判定。

### 6.4 "保存"只有一个意思

顶栏的"保存"按钮在两端是**同一个动作**：落草稿，有同步目标时再同步一步。桌面端不再有另一个"保存"（写回文件）的意思——**同步是保存的一部分，不是另一件事**。

- 有同步目标 ⇒ 保存 = 草稿 + 同步；
- 无同步目标（导入的、Web 端的草稿）⇒ 保存 = 草稿。

状态区显示**两个维度**（§2.2）✓：草稿维度与同步维度 ✓ ⇒ ⇒ 两端同一套文案 ✓ ⇒ ⇒ 措辞各归各的 ✓ ⇒ ⇒ 草稿那一行说草稿、同步那一行说文件 ✓ ⇒ ⇒ 不用含混的"已保存" ✓。

## 9. 回执与错误

原生命令的返回在应用层分三类，不混用：

| 类别 | 判定 | 对状态的影响 |
| --- | --- | --- |
| 取消 | 用户在系统对话框取消（原生侧返回"未选"） | 无 |
| 失败 | 操作未完成且原因不是取消 | 上下文与未同步状态不变 |
| 拒绝 | 来源守卫拒绝 | 与失败同样处理，文案区分（内部条件，不是用户操作问题） |

**取消在原生侧是可区分的**：`blocking_pick_files` / `blocking_save_file` 返回"未选"，与错误是两条路径。但要在应用层保住这个区分，需要两处改动：

1. **稳定码枚举化**。现在原生侧把所有 IO 失败塌缩成一个码（`files.rs` 的 `error()` → `native-io-failed`），前端只能靠**子串匹配**识别拒绝（`files.ts:15` 的 `String(error).includes(SOURCE_DENIED)`）。应改为：前端拿到结构化的机器码 + 友好文案两层，拒绝不再靠子串；原生侧细分失败原因（目标不存在 / 权限 / IO / 超限 / 目标不是普通文件），否则 UI 无法区分"文件被移走"与"磁盘写不进去"。
**稳定机器码清单**（原生侧给出；两边必须同步改）。**码按性质分四类** ✓，"不是错误"的那两类不在这张表里 ✓：

| 类 | 机器码 | 含义 | 用户看到 |
| --- | --- | --- | --- |
| **拒绝** | `native-source-denied` | 来源守卫拒绝 | 当前窗口无权使用原生文件能力 |
| **失败（用户可行动）** | `native-target-missing` | 目标不存在 | 文件已被移走或重命名 |
| | `native-permission-denied` | 权限不足 | 没有权限访问这个文件 |
| | `native-io-failed` | 其余 IO 失败 | 文件读写失败 |
| | `native-dialog-failed` | 系统对话框自身故障（**与取消不同**） | 系统文件对话框打不开 |
| | `file-too-large` | 超过大小上限 | 文件超过可处理的大小上限 |
| | `invalid-utf8` | 不是合法 UTF-8 文本 | 文件不是合法的 UTF-8 文本 |
| | `not-a-file` / `not-a-regular-target` | 目标不是普通文件 | 目标不是一个普通文件 |
| | `unknown-file-key` | 句柄不存在或已放掉 | 这个文件已经不再可访问 |
| | `print-failed` | 打印失败 | 打印失败 |
| **内部失活（不是用户的错）** | `file-capability-mismatch` | 应用把只读的句柄当可写的用 | 通用失败文案 |
| | `native-internal-failed` | 内部状态不可用（互斥锁中毒） | 通用失败文案 |
| | `invalid-file-name` / `invalid-target` | 名字或路径不可用 | 通用失败文案 |

**只有"用户可行动或可理解"那一类进前端的文案表** ✓；内部失活那类**不是用户造成的** ⇒ 用户看一句通用失败即可 ✓，机器码仍留在错误对象上给日志与诊断 ✓。

**取消不是错误**：选择器返回"未选"（`Ok(None)`），没有机器码 ✓（§12.5 把 macOS / Linux 的对话框语义留给 M10 验证 ✓）。
**G4 专用结果码。** 下列稳定码同样纳入 §8.5 文案配置。同步问答保持布尔语义，写回入口返回已提交或冲突。冲突结果用 `write-conflict`，提交前发现再次变化用 `write-target-changed`，目标身份仍有效时可附新的确认标识。确认已使用、过期或取消统一用 `write-confirmation-invalid`，句柄已放掉沿用 `unknown-file-key`。不回传路径或摘要，确认标识不用于展示和日志。验收覆盖替换同路径文件、确认过期、重放及句柄放掉。
**回执不是错误**："印出来了但没提交"是回执（`not-committed`）✓，不是失败 ✓，不进失败码表 ✓。

**打印路径的失败原因不是码**：那是诊断句（"打印宿主创建失败"）✓ ⇒ 命令边界只给固定码 `print-failed` ✓ ⇒ 诊断句留在原生侧 ✓：探针按它取证 ✓（它直接读实现层的回执 ✓），应用层看不到它 ✓（与今天一致 ✓）。

2. **跨平台语义需验证**。Linux（xdg portal）与 macOS 的对话框实现有可能把"对话框失败"也折叠成"未选"。§12.5 把 macOS/Linux 推给 M10，但"取消必须是取消"这条语义不能默认成立——需在对应平台各验一次。

"关联已失效"只在读/写失败且原因为"目标不存在"时标记；不做后台监视（§13）。

## 10. 隔离与安全边界

1. 文件能力只有 `files.rs` 一个来源，受 `source_guard` 单闸保护。
2. 不新增能力清单文件；新增受保护命令不改变允许范围（仍是 main/main），只扩大命令集合。
3. 不引入全盘读取范围：读取范围是用户本次选择的文件及另有原生句柄的目录。目录授权按《本地资源支持设计》§5 发放。
4. 句柄与文件引用 token 都不落盘、不进文档、不进日志（除必要的命令名与字节数）。
5. 路径不出原生侧；日志不记路径。
6. 应用不引入任意路径读写命令（"前端给个路径就读写"是禁止的形态）。
7. 目录授权及同一对象句柄读取按《本地资源支持设计》§5 执行。

## 11. 可观测性

- **同步与读取的结果已经有日志**：`write_native_bytes` / `read_native_text` 等命令在命令 span 内记 `source_decision` 与 `operation_result`（含字节数与原因码）。这部分不需要新做。
- **绑定的建立与释放是应用层状态**，原生侧的页面可回传事件是封闭枚举（`page_ready` / `call_started` / `call_finished` / `page_error`），没有承载位；原生侧也不知道绑定（绑定是应用层概念）。
  ⇒ **本期不把绑定生命周期记进原生日志。** 若要可观测性，先扩日志契约（`log-base-plan` §5.1 / §5.2 的 span 词汇与事件集），那是独立一步，不在本设计内。

2026-11-06 同步模型重构后修订。主要改动：

- **草稿是唯一的存放处**（§0、§2.1、§6.4）：IndexedDB 自动持久化、永远只有一份；本地文件是这份草稿的**同步目标**，不是另一种存储。于是"保存"在两端是同一个动作——落草稿，有同步目标时再同步一步；Web 端只是没有第二步。原先"桌面端保存 = 写回文件 / Web 端保存 = 存草稿"的分叉随之消失；
- **历史取舍，操作反馈已按 §6.1 调整**。**界面不再有"草稿已保存"这个状态**（§2.2）：草稿自动持久化，没有这种状态可表达。界面只表达同步状态，而同步失败在界面上叫**保存文件错误**——它是保存这件事里唯一会失败的部分；
- **另存为产生另一个文档**（§2.1、§6.2）：写新文件 + 新建文档绑定它，初始即已同步；旧文档继续同步它自己的文件，两边互不相关。原稿的"另存为 = 改指绑定"作废；
- **历史取舍，写入部分已由 G4 覆盖**。**同步只有两个方向，不做行级冲突解决**（§6.1）：正向（草稿→文件）与反向（文件→草稿）是同一件事的两个方向。冲突只有**覆盖**与**放弃**两个选择；覆盖是用户的明确选择，因此写入是**无条件**的——"期望摘要 + 重试一次 + 条件写原语"整套机制都不需要了，原语表里少了 `write_native_bytes_conditional`，冲突检测改成原生侧的一句问答 `is_native_synced`（应用侧连摘要值都拿不到）。文件被外部改动而草稿未改动时，走反向同步，不算冲突、不弹提示；

## 0. 这份文档是什么 / 不是什么

**是什么**：两份清单。

- **§1 核心观点** ⇒ 判定依据。回答"这个设计对不对"时用。
- **§2 已定决策索引** ⇒ 检索表。回答"这条定过了吗、在哪一节"时用。

**不是什么**：

- **不是决策的正文**。决策留在有上下文的地方（设计文档、评审记录、契约文件）。这里只指路。
- **不是愿望清单**。出现"以后应该…""建议…"就是跑偏了。
- **不是第二份设计文档**。若它长到需要目录导航，说明它变成了那个东西。

**为什么要它**：两件具体的事。

1. **同一条决定被重复推导**。M5-b1 动手前，"冲突消解是三个选择"这件事定在 `5bb8f77` 与《本地文档支持设计》§0，而实作核对时是翻 git 历史、翻旧会话记录才找到的。有 §2 就会是三十秒的事。
2. **同一条清单被写两遍，然后漂**。《本地文档支持设计》里"写回结果的六种"曾写了两次（§6.1 与 §6.5），两处都自称"六种"，成员不同 ⇒ ⇒ 合并是七种 ⇒ ⇒ 漂了。**代码层有"一个事实一处存放"，文档层当时没有** ⇒ ⇒ §1 的第一条就是它。

## 1. 核心观点

每条四样：**观点**、**判定问句**、**反例**、**落点**（仓库里已经体现它的地方）。

**没有落点的观点不写** ⇒ ⇒ 能写成检查的就写成检查 ⇒ ⇒ 脚本与测试是观点的可执行形态 ⇒ ⇒ §1 因此不会变成套话。

### 1.1 一个事实一处存放

- **观点**：同一个事实只有一份。副本要同步；同步一旦失败，它会以"误判冲突"或"误判未变化"的形式出现在用户眼前。
- **问句**：这个事实的第二份副本会漂吗？
- **反例**：文档层曾有的"六种"清单（同一份写两遍 ⇒ 漂 ⇒ 本文档 §0 的第 2 条 ✓ ⇒ ⇒ 现在那份清单由模型推出 ✓ ⇒ ⇒ 只有一处 ✓）。
- **落点**：`docs/contracts/*.json`（两端读同一份）✓；`src/core/platform/crypto.ts` 与 `src-tauri/src/hash.rs`（每个运行时一份实现）✓；`src/application/messages.ts` 的 `MESSAGE_CATEGORIES` 与 `web_error_categories!`（两侧一张表）✓。

### 1.2 事实归拥有者，判断也归拥有者

- **观点**：拥有事实的一方回答关于它的问题。应用层不替拥有者做判断。
- **问句**：这是不是在替拥有者做判断？
- **反例**：应用侧存一份磁盘摘要、自己比较 ⇒ ⇒ 两份摘要要同步 ⇒ ⇒ 同步失败就是误判。
- **落点**：`detect_native_target` 只回**状态**（`ready` / `changed` / `missing` / `unwritable` / `invalid` ✓），不回摘要 ✓；复核在 `write_native_sync` 内部（临时文件写完后、rename 之前）✓；原生侧不判"该同步还是该反向" ✓。

### 1.3 概念留在应用层，当且仅当应用层自己要用它回答一个问题

- **观点**：机制归机制，名词归名词。把不属于应用层的判断下沉到事实的拥有者那边；应用层只保留它要问的问题。
- **问句**：应用层自己答得上来吗？答不上来 ⇒ ⇒ 裁掉或下沉。
- **反例**：`sync.conflict` 曾留在上下文里（"文件已被外部改动"）⇒ ⇒ 可它不回答任何应用层要答的问题 ⇒ ⇒ 冲突是同步操作内部的一次提问 ⇒ ⇒ 裁掉（§2 记着这件事）。
- **反例**："一次保存"曾把**草稿的存放**与**写回文件**接成一个流程 ⇒ ⇒ "先草稿、后文件"还成了规则 ⇒ ⇒ 可那是一个应用层答不上来的问题 ⇒ ⇒ **两件事** ⇒ ⇒ 不接 ✓ ⇒ ⇒ 写回的结果因此从六种变五种 ✓ ⇒ ⇒ "草稿没存住所以没试"那种结果没有了 ✓（§2 记着这件事）。
- **反例**："关联还有效"曾想留在上下文里当一个常驻字段 ⇒ ⇒ 应用自己判 ⇒ ⇒ 而**"那个目标还在吗"是读侧的一句问答** ⇒ ⇒ 应用层答不上来 ⇒ ⇒ 只能由原生侧答 ✓ ⇒ ⇒ 应用侧据它派生 ✓ ⇒ ⇒ ⇒ **每一次写之后都跟一次验证读** ✓ ⇒ ⇒ ⇒ 写完之后的那个判断才是刚读出来的 ✓（§2 记着这件事）。
- **反例**：把"写成功"当成关联 ⇒ ⇒ 写成功只是**写出去了一件事** ✓ ⇒ ⇒ **那个文件在不在，答案在读那边** ✓ ⇒ ⇒ ⇒ **关联始终基于读成功** ✓ ⇒ ⇒ ⇒ 写 ⇒ ⇒ **接着读** ✓ ⇒ ⇒ ⇒ 读没确认 ⇒ ⇒ **没有关联** ✓（§2 记着这件事）。
- **落点**：《概念裁剪》§0–§1 的三个问句与"下沉/改名"两种手法 ✓；`sync.conflict` 与 `sync.pendingConfirmation` 两次裁剪 ✓；《本地文档支持设计》§4.3 / §6.1 的读写模型 ✓。

### 1.4 规则住在纯模块，宿主只给端口

- **观点**：能脱离宿主单测的规则，就放进纯模块；宿主给端口，平台差异留在平台那一侧。
- **问句**：这段判断要不要起浏览器、开桌面外壳才测得了？
- **反例**：把"文件变没变"的判定写在组件里 ⇒ ⇒ 测它要起浏览器 ⇒ ⇒ 没人测。
- **落点**：`src/application/workspace/documentOpen.ts`（宿主只给 `open`/`reference`/`boundDocument`/`detect`/`releaseHandle` 五个端口 ✓ ⇒ ⇒ **`detect` 答状态** ✓）✓；`scripts/check-module-boundaries.ts`（纯模块不许 import 非纯模块）✓；`src/application/workspace/outlineState.ts` 同一范式 ✓。

### 1.5 平台差异是端口的实现差异，不是调用点的分支

- **观点**：应用层不判 `isTauri`。有没有这个能力，由端口的实现回答。
- **问句**：这里是不是出现了 `isTauri`？
- **反例**：在应用层写 `if (isTauri) 写回 else 落草稿` ⇒ ⇒ 应用层开始知道平台 ⇒ ⇒ 平台知识散开。
- **落点**：《本地文档支持设计》§6.5 的端口表（**Web 侧那几个端口答不了就抛** ✓ ⇒ ⇒ 整条同步逻辑在 Web 形态下不跑 ✓）；`src/core/platform/tauri/files.ts` 的 `isNativeSynced` 只回布尔 ✓；`src/core/platform/web/filePorts.ts` 与 `src/core/platform/tauri/filePorts.ts` **两端各一套** ✓ ⇒ ⇒ 调用点不分叉 ✓。

### 1.6 派生优于存储

- **观点**：能现算的就现算。存下来的那份会过期。
- **问句**：这是存一份，还是现算一份？
- **反例**：待处理资源数曾作为字段存在 ⇒ ⇒ 那是快照的副本 ⇒ ⇒ 两边会不一致 ⇒ ⇒ 改为派生。
- **落点**：`syncStatus()`（界面读派生值，各处不各判一遍）✓；《本地文档支持设计》§8.6 的视图模型表 ✓；**写完之后跟一次验证读** ⇒ ⇒ 派生出来的关联有效性**不会过期** ✓ ⇒ ⇒ 写失败时它也照常刷新 ✓ ⇒ ⇒ 不靠失败推出来 ✓。

### 1.7 失败用封闭词表的机器码，两侧一张表

- **观点**：失败有稳定的机器码；文案在词表里一处给出；两侧（Rust 与 TS）必须同步。
- **问句**：两侧对得上吗？这个码用户能行动吗？
- **反例**：拒绝靠子串匹配 ⇒ ⇒ 文案一改就认不出。
- **落点**：`scripts/check-message-vocabulary.ts`（两侧各 38 类）✓；`WebCommand` 枚举与 `command_name` ✓；`scripts/check-command-admission.ts`（注册/受保护/可汇报三份名单）✓。

### 1.8 决定一处记，索引可查

- **观点**：决定写下来就不要再推导第二次。检索靠索引，不靠考古。
- **问句**：这条定过了吗？定在哪一节？
- **反例**：M5-b1 动手前，"冲突消解是三个选择"要翻 git 历史与旧会话记录才找到（§0 的第 1 条）。
- **落点**：本文档 §2 ✓。

### 1.9 分层分块定位

- **观点**：问题在哪一层，就只查那一层的材料。往上跨一层就要付一次代价，且容易把上一层的结论当成本层的证据。
- **问句**：问题在哪一层？我查的材料超层了吗？
- **反例**：2026-11-09 问"六种结果为什么有两份"，先去翻了 `files.rs`、`App.tsx`、消息表、通知集、边界脚本 ⇒ ⇒ 答案在设计文档 §0 与一条 commit message 里 ⇒ ⇒ **超层了**。
- **落点**：《分析与验证规范》§2（分析：先切小，再顺着因果链往本质追）✓；§2.2（每一层用什么检查）✓。

### 1.10 门是流程上的节点，不是 lint 的子项

- **观点**：一个检查要能被单独跑到，也要能被当成一档的节点。"我跑了 lint"不能等于"所有门都过了"。
- **问句**：这个门在档里是独立的一步吗？漏掉它，这一档还完整吗？
- **反例**：格式检查曾藏在 `lint` 里 ⇒ ⇒ 少跑一个入口时它不在 ⇒ ⇒ 静默遗漏。
- **落点**：`package.json` 的 `check` = typecheck → format:check → lint → unit → build（五个节点）✓；`tests/unit/verification-gates.test.ts` 把这串钉住 ✓。

## 3. 怎么维护

- **§1 加一条的门槛**：能指出**判定问句**、**至少一个反例**、**至少一个落点**。三者缺一 ⇒ ⇒ 不写。落点可以是脚本、测试、契约文件，或设计文档里已写成句的那一段。
- **§2 加一行的门槛**：能指出**定在哪一节**。指不出 ⇒ ⇒ 那是还没定的，别写进索引。
- **状态只有三档**：`成立` / `已定，正文待改` / `已废（指向取代它的那一条）`。不写"待议""可能"。
- **决策被推翻时**：旧行改 `已废` 并指向新行 ⇒ ⇒ **不删** ⇒ ⇒ 历史可追。
- **本表不搬正文**。一行超过两句话 ⇒ ⇒ 那是决策正文 ⇒ ⇒ 它该在那份设计文档里。
- **它自己的复核**：`docs/README.md` 里有一行指向本文档 ⇒ ⇒ 文档导航因此是它的第一道门。

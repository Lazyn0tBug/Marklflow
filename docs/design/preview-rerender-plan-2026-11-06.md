# 预览重渲染优化设计（2026-11-06）

状态：未来版本设计。当前以 Markdown 原文为权威来源，以 HTML 为预览和导出的统一内容映射。沿用浏览器和系统 WebView、现有公式与分页引擎及前后台串行调度。以下验证均待实施。

## 1. 当前路径与证据

计算 Worker 解析 Markdown，返回摘要和源映射。生产预览随后在 DOM 宿主调用 `renderDocument`，A4 经 `paginateDocument` 调用同一渲染器。渲染器先解析原文收集公式，再用 `parseMarkdownDocument` 重新解析并转换为 HTML，随后处理图表、净化和 SVG 引用。一次常规预览中可确认这三个 Markdown 解析入口，Worker 没有返回完整预览 HTML。

早期 macOS Chromium 构建的观察记录了单次键入时约 37–134 ms 的留白，以及 800 行样本连续输入时约 75 ms 的留白。记录缺少可对应的构建标识与分阶段计时，只用来选复验场景。其他解析器的微基准无法确定本应用的耗时分布。

## 2. 两项独立验证

两项均与同一个未改动基线分别对比，记录提交、构建、运行环境、样本和冷热状态。分别通过后再验证组合效果。

### V1 减少作废渲染

在现有预览入口合并内容变更。尾沿静默窗口初试约 300 ms，可调整。IME 组合期间不提交渲染需求，确认组合结束及紧邻输入只产生一次需求。切换 Tab、流式/A4 或渲染配置立即处理，并取消与旧条件关联的计时器。沿用现有角色队列、任务身份和缓存规则。

同一文档等待时保留上次可展示画面，无需刷新标记。完整产物通过身份和版本核对后整体替换。新旧源映射不匹配时暂停双向同步，就绪后按源码行恢复。切换 Tab 只允许显示目标文档匹配的缓存或新产物。React transition 可作为可选提交手段，任务取消和迟到结果仍由协调器判定。

以固定间隔连续输入至少十次，对比渲染请求数、启动数、作废数和实际进入公式、图表、分页的次数。覆盖 IME、迟到结果、切换 Tab 和切换模式。记录最后一次输入到可见、静默窗口结束到可见两种时延。后者对预算内样本以 200 ms 为观察目标，连续输入和超预算文档没有固定刷新时限。

### V2 复用一次语法解析

保留既有解析器及 Worker 协议。只验证渲染器内由同一份语法树提取带源码位置的公式，再用既有转换步骤生成 HTML。预期每次渲染器调用少一次全文解析。Worker 的独立摘要仍保留，整树跨 Worker 传输另行评估。

核对解析调用次数和分阶段耗时，使用含 GFM、作者 HTML、分页符、公式宏与编号、图表及相对资产的样本比较 HTML 语义、源码位置和诊断。渲染器同时服务流式、A4 和冻结导出，等价性验证覆盖三条调用路径。保持现有净化、资产与导出校验。若语义不等价或端到端收益不足以覆盖新增复杂度，保留现有路径。

## 3. 产物接收与诊断

- **局部诊断仍可发布**。产物完整、净化通过、版本及源映射匹配，且失败隔离在有明确位置的安全占位内时，可展示正文和占位。例如单个公式、图表或图片失败。验证出现坏块后继续修改正文，正文仍能刷新，修复坏块后诊断消失。
- **整份产物拒收**。净化或完整性校验失败、源映射无法对应、A4 分页未完成，均不得展示或缓存为完成产物。超时和引擎失败保留同文档上次可展示结果，并在预览范围内反馈失败。首次无可用产物时显示失败状态。取消或迟到结果直接丢弃，避免提示覆盖当前任务。
- 可展示的诊断不等同于导出成功。沿用各格式现有的产物校验和降级确认，导出仍使用冻结输入及统一 HTML 输出源。

## 4. 独立评估与后续选项

**DOT 替换独立评估。** 先明确需要当前有限 DOT 子集还是真正的 Graphviz 兼容性。候选库可替掉自研 DOT 解析、布局与 SVG 生成。保留共享 DOM 调度、错误占位、SVG 净化和 ID 隔离。用相同样本对比支持范围、错误行为、SVG 自包含、冷加载耗时、Web 构建及桌面包增量，并验证离线加载。V1 与 V2 不依赖此项。

**块级渲染待测。** V1、V2 后若数据表明完整文档提交或某个可隔离阶段仍是主要瓶颈，才做局部原型。先验证跨块引用、公式编号、净化、源映射和块身份。源码行号会随编辑移动，不能单独充当稳定身份。A4 仍按整篇验证分页。

**通用 WASM 渲染器待测。** 只有本应用的分阶段数据确认瓶颈可迁移，且同输入对照显示端到端收益足以覆盖加载、包体、跨边界传输及语义迁移成本，才启动验证。端到端超过 200 ms 或桌面需要输出 PDF 都不足以触发此项。Windows PDF 已有 WebView2 交付路径。

## 5. Markdown 转 HTML 的选型

现阶段保留 remark/rehype。先验证 V2 在同一次渲染中复用语法树的收益，解析器选型与 V1 的刷新调度分别评估。

| 路线 | 在本项目的取舍 |
| --- | --- |
| remark/rehype | 复用已实现的语法扩展、HTML 转换和源码位置。V2 预计省去渲染器内一次全文解析，仍保留 HTML 树转换及其依赖。 |
| markdown-it | token 与渲染规则可能替代部分树转换。行内公式偏移、作者 HTML 混排、净化和源映射需要做等价性验证。若需要补回同等复杂度的 HTML 重写层，节省可能抵消。 |
| Marked | token 与 renderer 适合约束较少的转换路径。当前需求仍需补源位置和语义规则，暂不列入对照。 |
| Comrak/WASM | 可作为解析阶段的候选。当前缺少解析为主瓶颈的证据，仍适用第 4 节的 WASM 启动条件。 |

只有 V2 后的实测能指出仍可删除的转换工作或生产依赖，才启动 [markdown-it 对照方案](markdown-renderer-comparison-plan.md)。对照结果用于决定是否另行规划迁移。

## 6. Future 讨论：双屏浮动预览

浮动预览仅用于将预览移到独立窗口，方便双屏编辑。浮窗生命周期依赖主窗口，主窗口退出时一并关闭。该条目仅记录讨论，不纳入当前实施路线或 V1、V2 的验收。

可考虑将浮窗作为现有预览的另一处展示位置，由主窗口继续管理会话、任务和缓存，浮窗消费同版本的 HTML、资源与源映射。Tauri 独立 WebView 窗口是候选，Web 端可另评估浏览器弹窗。分离与归位的阅读位置、焦点、滚动同步及大产物传输成本留待原型验证。具体窗口 API、权限配置、消息协议和资源交付方式暂不定案。

WASM 或 Rust 参与 Markdown 转换仍按第 4 节的实测条件评估。Rust 管理桌面窗口属于平台适配，可与现有 HTML 生成路径配合。

# 预览重渲染：预览何时刷新、刷新时看到什么（2026-11-06）

状态：**独立设计，未来版本的工作项**。当前版本不改渲染链，只保证渲染正确。

---

## 0. 决策摘要

| 决定 | 内容 |
| --- | --- |
| 定位 | 这份设计属于**未来版本**。当前版本的工作顺序是：大纲 → 渲染正确 → 文档资产；预览的刷新节奏不在当前版本里改 |
| 刷新时机 | **停手才渲染**（尾沿静默窗口），不做"每次击键渲染一次"，也不做"打字期间每 300ms 刷一次"的节流 |
| 屏上画面 | **双缓冲**：屏上永远是最后一次成功渲染的产物；新产物就绪后整体替换。**不清空、不加"更新中"标记** |
| 不合格产物 | 新产物带错误诊断（公式写了一半、代码块未闭合）时**不采用**，保留上一帧并给出提示 |
| 时延承诺 | 目标：从"系统判定输入结束"到预览就绪 ≤ 200ms。超出渲染预算的大文档按降级处理（保留旧画面），不承诺时延 |
| 落地顺序 | ① DOT→SVG 换成成熟 WASM 实现 → ② 调度层 + `startTransition` → ③ 产物改为结构化顶层块 |
| WASM 渲染器 | 暂不做。带触发条件：块级路线完成后大文档仍 > 200ms，或原生侧将来要自己产出 HTML/PDF |
| 范围 | 只管**预览**。大纲是同步派生的（`Sidebar.tsx` 的 `extractOutline` 在渲染期算），源码编辑区是同步的，两者都不在本设计内 |

## 1. 现场事实

### 1.1 当前行为（实测，Chromium / macOS / 构建后的 dist）

| 场景 | 出现留白的按键 | 单次留白 | 折合帧（60fps） | 键入到就绪 p50 |
| --- | --- | --- | --- | --- |
| 空文档，单字 | 8/15 | 53–79ms | 2–4 帧 | 75ms |
| 200 段文档，单字 | 7/15 | ~37ms | 3 帧 | 10ms |
| 800 行 / 17KB，单字 | 9/15 | 77–134ms | 3–7 帧 | 110ms |
| 空 / 200 段，连打 60ms 一字 | — | 7–42ms | **0 帧**（落在同一帧内，看不见） | — |
| 800 行，连打 80ms 一字 | — | ~75ms | **3–4 帧**（看得见） | 10 字共 1.09s |

三个由此得出的结论：

1. **留白不可忽略**：单次按键 37–134ms 是 2–7 帧；大文档连续输入时每个打字间隔里有 75ms 是空的，预览几乎全程空白。
2. **当前行为本身是竞态**：约一半的按键从未把 `pending` 提交到 DOM（React 提交 pending 之前，worker 的 ready 已到，pending 被丢弃）。那一半里旧内容留在屏上。所以现状是"**有时旧内容、有时空白**"，取决于 worker 响应与 React 提交的赛跑——不是确定行为。
3. **渲染成本被逐键放大**：连续输入 10 个字让 worker 跑了 10 次渲染，9 次的结果直接作废。

### 1.2 渲染管线：重活已经外包

`src/core/render/documentRenderer.ts` 的实际管线：

```
markdown
 → MathJax 3.2.2 排版全文所有公式
 → remark AST → remark-rehype → rehype-raw → rehype-stringify
 → root.innerHTML = parsed.html        ← HTML 字符串第 1 次被解析成 DOM
 → mermaid / graphviz 逐图渲染
 → DOMPurify 全量清洗 → uniqueSvgIds 遍历全文
 → root.innerHTML 回传字符串
 → worker 往返（产物 + sourceMap 结构化克隆）
 → 主线程 dangerouslySetInnerHTML      ← HTML 字符串第 2 次被解析成 DOM
```

自研渲染代码 833 行（`src/core/render/*.ts`），其中 **289 行是 DOT → SVG 渲染器**——一个"纯前端离线"的 Graphviz 替代品。其余自研（源映射注入、作者 HTML 授权策略、诊断、产物校验、身份与缓存键、worker 编排）是**产品语义**，不是渲染。

### 1.3 解析不是瓶颈

材料给出的纯解析基准：marked 约 3ms / 1 万字，Rust/WASM 约 2ms / 100KB。实测 R（渲染往返）是 37–75ms。**解析只占其中一小块**，大头是 MathJax 全量排版、两次 HTML→DOM 解析、全量 DOMPurify 清洗与 SVG id 遍历。

⇒ 换更快的解析器买不到 200ms；能买到的是"调度 + 粒度"。

## 2. 目标与非目标

**目标**

- 停手才渲染；打字期间预览不重排（注意力在编辑器上）。
- 屏上永远有一帧完整画面：不清空、不闪烁、不加标记。
- 写了一半的公式、没闭合的代码块不污染预览。
- 刷新成本与**改动量**成正比，而不是与文档长度成正比。

**非目标**

- 不追求"每一毫秒都最新"。预览允许落后，落后量有上限。
- 不引入"正在更新"这类可见状态。（用户明确不要。）
- 不做逐块增量渲染的完整实现前，不声称成本已与文档长度脱钩。
- 不改 HTML 兼容基线、不改导出链。

## 3. 契约

### 3.1 屏上画面（双缓冲）

1. 预览显示的是**最后一次成功渲染的产物**。渲染进行中不清空、不替换。
2. 新产物就绪后**整体替换**（不是逐块打补丁）。
3. 新产物带错误诊断 ⇒ **不采用**，保留上一帧并给出提示。
4. 例外（允许清空）：**换文档**（旧产物属于别的文档）；**首次渲染**；预览面板不可用。

### 3.2 触发

| 事件类别 | 例子 | 何时渲染 |
| --- | --- | --- |
| **内容变更** | 键盘输入、粘贴/剪切、撤销/重做、工具栏插入、外部替换 | 静默窗口结束后 |
| **渲染条件变更** | 换文档、切 flow/A4、主题/选项变更 | 立即，不等静默窗口 |

### 3.3 输入结束的判定

- **定义**：最后一个内容变更事件之后，连续 **T** 内没有新的内容变更 ⇒ 输入结束 ⇒ 启动渲染。
- **T = 300ms 量级**（可调参数）。依据是人类节奏：快打约 200–300ms/键、词间 300–500ms；T 必须落在这个量级才能分辨"击键"与"停顿"，否则快打时每个键都会触发一次渲染。
- **IME 组合输入**：编辑器在组合期间跳过 `onChange`（`src/components/editor/Editor.tsx` 的 `composing.current` 判断），只有 `compositionend` 才提交一次变更 ⇒ "输入结束"天然落在组合提交之后，无需额外规则。
- **时钟**：用单调时钟。切后台或休眠会让定时器迟到——回来时按真实时间算，输入早已结束 ⇒ 直接渲染。

### 3.4 时延与降级

- 目标：从**系统判定输入结束**到预览就绪 ≤ 200ms。
- 分解：静默等待 T（300ms 量级）+ 渲染 R（预算 100ms 量级）。R 随文档长度增长，因此 200ms 只对**渲染成本在预算内**的文档成立。
- 超预算时**降级**：保留旧画面（不闪烁、不标记），不阻塞输入；实际时延记录下来作为证据。
- 与"从最后一次击键起算"的口径分开写：击键到就绪的实际值 ≈ T + R ≈ 375ms 量级，不承诺 200ms。

### 3.5 与滚动同步的关系

预览显示旧产物期间，它的滚动位置属于**旧内容**。此时按行号做跨面板同步，就是拿旧内容的行去对编辑器的新内容。

⇒ **落后窗口内，两个方向的跨面板同步都暂停**；新产物就绪后按**行**重新落位（现有 `pendingPreviewLine` / `restorePreview` 已是按行的）。

## 4. 实现路径

| 步 | 内容 | 性质 | 退出依据 |
| --- | --- | --- | --- |
| **a** | DOT → SVG 换成 `@hpcc-js/wasm-graphviz`（已核实存在，1.30.0） | 纯减负：删 289 行自研，换真正的 Graphviz 布局 | 现有 DOT 渲染的端到端断言全绿；SVG 自包含与 id 唯一化仍成立（`uniqueSvgIds`） |
| **b** | 调度层 + `startTransition` | 消掉逐键渲染；双缓冲交给 React | 打字期间不再产生渲染任务；产物到达后经 transition 提交，过期帧被 React 丢弃；屏上无空白帧 |
| **c** | 产物从 HTML 字符串改为**结构化顶层块** | 块级增量的前提；顺带少一次 HTML→DOM 往返 | 只重渲被改的块；MathJax 只排被改的公式；渲染成本与改动量成正比 |

### 4.1 为什么 b 用 `startTransition`

`startTransition` 标记的更新是非紧急的：React 可以中断它去优先响应击键，准备好再整体换上。这正是双缓冲在 React 层的实现——**不需要我们自己发明"保留旧帧"的机制**，也不需要"渲染中清空再填"的状态分支。

### 4.2 为什么 c 是"结构化块"而不是"块级 diff"

产物若是 HTML 字符串，主线程要拿到块边界只能再解析一次字符串。worker 手上有 hast（`rehype` 之后的树），顶层子节点天然就是块（与 Typora 的块级一致），每块带上 `data-line` 区间做稳定键 ⇒ 主线程按块 `React.memo` 渲染，只有被改的块重渲。源映射、作者 HTML 授权、诊断这些作用在**节点**上而不是字符串上，比现在干净。

## 5. WASM 渲染器：暂不做，带触发条件

WASM 对墨流的真正价值不是"更快"，而是**一份实现、两个运行时**（前端预览 + 原生侧导出共用）。但今天原生侧不渲染 markdown（`src-tauri` 里只有 `files.rs` 与哈希），这个收益是将来的。

不做的另一个理由：换解析器要重写全部产品语义（源映射注入、作者 HTML 授权、分页符、任务列表、图表占位），而收益只是 R 的 10ms 量级；且若与调度/块级同时改，出了问题无法归因。

**触发条件**（满足其一才启动）：

1. c 完成之后，大文档的 R 仍 > 200ms；
2. 原生侧将来要自己产出 HTML/PDF（那时一份 Rust 实现两处用，价值立刻成立）。

届时形态：**不是"换 comrak"**，而是用 pulldown-cmark / comrak + latex2mathml + ammonia 等 Rust 组件自建一个 crate，把产品语义在 Rust 侧实现一次，编译成 WASM。

## 6. 验收（未来版本）

| 编号 | 断言 |
| --- | --- |
| P-1 | 一次连续输入（≥10 键）只产生一次渲染任务；worker 渲染次数与击键数解耦 |
| P-2 | 打字期间预览的屏上画面不变化（无空白帧、无替换帧） |
| P-3 | 停手后，屏上画面在目标时延内整体换成新产物；期间无中间态 |
| P-4 | 新产物带错误诊断时，屏上保留上一帧，并出现提示；产物修复后正常换上 |
| P-5 | 换文档时屏上清空并显示新文档的预览（不显示上一个文档的内容） |
| P-6 | 落后窗口内两个方向的跨面板同步都不动作；新产物就绪后按行落位 |
| P-7 | 组合输入（IME）期间不触发渲染；组合结束后按静默窗口触发一次 |
| P-8 | 渲染条件变更（切 flow/A4、主题变更）立即触发，不等静默窗口 |
| P-9 | 大文档超出渲染预算时：屏上保留旧画面，输入不卡，渲染任务不堆积 |

---

## 7. 不做

- 不做"正在更新"标记或任何可见的刷新状态。
- 不做逐块增量渲染的完整实现前，不承诺渲染成本与文档长度脱钩。
- 不改 HTML 兼容基线、不改导出链、不改 MathJax 版本。
- 不做公式排版器的替换评估（KaTeX / Rust mathml 会改产物基线）。

## 8. 业界依据

| 来源 | 事实 | 对我们的意义 |
| --- | --- | --- |
| VS Code `extensions/markdown-language-features/src/preview/preview.ts` | `readonly #delay = 300`；注释写 "debounced"，但计时器不重置 ⇒ 实际是**节流**：打字期间每 300ms 重排一次预览 | 量级（300ms 是人类节奏）可借，语义（打字时也刷）不可借——那正是"公式写到一半被重排"的来源 |
| [VS Code #344635](https://github.com/microsoft/vscode/issues/344635) | markdown 编辑器输入延迟随文档增长，原因是**每次击键全量重解析与重测量** | "一次键盘一次渲染"是行业记着的缺陷 |
| [VS Code #131315](https://github.com/microsoft/vscode/issues/131315)、[#65504](https://github.com/microsoft/vscode/issues/65504) | 预览在打字时刷新会把编辑器滚动位置带跑 | 与 `tauri-migration-plan-2026-10-29.md` §4.5 的滚动契约同类；"打字时不渲染"直接消除这个触发源 |
| [Zettlr PR #5755](https://github.com/Zettlr/Zettlr/pull/5755) | Prevent image reloading on every keystroke using debounce | 去抖是行业用来止住逐键工作的常规手段 |
| Streamdown / brookmd | 块级记忆化 + 稳定键 + `startTransition`；只重渲最后一个变化的块 | 粒度层与双缓冲的实现范式（c、b） |
| Typora | 块级渲染：正在编辑的那块重排，其余不动 | "写到一半的公式不污染整篇"在文档级下的最近替代是 §3.1 第 3 条 |
| marked / comrak 基准 | marked ≈ 3ms/1 万字；Rust/WASM ≈ 2ms/100KB；WASM 在极小输入或极频繁调用下跨界开销会吃掉优势 | 解析不是我们的瓶颈（§1.3）；换解析器收益小、代价大 |

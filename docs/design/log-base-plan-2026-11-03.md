# 日志基座设计（L1/L2）

日期：2026-11-03。基线：architecture-refactor / `2754167`。状态：**设计已定，尚未实施**。

本文定义 MarkFlow 的日志基座：Rust 侧的文件 sink（L1）、web→Rust 的回传通道（L2），以及由它支撑的**证据形态**（怎么记、怎么取信、怎么被机器校验）。

本文是**跨阶段的基础设施**，不是某个探针的附属：D1b 的取证、D1c 的打印宿主诊断、D8 的生产接入与可监测性都用它。探针方案只引用本文，不重复定义。

## 1. 动因

1. **交付宿主上看不见**：Windows 的 GUI 应用没有控制台，stdout 在生产环境直接丢弃。
2. **崩溃时 stdout 会丢尾巴**：管道有缓冲，而崩溃正是最需要日志的时候。
3. **证据要能像固化样本那样归档**：文件才是原物，终端输出是转述；转述会丢、会抄错、说不清当时到底看到了什么。
4. **失败定位的往返成本**：2026-11-03 交付宿主复跑时，探针失败只有几行 `println!`，无法判断是源不可达、初载未落地还是导航被取消，只能"加临时打印再跑一遍"——一次往返要 push + pull + build + run。日志落地后，这类判定不再依赖往返。

| 项 | 内容 |

## 3. L1 Rust 日志基座

| 项 | 决定 |
| --- | --- |
| 框架 | `tracing` 做门面、`tracing-subscriber` 做输出（`default-features = false`，开 `fmt`/`ansi`/`std`/`json`）。不引 `env-filter`（正则）与 `tracing-log` 桥 |
| 过滤 | `MARKFLOW_LOG` 解析全局级别；默认 debug 构建 INFO、release 构建 WARN |
| 形态 | 人读一行式为主（时间 级别 目标 字段=值）；`MARKFLOW_LOG_FORMAT=json` 切 JSON 行 |
| 主 sink | **文件**：`app_log_dir()/markflow.log`。**size 与 day 双约束轮转**（单文件 8 MiB 或跨日即轮转），归档 `markflow.log.YYYY-MM-DD.NNN`，只保留最新 10 份 |
| 次 sink | stdout（tee）。开发期的快反馈回路 |
| 写入 | 专用写线程 + 有界队列；队列满则丢行并计数。**UI 线程不得被日志阻塞** |
| 运行标记 | 每次进程启动写一行 `event=run_start run_id=… os=… arch=… app_version=… feature=…`。轮转后一个文件含多次运行，靠它圈出本次 |
| 凭据策略 | 开发构建输出完整 key，该行标 `secret=true`；**发布构建不输出完整 key**（编译期门控，非运行时开关）。日志不含文档内容与文件路径 |

## 4. L2 web→Rust 日志回传

| 项 | 决定 |
| --- | --- |
| 通道 | 新增 `log_event` 命令，web 侧事件经它进入同一套日志 |
| 边界 | **该命令只写日志，不铸任何授权**：D1b 的"无命令能铸造授权"这条实质性质不变。逐字意义上的"`invoke_handler` 不变"在此放宽为一个例外 |
| 防伪造 | **每条事件按发生地判定可信来源**：native 侧事件只认 `origin=rust`，web 侧事件只认 `origin=web`。两侧都写不出对方形状的事件——web 消息只进**不透明字符串字段**，绝不映射成 `event=` 这类结构化字段；Rust 侧事件也不写成 web 的形状 |
| 限流 | 单条长度上限 + 按窗口限频；超出丢弃并计数 |
| 身份 | web 行带调用方身份对，由 Rust 侧归属 |
| 页面侧留痕 | 探针页把步骤日志写进 DOM，并经 `log_event` 回传。浏览器控制台在交付宿主上看不见，DOM 与回传是页面侧叙事的唯一出口 |

## 5. 证据形态与取信规则

**证据 = 日志文件**：归档至 `docs/acceptance/pdf-probe/`，记录原始文件的 SHA-256。JSON 形态下断言由机器校验。

**按发生地分侧**：许多事件本来就发生在 web 侧（页面是否加载、页面发起了哪几次调用、页面侧有无异常），这些只有 web 侧知道，故 **web 侧事件是其领域的权威记述**，不是旁证。判定规则是：native 侧断言查 `origin=rust` 的行，web 侧断言查 `origin=web` 的行。

**两侧一致性是防伪造的真正着力点**：同一次调用在两侧各留一份记述——native 侧记守卫判定与拒绝码，web 侧记自己发起了什么调用、收到了什么结果——校验器比对二者是否相符。任何一侧伪造或谎报，都过不了这一关。这比"只信一侧"更强，因为它把两侧都变成了对方的对照。

**须分清的一种混淆**：native 侧把页面报告读回后转成的事件，是 **native 侧对页面结果的读数**，不是页面自己的记述；两者分别落在 `origin=rust` 与 `origin=web`，不可混为一谈，否则"两侧对照"就变成自己对自己。

**归档含完整 key 的开发日志为何安全**：能力是进程内的（`FileAccess` 是内存 `HashMap`），铸出 key 的进程退出即失效，**日志里的 key 在归档时必已是死的**。故归档原始日志即可，不剔除 `secret=true` 行，开发期不增加步骤。

## 6. 执行约定

| 约定 | 内容 | 理由 |
| --- | --- | --- |
| C 日志基座与证据形态 | 日志以**文件为主 sink**（size 与 day 双约束轮转），stdout 为次 sink；证据取自日志文件，JSON 形态下机器校验，按**发生地分侧**取信并比对两侧一致性 | Windows GUI 应用无控制台，stdout 会丢；证据要能像固化样本那样作为文件归档、哈希与复算 |
| D IPC 例外的边界 | `log_event` **只写日志，不铸任何授权**；web 消息只进不透明字符串字段，不得映射成结构化事件字段；带长度上限与限频；每条事件按发生地判定可信来源，两侧记述须相符 | 逐字意义的"`invoke_handler` 不变"要让位于可观测性，但"无命令能铸造授权"这条实质性质必须保住。web 侧事件是其领域的权威记述，不能降级为旁证；而两侧互为对照，才是伪造过不去的地方 |

## 7. 三处取舍留档

1. **落点选文件而非 stdout**：Windows 的 GUI 应用没有控制台，stdout 在生产环境直接丢失；且 stdout 经管道时崩溃会丢尾巴，而崩溃正是最需要日志的时候。更关键的是，**日志文件才能像固化样本那样作为文件归档、哈希与复算**——终端输出是转述，文件是原物。
2. **轮转按 size 与 day 双约束**：单按日，一天的日志可能很大；单按 size，跨日不会切分，时间归属丢失。双约束 + 保留最新 10 份是常见做法；实现自带写入线程，故不必引 `tracing-appender`（它只支持按时间轮转，且会带 `crossbeam-channel`/`parking_lot`/`time`）。
3. **开发构建输出完整 key、发布构建不输出**：按编译期门控（`debug_assertions`）而非运行时开关，生产保证不会被误开；输出时标 `secret=true` 使敏感行可辨。归档含 key 的开发日志是安全的（见 §5），故不必为归档增加剔除步骤，开发期也不增加复杂度。

## 8. 退出条件

- **L1**：守卫判定与副作用、身份回报、宿主诊断均有日志行；全局级别可调；人读与 JSON 双形态可用；写入走非阻塞路径且丢弃可计数；轮转与归档清理生效。
- **L2**：web 侧事件进入同一套日志；web 消息写不出可被读成 native 事件的行；长度与频率有上限且丢弃可计数；web 行带调用方身份对。
- **证据形态**：断言能从日志行机器校验；native 侧断言只取 `origin=rust`、web 侧断言只取 `origin=web`；两侧一致性作为独立断言存在。

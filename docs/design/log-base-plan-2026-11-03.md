本文定义 MarkFlow 的日志基座：Rust 侧的文件 sink（L1）、web→Rust 的回传通道（L2），以及由它支撑的**证据形态**（怎么记、怎么取信、怎么被机器校验）。

术语：本应用以Tauri为桌面宿主，Web应用层与Rust原生层共同构成同一个应用，不采用远端客户端—服务端模型。`origin=web` / `origin=rust`仅区分应用内记录来源和观察位置，不表示Web应用层不是应用端。应用内正常日志均用于诊断；涉及原生权限、副作用或隔离验收时，仍需区分页面报告与原生直接观察，不因同属一个应用就互相替代。

本文是**跨阶段的基础设施**，不是某个探针的附属：D1b 的取证、D1c 的打印宿主诊断、D8 的生产接入与可监测性都用它。探针方案只引用本文，不重复定义。

## 1. 动因

1. **交付宿主上看不见**：Windows 的 GUI 应用没有控制台，stdout 在生产环境直接丢弃。
2. **崩溃时 stdout 会丢尾巴**：管道有缓冲，而崩溃正是最需要日志的时候。
3. **证据要能像固化样本那样归档**：文件才是原物，终端输出是转述；转述会丢、会抄错、说不清当时到底看到了什么。
4. **失败定位的往返成本**：2026-11-03 交付宿主复跑时，探针失败只有几行 `println!`，无法判断是源不可达、初载未落地还是导航被取消，只能"加临时打印再跑一遍"——一次往返要 push + pull + build + run。日志落地用于减少这类往返，但不能保证每种故障均有足够证据。

### 3.1 故障、退出与丢失边界

- 日志初始化先于业务事件。目录不可创建/打开时，应用继续运行；内存健康状态记为不可用，不将日志故障转为业务失败，不递归写日志。写入/轮转失败暂停文件sink并记录首个错误类别及计数，本次进程不做重试框架；仅在 log.stdout=true 时尝试 stdout 镜像，文件不可用不改变此开关。
- 文件 sink 与 stdout 分别处理返回错误。stdout 返回错误后本进程停用镜像，标记 stdout_failed，仅此不否定文件证据。启用镜像时两者仍使用同一写线程，stdout 同步阻塞可能拖延后续文件记录并导致队列丢弃。关闭时普通日志和健康摘要均跳过 stdout。
- 写线程至少每秒刷新用户态缓冲，WARN/ERROR写入后刷新；正常退出请求排空并刷新，最多等待2秒。超时放弃等待，不阻塞应用退出；不每条执行磁盘同步，不承诺强杀、崩溃、断电或磁盘故障时尾部可靠保存。
- 队列丢弃、限流、格式拒收、sink故障分别计数于进程内有界状态；健康输出可用时按限频摘要输出，不对每次丢弃递归产生日志。普通发布态通过轻量的「日志与诊断」入口查看有效目录、文件可用性及最近一次故障类别，并能打开目录或导出所选日志文件。文件不可用时提供同一入口可回看的简短状态。原生受控验收读取同一份健康状态。路径只作为本机诊断展示，不写日志载荷。该入口按主窗口来源授权，日志导出沿用现有文件交付端口。
- 计数和健康状态同样不保证跨崩溃保留；缺失结束标记或存在丢弃/写入错误时，不宣称日志完整。

### 3.2 轮转与保留

**目标契约，部分待实施。** 当前代码已有 8 MiB/UTC 跨日轮转，但仍按 KEEP_ARCHIVES=10 裁剪归档，尚无 14 天清理。LS3 实施后以以下规则取代数量裁剪；旧的 80 MiB 总量预算方案取消，不作为待实现要求。

- 日界和时间戳统一 UTC。跨日，或下一条完整记录会使当前文件超过 8 MiB，先轮转再写；空文件不反复轮转，单条记录仍受现有限额约束。
- 启动时检查已有活动文件，按最后修改时间的 UTC 日期和实际大小决定是否先轮转；归档日期取旧文件所属日期。归档序号继续按日期分配，不覆盖既有内容。
- `log.retention_days` 默认 14，按最后修改时间距本次清理时刻达到 14 × 24 小时判定过期；使用 UTC 时间。保留期决定何时可删除，不是轮转间隔。
- 启动、轮转、正常退出时清理本模块精确命名且能确认已结束运行的文件，包括归档和遗留 `.log`。当前及其他活跃实例文件不能删除，无法确认的跳过；不误删其他文件。PID 复用不能只凭名称当成已结束实例。
- 取消归档数量和目录总字节上限；保留期内可以超过 10 份及 80 MiB。实际占用取决于日志量；不承诺总空间硬上限。
- 过期删除是触发时尽力执行，应用未运行时不主动清理。文件占用或删除失败记录健康故障及实际未清理状态，不声称过期文件已全部移除。不新增常驻清理线程或重试平台。

### 4.2 生产调用关联与通道健康收口（2026-11-11，已接线，系统验收待补）

工作台首次就绪发 page_ready。受保护命令的统一调用入口为一次调用生成 call_id，开始与完成事件采用同一次解析得到的消息端口。call_id 随真实业务命令传入 Rust，由命令入口校验格式和长度，只有有效值写入 command span；缺失或非法值均不阻止业务，不改变来源守卫、文件授权和真实返回结果。非法值不落日志、不作为授权依据，可记录固定脱敏诊断；校验器将对应调用列为未关联。有有效调用关联的页面事件使用 page_call span；无关联 page_ready 和全局 page_error 使用 run 根 span，不伪造 call_id。日志通道仍可拒收带非法 ID 的载荷，此回执只影响上报，不影响业务命令。关联键为 run_id、Rust 注入的窗口/WebView 身份、call_id，并校验命令枚举一致。call_id 是关联字段，不能参与授权判定。一次调用即使业务失败或被拒绝，也报告页面侧完成结果。选择器取消沿用原生成功返回的 ok 口径，不将取消记为失败。调用被中断造成的缺失要留作不完整证据。

页面完成结果表达页面观察到的 Promise 结果，Rust operation_result 表达原生执行结果。页面适配器的结果解析失败可能晚于原生成功，校验器应保留两者差异供诊断。平台信息、配置和 log_event 自身不产生受保护命令调用事件，避免递归。开始/完成每次增加两条事件，现有限流可能导致丢弃，验收记录实际接受率及丢弃计数。

消息端口消费 accepted、dropped、rejected 及调用异常，按现有通道健康约定保留一份有界最后状态，Rust 继续维护拒绝/丢弃及文件写入健康。accepted 仅代表入队。业务执行不依赖日志接收成功，统一适配器独立发送日志，业务调用和用户反馈均不等待上报。每次调用的开始与完成按顺序尝试发送，每次接收等待最多 log.call_timeout_ms，默认 200 ms；首次读取等待配置也以 200 ms 为上限，失败使用默认等待值。超时结束页面侧等待并记录最后状态，随后可尝试完成事件。超时不能取消底层 IPC，迟到结果仅供诊断，不能改业务结果。日志不重试、不递归，不为通道不返回增加无限积压的全局队列。

## 5. 证据形态与取信规则

**日志是如实记录，不是防伪造机制。** 它保证的是「按观察到的内容记录」——记录者写下的，是它**观察到**的东西；它不保证记录为真，也不提供防篡改保证。取证时读到的每一条，都是「某侧在某时观察到了某事」，不是「某事确实如此」。

**观测单位是 span**：一条孤立的事件说明不了什么，一次调用（守卫判定、对话框、读写、撤销）才是有意义的单位。故每次调用开一个 span，调用内的事件挂在该 span 上，span 携带起止与耗时；本次运行是所有 span 的根。**不设全局序号**：区分记录靠时间戳与 span 上下文，同一时间戳涌入多个事件是正常现象，要防的是同一事件被重复输出。序号在别的系统里用于游标（journald）、跨批次排序去重（Vector/Fluentd）或跨进程串联（OpenTelemetry），本应用三者都不需要：顺序由单写线程的 FIFO 决定，完整性由丢弃计数与 `log_health` 承担，跨侧关联由 `call_id` 与 span 上下文承担。

**来源与事实分开**：origin=rust仅指Rust记录者，仍须看事件语义。守卫实际判定、文件副作用、原生宿主创建等由Rust直接观察；Rust读取DOM报告记为 `page_report_observed`，其内容仍是页面自述，不转为“原生证实页面事件”。origin=web统一是Web应用层报告，Rust只证明收到该身份的声明。日志不是防篡改审计系统，哈希用于固定归档输入，不证明事件真实性。

**两侧对照**用于定位某次调用的两份记述是否一致：一致是常态，不一致就是线索。它不证明所有事件均发生或完整。原生结果以同请求的Rust观测为准；Web侧的成功声明不能覆盖原生的拒绝或缺证。实际IPC结果及拒绝归因继续遵守探针方案的正向证据规则。

### 5.1 span 模型（两级）

**观测单位是 span**：一条孤立的事件说明不了什么，一次调用（守卫判定、对话框、读写、撤销）才是有意义的单位。每次调用开一个 span，调用内的事件挂在该 span 上；本次运行是所有 span 的**根**。

**层级只有两级**，且所有调用 span 都是根 span 的**直接子**。探针装配、宿主创建、各次调用互为兄弟，不因"因果"再嵌一层——否则正常会话里的调用与探针里的调用形状不同，读日志的规则就要分叉。

**span 上放这次调用的标识与参数，事件上放这次调用的结果与结论**：读日志时先看 span（这是什么操作），再看事件（发生了什么）。span 词汇表是固定的，不开放任意结构：

| span 名     | 谁开             | span 上的字段                                               | span 内的事件                                                                      | 事件字段                                                                                                       |
| ----------- | ---------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `run`       | 进程启动         | run_id, os, arch, app_version, feature                      | `run_start` / `run_end` / 无关联 `page_ready`、全局 `page_error`                   | —                                                                                                              |

两条补充约束（实施时查出，写进契约免得再犯）：

- **关联字段必须进入最终记录**。统一 Rust 发送口把允许的 call_id、command、window_label、webview_label 复制到相关 command 事件字段，页面事件使用相同关联键。校验最终 JSON，而非仅检查 span 声明。历史实现中 span 字段尚不进记录。记录只带 span 名、id 与父 id，故 `run` span 上的 os／arch／app_version／feature 必须在 `run_start` 事件上重复一次——校验器要按 §5.3 记构建、feature 与环境，这些字段得真的在日志里。**配置的来源与有效级别、有效形态同样如此** ✓（2026-11-05 补 ✓）：它们是"这轮跑的是哪份配置"的证据 ✓，只在日志里留一份配置文件不算数 ✓。 **构建标识同样如此** ✓（2026-11-10 补 ✓）：`build_commit` 与 `build_time` 随运行标记落笔 ✓ ⇒ ⇒ **日志能说出是哪个构建** ✓ ⇒ ⇒ 不用问人那个包是不是新的 ✓ ⇒ ⇒ 也不用靠时间戳猜 ✓。
- **每个 command span 都要有 `operation_result`**。拒绝路径没有命令体，由 span 层补一条 `result=denied` 与 `reason_code`；授权解析失败等早退路径同样要记。否则"原生看见了失败却没落笔"，跨侧对照就成了单边叙述。

**`operation_result` 上那两个布尔是什么**（2026-11-04 补记 ✓）：

- `committed` ✓：**目标真的提交了吗** ✓。它是"提交成功才 saved"的**证据** ✓——
  没有它 ✓，那条承诺只能靠页面自述 ✓，而页面自述证明不了 ✓。
- `pdf_temp_removed` ✓：**产物的临时文件清掉了没有** ✓。它是"超时 → 删除"的**证据** ✓——
  删不掉是有可能的 ✓（Windows 上文件被占着 ✓），而没有它就证明不了 ✓。

两者都是布尔 ✓（§5.2 的字段策略允许 ✓），都**必须实测** ✓：
断言出来的字段不是证据 ✓，是谎报的前身 ✓。

**健康计数按原因记录。** page 入口分别维护 web_rate_limited、web_rejected，日志发送口分别维护 queue_dropped、record_too_long。文件维护 write_failures、rotate_failures、delete_failures 及 file_unavailable，stdout 单独记录 stdout_failed。四类丢弃与拒收计数不相互累加。升级校验器时兼容旧 dropped/rejected，但旧合计仅能说明存在缺口，不能定位原因。新日志中未知页面类别计入 web_rejected，不回显不受控类别。

两条实现约束（都会咬人，写在这里免得实现时再撞）：

- **异步命令用 `Instrument` 附着 span，不用 `enter()` 守卫跨 await**。守卫是 `!Send`，跨 `.await` 持有会让 future 不再是 `Send`，Tauri 命令直接编译不过；即便绕过去，跨线程后"当前 span"也是错的。
- **span 的耗时不会自动记录**。`tracing` 的 formatter 只输出 span 名与 id，不输出起止与耗时，故耗时由结束事件带 `elapsed_ms` 字段。

**span 实例数**：单次运行的实例数约 20（run 1 + probe 1 + host 1 + 受保护命令 span 约 8 + 页面调用 span 约 8 + log 1）。这是**单次运行**的量级，不是全局上限——正常会话里受保护命令的调用次数无界。

### 5.2 最小记录契约

- **机器验收以 JSONL 为准**；人读格式同样可被校验器解析——两者由**同一个写出器**从同一批记录生成，字段与脱敏规则相同，不是人工转述。**修订（2026-11-03）**：原条款是"人读格式只供诊断，不解析其文字作机器证据"，理由是怕把转述当证据；实测该顾虑不成立（人读形态由写出器生成，不是人抄的），而交付宿主上因为漏设 `MARKFLOW_LOG_FORMAT=json` 产出的正是人读形态，硬性拒绝它等于作废已取得的证据。故改为两形态皆可解析，人读形态的值含空格时按"续写上一个字段"还原。归档仍以 JSONL 为准。**2026-11-05 补记** ✓：形态不再由环境变量决定 ✓，改由配置文件 `log.format` 决定 ✓ —— 那一类"漏设 → 证据作废"的事故从此不会发生 ✓（配置就在仓库里 ✓，看得见 ✓）。
- 每条必填 `schema_version=1`、`run_id`（Rust每次启动生成，即本次运行的根 span）、`timestamp`（Rust记录UTC时间）、`level`、`origin`、`event`，以及**所在 span 的上下文**（span 名、span id、父 span）。span 的划分与字段按 §5.1 的词汇表。**不设全局序号**：区分记录靠时间戳与 span 上下文，同一时间戳涌入多个事件是正常现象；真正要防的是**同一事件被重复输出**。Web外层事件固定 `web_event`，附原生取出的 `window_label` / `webview_label`；业务事件在受校验的 `page_event` 字段内，不能变成原生事件名。
- 最小稳定原生事件：`run_start`、`run_end`、`source_decision`、`operation_result`、`host_state`、`page_report_observed`、`log_health`；Web事件枚举先限 `page_ready`、`call_started`、`call_finished`、`page_error`。具体阶段只能按需增加枚举，不开放任意结构化字段。
- **观测单位是 span，不是单条记录**：一次调用开一个 span，调用内的守卫判定与操作结果是该 span 内的事件，span 携带起止与耗时。原生侧每个受保护命令一个 span（`command` 为 span 名）；Web侧每次调用一个 page_call span，call_id 用于查找该 span，与 tracing 内部 span id 分别记录。调用类记录带不具授权能力的 `call_id`、命令枚举、结果枚举；原生守卫记录allow/deny及稳定原因码。Web应用层调用ID只用于关联，不是身份或权限；Rust限制其长度和字符集，绑定run_id、原生身份、命令。生产页面正常生成并传递唯一 ID；Rust 对缺失或非法 ID 均按无关联执行，非法值不回显，校验器列为未关联，不得据此判定链路已贯通。关联字段不改变业务返回值和权限。未落实同请求贯通时，不能只按时间近似配对后宣称调用已对应。
- 其他字段只允许固定枚举、计数、布尔值或有界诊断ID；`page_error`只传错误类别与**一个有界的定位串**，不传原始异常message。**定位串**是页面上那个问题出在哪儿（异常的类型 + 我们自己构建产物里的文件与行）✓ ⇒ ⇒ **不含用户数据** ✓ ⇒ ⇒ **日志因此能指出是哪儿** ✓ ⇒ ⇒ 下一次同样的事看日志就够 ✓ ⇒ ⇒ 不必再开控制台找那一行 ✓。**"在我们自己的构建产物里"是约束，不是假设** ✓ ⇒ ⇒ 只认 http(s) 的帧 ✓ ⇒ ⇒ 别的来源的帧（`file://` 的用户路径 ✓）一律不取 ✓ ⇒ ⇒ 实在没有我们的帧就说**没有帧** ✓ ⇒ ⇒ `异常名@no-frame` ✓ ⇒ ⇒ 不用用户路径凑数 ✓ ⇒ ⇒ **与"不是异常"分得清** ✓ ⇒ ⇒ 不是异常 ⇒ ⇒ `rejection:字符串／对象／空` 一类 ✓ ⇒ ⇒ 只说种类、不说内容 ✓ ⇒ ⇒ 看日志就知道问题在哪一侧 ✓。**页面报出它自己的构建** ✓ ⇒ ⇒ 载荷多一个 `build` ✓（那个页面的 commit ✓）⇒ ⇒ 原生侧记成 `page_build` ✓ ⇒ ⇒ 与运行标记里的 `build_commit` 一比 ⇒ ⇒ **页面与原生侧是不是同一个构建** ⇒ ⇒ 日志直接答 ✓ ⇒ ⇒ 不用问人 ✓ ⇒ ⇒ **有界** ✓ ⇒ ⇒ 那一条不会变长 ✓。**每条记录都带 `at`** ✓：**我们代码里的文件与行** ✓ ⇒ ⇒ 日志能指出**在我们代码的哪一处** ✓ ⇒ ⇒ **位置由发射点自己带** ✓ ⇒ ⇒ 不用给每个调用点手写 ✓ ⇒ ⇒ **页面不能伪造** ✓ ⇒ ⇒ **只认我们自己的源文件** ✓ ⇒ ⇒ 不是用户的路径 ✓ ⇒ ⇒ 空格换下划线 ✓ ⇒ ⇒ 那一条始终是一行 ✓。日志入口和底层sink均不输出原始授权key，不以secret=true作为泄露许可。字段白名单的作用是**记录的内容受控**，不承担防伪职责。

### 5.3 校验与归档

- 校验器记录run_id、原始日志文件集合及SHA-256、构建/feature和环境；跨轮转时收集本次运行所需全部文件（按运行分文件后，同一运行的日志通常只在一份文件里，但轮转会把它分成多份）。缺run_start、未知schema、JSON损坏、所需事件缺失/重复或关联不匹配，相关断言记未能确认，不自动补齐。
- 同一 span 内同名事件重复出现即视为重复输出，须报告；跨侧按 call_id 与 span 上下文配对，允许Web异步迟到。身份/命令冲突及结果不一致均须报告；无对应Rust观察的Web声明不能证明原生成功。只对该验收所需事件设完整性条件，不要求全部业务事件两侧双写。
- 验收取证运行须显式启用覆盖所需事件的级别与JSON格式；默认发布 INFO 提供操作上下文；用户显式过滤到 WARN/OFF 时，按有效过滤记录证据缺口。缺少过滤掉的事件仍属证据不足，不能认作未发生。
- 日志不含文档正文、完整本地路径或任何授权凭据，包括查询串、异常与DOM报告的间接泄露。关联使用单独ID，不使用key片段作为常规关联办法。已有探针URL/cleanup打印原始key的路径须在接入基座时同步迁移，不能tee后继续泄露。

**校验器的实现**：`scripts/pdf-probe-check.ts`（`bun scripts/pdf-probe-check.ts <日志文件或目录...> [--run <run_id>] [--json]`）。**两种形态都读**（JSONL 与人读文本），并在报告里标出每个文件是哪种形态。它做两件事：

1. 按探针方案 §5.3 的证据矩阵逐条判定 D1b-1—D1b-6，三态结论（通过／未通过／未能确认），每条都写明判定依据及其来源（native 观察／web 观察／页面自述）。退出码：0 全部通过，1 有未通过或有错误级诊断，2 有未能确认。
2. 做**契约体检**（诊断项，不混进断言）：重复输出、调用 span 是否都是根的直接子、事件是否落在契约规定的 span 内、跨侧结果不一致、两侧记录数量不匹配、web 侧只记开始没有完成、`log_health` 计数、run_end 缺失、脱敏扫描（凭据片段／完整本地路径／带凭据 URL／夹具正文）。

**内容相符的依据边界**：原生不记正文（§3 凭据策略），故"读到的内容与夹具逐字相符"只有页面自述（`read_matches_fixture`）一个来源；原生能证明的是"放行、读成功、返回 N 字节"。校验器据此把该依据标为页面自述，并在诊断里显式提示，不把它写成原生证实。

## 6. 执行约定

- **L1**先接Rust文件日志、队列、健康状态、轮转和退出清理，再替换相关原生临时打印；所有构建统一脱敏。此步不扩大为全仓日志改造。
- **L2**再接受限log_event与探针页面，沿已有组合根装配；生产模块保持默认可用，探针额外身份与夹具只在pdf-probe路径启用。更新invoke_handler的明确例外，但不新增铸造授权命令或改变文件来源守卫。
- 关联字段贯通、DOM报告读数及机器校验随L2定向完成；复用既定阶段记录，不增加独立日志平台、动态规则、遥测服务或通用事件总线。L1/L2仍是两个小步，不新增主阶段。

## 7. 取舍与边界

文件为主便于受控归档，stdout仅为尽力镜像。采用现有tracing门面与轻量本地写线程；自建轮转和队列仍须承担其故障测试成本，不以“异步”替代可靠性证明。本轮不引入tracing-appender、远程服务或强持久化承诺。

日志不能替代实际系统操作、IPC对照和PDF验收，也不能证明未记录事件不存在。日志如实记录观察到的内容，不承担防伪职责：Web数据统一视为Web应用层报告；两侧一致只是诊断条件。

stdout 独立线程与有界镜像队列留待后续需求评估。当前采用默认关闭策略，显式开启用于开发排障，并保留上述共享写线程的阻塞边界。

## 8. 退出条件

- **L1**：定向验证级别/JSON和人读输出、必填字段、字段脱敏、span 词汇表与两级结构（span 名与字段的枚举、调用 span 均为根的直接子、结束事件带 `elapsed_ms`）、按运行分文件后同一文件只有一个写者；验证8 MiB边界/UTC跨日/同日重启后归档序号续接、按天过期清理与活跃文件保护，以及不误删其他文件。
- **stdout 配置**。验证缺失配置及字段缺省为 false，显式 true/false 与有效值记录一致。关闭时即使文件不可用也不调用 stdout，关闭不计为 stdout_failed。开启时返回错误停用镜像且文件继续写。阻塞通过可控 sink 释放夹具验证共享线程边界，记录真实丢弃而非将其归为文件正常。健康摘要同样遵循开关。
- **故障**：以可控sink或临时目录夹具验证目录不可写、写入/删除/stdout失败、队列满和超长行、分原因健康计数；验证正常退出排空和2秒超时不拖住退出。明确崩溃/强杀尾部不保证，不能宣称崩溃可靠性已验。跨平台文件锁/轮转行为逐平台留证，未测平台列待验。
- **L2**：实际IPC验证允许/拒绝身份、未知字段与超长/超频请求、原生身份不可被载荷覆盖、无文件授权副作用、失败不递归；返回accepted不误报落盘。默认feature关闭时无探针额外身份与专用入口。
- **证据**：用小夹具验证原生allow/deny与Web声明正常配对；缺失、重复、乱序、页面写原生事件名、未知schema、损坏JSON、结果不符分别按§5处理。所有来源均验证无key、路径、正文与带凭据URL；不得以“已通过单测”代替真实IPC证据。
- 日志基座是否通过与探针业务是否通过分开记录；源码/接口条款的已实施范围以实施记录为准，不把本文修订当运行证据。

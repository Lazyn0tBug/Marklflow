# 日志基座设计（L1/L2）

日期：2026-11-03。基线：architecture-refactor / `2754167`。状态：**设计修订，尚未实施**。本次补充日志记录边界、脱敏、故障及验收契约；不改变产品业务流程。

本文定义 MarkFlow 的日志基座：Rust 侧的文件 sink（L1）、web→Rust 的回传通道（L2），以及由它支撑的**证据形态**（怎么记、怎么取信、怎么被机器校验）。

术语：本应用以Tauri为桌面宿主，Web应用层与Rust原生层共同构成同一个应用，不采用远端客户端—服务端模型。`origin=web` / `origin=rust`仅区分应用内记录来源和观察位置，不表示Web应用层不是应用端。应用内正常日志均用于诊断；涉及原生权限、副作用或隔离验收时，仍需区分页面报告与原生直接观察，不因同属一个应用就互相替代。

本文是**跨阶段的基础设施**，不是某个探针的附属：D1b 的取证、D1c 的打印宿主诊断、D8 的生产接入与可监测性都用它。探针方案只引用本文，不重复定义。

## 1. 动因

1. **交付宿主上看不见**：Windows 的 GUI 应用没有控制台，stdout 在生产环境直接丢弃。
2. **崩溃时 stdout 会丢尾巴**：管道有缓冲，而崩溃正是最需要日志的时候。
3. **证据要能像固化样本那样归档**：文件才是原物，终端输出是转述；转述会丢、会抄错、说不清当时到底看到了什么。
4. **失败定位的往返成本**：2026-11-03 交付宿主复跑时，探针失败只有几行 `println!`，无法判断是源不可达、初载未落地还是导航被取消，只能"加临时打印再跑一遍"——一次往返要 push + pull + build + run。日志落地用于减少这类往返，但不能保证每种故障均有足够证据。

## 3. L1 Rust 日志基座

| 项 | 决定 |
| --- | --- |
| 框架 | `tracing` 做门面、`tracing-subscriber` 做输出（`default-features = false`，开 `fmt`/`ansi`/`std`/`json`）。不引 `env-filter`（正则）与 `tracing-log` 桥 |
| 过滤 | `MARKFLOW_LOG` 解析全局级别；默认 debug 构建 INFO、release 构建 WARN |
| 形态 | 人读一行式为主（时间 级别 目标 字段=值）；`MARKFLOW_LOG_FORMAT=json` 切 JSON 行 |
| 主 sink | **文件**：日志目录 `app_log_dir()` 下**按运行分文件**（`markflow.<pid>.log`）；单文件 8 MiB 或 UTC 跨日轮转，归档 `markflow.<pid>.log.YYYY-MM-DD.NNN`，只保留最新 10 份归档，规则见§3.2 |
| 次 sink | stdout（tee）。开发期的快反馈回路 |
| 写入 | 专用写线程；最多 1024 条待写记录，每条编码后最多 16 KiB。生产者不等待队列空间或文件I/O，队列满则丢弃新记录并计数；超长记录拒收，不截断成无效JSON。**UI 线程不得被日志阻塞**。**同一日志文件只有一个写者**——按运行分文件后结构上成立，无需跨进程协调 |
| 运行标记 | 每次进程启动写一行 `event=run_start run_id=… os=… arch=… app_version=… feature=…`。`run_id` 同时是本次运行的**根 span**；轮转后一个文件含多次运行，靠它圈出本次 |
| 凭据策略 | 所有构建均不记录完整授权key、文档正文、完整本地路径或带凭据URL；以不具授权能力的关联ID替代。字段按允许清单输出，异常文本及Web载荷同样受限，见§5 |

### 3.1 故障、退出与丢失边界

- 日志初始化先于业务事件。目录不可创建/打开时，应用继续运行；内存健康状态记为不可用，不将日志故障转为业务失败，不递归写日志。写入/轮转失败暂停文件sink并记录首个错误类别及计数，本次进程不做重试框架；stdout可用时仍保留尽力输出。
- 文件sink与stdout分别处理错误；stdout失败停用该输出，不拖停文件sink。所有I/O位于写线程，非阻塞承诺针对业务生产者；受阻写线程仍可能导致队列溢出。
- 写线程至少每秒刷新用户态缓冲，WARN/ERROR写入后刷新；正常退出请求排空并刷新，最多等待2秒。超时放弃等待，不阻塞应用退出；不每条执行磁盘同步，不承诺强杀、崩溃、断电或磁盘故障时尾部可靠保存。
- 队列丢弃、限流、格式拒收、sink故障分别计数于进程内有界状态；健康输出可用时按限频摘要输出，不对每次丢弃递归产生日志。stdout不可用时，原生受控验收入口直接读取该状态；验证记录须抄录状态和观察来源。不为此新增IPC、监控面板或后台重试服务。
- 计数和健康状态同样不保证跨崩溃保留；缺失结束标记或存在丢弃/写入错误时，不宣称日志完整。

### 3.2 轮转与保留

- 日界和时间戳统一UTC。写线程串行判断：跨日，或下一条完整记录会使当前文件超过8 MiB，先轮转再写。空文件不反复轮转；单条记录上限小于文件限额。
- 启动时检查已有活动文件：按其最后修改时间的UTC日期及实际大小决定是否先轮转；归档日期为旧活动文件所属日期。首次启用时不改写既有内容。
- `NNN`为该归档日期现存最大序号加一、至少三位，不覆盖已有归档；重启继续分配。保留排序按归档日期再按数值序号，删除最旧者；活动文件不计入10份归档，但仍受8 MiB限制。
- **日志按运行分文件**（`markflow.<pid>.log`）：不同实例各写各的，同一文件天然只有一个写者，不需要锁、不需要跨进程协调，也不引入日志协调服务。轮转与归档按文件各自进行；目录级清理保留最新 10 份归档（跨实例一并计算）。
- 只清理本模块精确命名的归档文件，不删其他文件；轮转或删除失败按§3.1留故障，不悄悄声称保留上限已满足。

## 4. L2 web→Rust 日志回传

| 项 | 决定 |
| --- | --- |
| 通道 | 新增 `log_event` 命令，web 侧事件经它进入同一套日志 |
| 边界 | **该命令只写日志，不铸任何授权**：D1b 的"无命令能铸造授权"这条实质性质不变。逐字意义上的"`invoke_handler` 不变"在此放宽为一个例外 |
| 来源封装 | Rust生成外层 `origin=web`、真实调用方身份和接收时间；页面不能覆盖外层字段。页面记录是 Web 应用层报告，Rust 只证明收到了该身份的声明；本地日志不抵御已控制进程或可改日志文件的攻击者 |
| 限制 | 每条请求UTF-8最多4 KiB；仅接收最小事件结构及允许字段，拒绝自由正文、堆栈、路径、URL和key。未知字段/事件拒收——**可记录的内容是受控的白名单**，不靠事后过滤 |
| 调用身份 | 注入owned Webview读取窗口/WebView身份对。**写日志是有准入的**（与敏感命令同一套身份判定）：正常路径仅允许主窗口；默认关闭的pdf-probe构建可额外接收由原生实际创建并登记的本次探针输出实例，身份仍归受限文件调用侧。不得由页面自报身份获得允许，也不因此扩展文件权限 |
| 限流 | 每个允许身份对最多20条/秒、进程全部Web调用最多100条/秒（每秒固定窗口）；拒绝者不建立无限身份桶。所有请求先做廉价大小/身份限制，超限丢弃并计数；不承诺阻止IPC反序列化本身的开销 |
| 失败 | log_event只表示已校验并接受入队或明确丢弃，不表示已落盘；使用稳定结果 accepted / dropped / rejected。页面最多保留一份最后状态，不重试刷屏；失败不再调用log_event记录自身失败。拒绝/丢弃计数由Rust健康状态维护 |
| 页面侧留痕 | 探针页DOM保留有界且同样脱敏的步骤摘要；回传失败时保留Web应用层观察供诊断，不当作原生结果或文件日志完整性的证明 |

## 5. 证据形态与取信规则

**日志是如实记录，不是防伪造机制。** 它保证的是「按观察到的内容记录」——记录者写下的，是它**观察到**的东西；它不保证记录为真，也不提供防篡改保证。取证时读到的每一条，都是「某侧在某时观察到了某事」，不是「某事确实如此」。

**观测单位是 span**：一条孤立的事件说明不了什么，一次调用（守卫判定、对话框、读写、撤销）才是有意义的单位。故每次调用开一个 span，调用内的事件挂在该 span 上，span 携带起止与耗时；本次运行是所有 span 的根。**不设全局序号**：区分记录靠时间戳与 span 上下文，同一时间戳涌入多个事件是正常现象，要防的是同一事件被重复输出。序号在别的系统里用于游标（journald）、跨批次排序去重（Vector/Fluentd）或跨进程串联（OpenTelemetry），本应用三者都不需要：顺序由单写线程的 FIFO 决定，完整性由丢弃计数与 `log_health` 承担，跨侧关联由 `call_id` 与 span 上下文承担。

**来源与事实分开**：origin=rust仅指Rust记录者，仍须看事件语义。守卫实际判定、文件副作用、原生宿主创建等由Rust直接观察；Rust读取DOM报告记为 `page_report_observed`，其内容仍是页面自述，不转为“原生证实页面事件”。origin=web统一是Web应用层报告，Rust只证明收到该身份的声明。日志不是防篡改审计系统，哈希用于固定归档输入，不证明事件真实性。

**两侧对照**用于定位某次调用的两份记述是否一致：一致是常态，不一致就是线索。它不证明所有事件均发生或完整。原生结果以同请求的Rust观测为准；Web侧的成功声明不能覆盖原生的拒绝或缺证。实际IPC结果及拒绝归因继续遵守探针方案的正向证据规则。

### 5.1 span 模型（两级）

**观测单位是 span**：一条孤立的事件说明不了什么，一次调用（守卫判定、对话框、读写、撤销）才是有意义的单位。每次调用开一个 span，调用内的事件挂在该 span 上；本次运行是所有 span 的**根**。

**层级只有两级**，且所有调用 span 都是根 span 的**直接子**。探针装配、宿主创建、各次调用互为兄弟，不因"因果"再嵌一层——否则正常会话里的调用与探针里的调用形状不同，读日志的规则就要分叉。

**span 上放这次调用的标识与参数，事件上放这次调用的结果与结论**：读日志时先看 span（这是什么操作），再看事件（发生了什么）。span 词汇表是固定的，不开放任意结构：

| span 名 | 谁开 | span 上的字段 | span 内的事件 | 事件字段 |
| --- | --- | --- | --- | --- |
| `run` | 进程启动 | run_id, os, arch, app_version, feature | `run_start` / `run_end` | — |
| `command` | 每个受保护命令 | command, window_label, webview_label | `source_decision` | decision(allow/deny), reason_code |
| | | | `operation_result` | result, bytes, elapsed_ms |
| `page_call` | 页面侧每次调用 | call_id, command, window_label, webview_label | `call_started` / `call_finished` / `page_error` | result, error_category |
| `host` | 每次原生宿主创建 | host_kind, host_label, visible | `host_state` | state, instances |
| `probe` | 探针装配一次 | — | `probe_source_check` / `probe_initial_load` / `probe_navigation` / `probe_cleanup` | reachable, loaded, navigated, revoked |
| | | | `page_report_observed` | host, role, read_ok, read_matches_fixture |
| `log` | 日志基座自身 | — | `log_health` | dropped, rejected, write_failures, rotate_failures, stdout_failed |

两条补充约束（实施时查出，写进契约免得再犯）：

- **span 上的字段不进记录**。记录只带 span 名、id 与父 id，故 `run` span 上的 os／arch／app_version／feature 必须在 `run_start` 事件上重复一次——校验器要按 §5.3 记构建、feature 与环境，这些字段得真的在日志里。
- **每个 command span 都要有 `operation_result`**。拒绝路径没有命令体，由 span 层补一条 `result=denied` 与 `reason_code`；授权解析失败等早退路径同样要记。否则"原生看见了失败却没落笔"，跨侧对照就成了单边叙述。

两条实现约束（都会咬人，写在这里免得实现时再撞）：

- **异步命令用 `Instrument` 附着 span，不用 `enter()` 守卫跨 await**。守卫是 `!Send`，跨 `.await` 持有会让 future 不再是 `Send`，Tauri 命令直接编译不过；即便绕过去，跨线程后"当前 span"也是错的。
- **span 的耗时不会自动记录**。`tracing` 的 formatter 只输出 span 名与 id，不输出起止与耗时，故耗时由结束事件带 `elapsed_ms` 字段。

**span 实例数**：单次运行的实例数约 20（run 1 + probe 1 + host 1 + 受保护命令 span 约 8 + 页面调用 span 约 8 + log 1）。这是**单次运行**的量级，不是全局上限——正常会话里受保护命令的调用次数无界。

### 5.2 最小记录契约

- 机器验收使用JSONL；人读格式只供诊断，不解析其文字作机器证据。两种格式共享字段过滤与脱敏。
- 每条必填 `schema_version=1`、`run_id`（Rust每次启动生成，即本次运行的根 span）、`timestamp`（Rust记录UTC时间）、`level`、`origin`、`event`，以及**所在 span 的上下文**（span 名、span id、父 span）。span 的划分与字段按 §5.1 的词汇表。**不设全局序号**：区分记录靠时间戳与 span 上下文，同一时间戳涌入多个事件是正常现象；真正要防的是**同一事件被重复输出**。Web外层事件固定 `web_event`，附原生取出的 `window_label` / `webview_label`；业务事件在受校验的 `page_event` 字段内，不能变成原生事件名。
- 最小稳定原生事件：`run_start`、`run_end`、`source_decision`、`operation_result`、`host_state`、`page_report_observed`、`log_health`；Web事件枚举先限 `page_ready`、`call_started`、`call_finished`、`page_error`。具体阶段只能按需增加枚举，不开放任意结构化字段。
- **观测单位是 span，不是单条记录**：一次调用开一个 span，调用内的守卫判定与操作结果是该 span 内的事件，span 携带起止与耗时。原生侧每个受保护命令一个 span（`command` 为 span 名）；Web侧每次调用一个 span，`call_id` 即其 span id。调用类记录带不具授权能力的 `call_id`、命令枚举、结果枚举；原生守卫记录allow/deny及稳定原因码。Web应用层调用ID只用于关联，不是身份或权限；Rust限制其长度和字符集，绑定run_id、原生身份、命令。每个探针请求使用唯一ID；若需传入生产命令，仅作为可选诊断关联字段，不改变返回值和业务判定，也不允许关联字段控制身份。未落实同请求贯通时，不能只按时间近似配对后宣称调用已对应。
- 其他字段只允许固定枚举、计数、布尔值或有界诊断ID；`page_error`只传错误类别，不传原始异常message。日志入口和底层sink均不输出原始授权key，不以secret=true作为泄露许可。字段白名单的作用是**记录的内容受控**，不承担防伪职责。

### 5.3 校验与归档

- 校验器记录run_id、原始日志文件集合及SHA-256、构建/feature和环境；跨轮转时收集本次运行所需全部文件（按运行分文件后，同一运行的日志通常只在一份文件里，但轮转会把它分成多份）。缺run_start、未知schema、JSON损坏、所需事件缺失/重复或关联不匹配，相关断言记未能确认，不自动补齐。
- 同一 span 内同名事件重复出现即视为重复输出，须报告；跨侧按 call_id 与 span 上下文配对，允许Web异步迟到。身份/命令冲突及结果不一致均须报告；无对应Rust观察的Web声明不能证明原生成功。只对该验收所需事件设完整性条件，不要求全部业务事件两侧双写。
- 验收取证运行须显式启用覆盖所需事件的级别与JSON格式；release默认WARN不保证收集INFO证据。缺少过滤掉的事件仍属证据不足，不能认作未发生。
- 日志不含文档正文、完整本地路径或任何授权凭据，包括查询串、异常与DOM报告的间接泄露。关联使用单独ID，不使用key片段作为常规关联办法。已有探针URL/cleanup打印原始key的路径须在接入基座时同步迁移，不能tee后继续泄露。

**校验器的实现**：`scripts/pdf-probe-check.ts`（`bun scripts/pdf-probe-check.ts <日志文件或目录...> [--run <run_id>] [--json]`）。它做两件事：

1. 按探针方案 §5.3 的证据矩阵逐条判定 D1b-1—D1b-6，三态结论（通过／未通过／未能确认），每条都写明判定依据及其来源（native 观察／web 观察／页面自述）。退出码：0 全部通过，1 有未通过或有错误级诊断，2 有未能确认。
2. 做**契约体检**（诊断项，不混进断言）：重复输出、调用 span 是否都是根的直接子、事件是否落在契约规定的 span 内、跨侧结果不一致、两侧记录数量不匹配、web 侧只记开始没有完成、`log_health` 计数、run_end 缺失、脱敏扫描（凭据片段／完整本地路径／带凭据 URL／夹具正文）。

**内容相符的依据边界**：原生不记正文（§3 凭据策略），故"读到的内容与夹具逐字相符"只有页面自述（`read_matches_fixture`）一个来源；原生能证明的是"放行、读成功、返回 N 字节"。校验器据此把该依据标为页面自述，并在诊断里显式提示，不把它写成原生证实。


## 6. 执行约定

- **L1**先接Rust文件日志、队列、健康状态、轮转和退出清理，再替换相关原生临时打印；所有构建统一脱敏。此步不扩大为全仓日志改造。
- **L2**再接受限log_event与探针页面，沿已有组合根装配；生产模块保持默认可用，探针额外身份与夹具只在pdf-probe路径启用。更新invoke_handler的明确例外，但不新增铸造授权命令或改变文件来源守卫。
- 关联字段贯通、DOM报告读数及机器校验随L2定向完成；复用既定阶段记录，不增加独立日志平台、动态规则、遥测服务或通用事件总线。L1/L2仍是两个小步，不新增主阶段。

## 7. 取舍与边界

文件为主便于受控归档，stdout仅为尽力镜像。采用现有tracing门面与轻量本地写线程；自建轮转和队列仍须承担其故障测试成本，不以“异步”替代可靠性证明。本轮不引入tracing-appender、远程服务或强持久化承诺。

日志不能替代实际系统操作、IPC对照和PDF验收，也不能证明未记录事件不存在。日志如实记录观察到的内容，不承担防伪职责：Web数据统一视为Web应用层报告；两侧一致只是诊断条件。

## 8. 退出条件

- **L1**：定向验证级别/JSON和人读输出、必填字段、字段脱敏、span 词汇表与两级结构（span 名与字段的枚举、调用 span 均为根的直接子、结束事件带 `elapsed_ms`）、按运行分文件后同一文件只有一个写者；验证8 MiB边界/UTC跨日/同日重启后归档序号续接、保留排序与活动文件限额，以及不误删其他文件。
- **故障**：以可控sink或临时目录夹具验证目录不可写、写入/删除/stdout失败、队列满和超长行、健康计数；验证正常退出排空和2秒超时不拖住退出。明确崩溃/强杀尾部不保证，不能宣称崩溃可靠性已验。跨平台文件锁/轮转行为逐平台留证，未测平台列待验。
- **L2**：实际IPC验证允许/拒绝身份、未知字段与超长/超频请求、原生身份不可被载荷覆盖、无文件授权副作用、失败不递归；返回accepted不误报落盘。默认feature关闭时无探针额外身份与专用入口。
- **证据**：用小夹具验证原生allow/deny与Web声明正常配对；缺失、重复、乱序、页面写原生事件名、未知schema、损坏JSON、结果不符分别按§5处理。所有来源均验证无key、路径、正文与带凭据URL；不得以“已通过单测”代替真实IPC证据。
- 日志基座是否通过与探针业务是否通过分开记录；源码/接口设计条款均为待实施要求，不把本文修订当运行证据。

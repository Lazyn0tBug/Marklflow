# PDF 内容核验的实现选择：问题与建议（2026-11-04）

D1d 的机器部分需要从探针产出的 PDF 里读出四样东西：页数与页面尺寸、每页正文、首末标记落在哪一页、字体与图像报告。

2026-11-04 讨论的问题是：**这些应当自己写解析器，还是用第三方库或工具。**

本文记录：这一轮出的问题（实现上的与流程上的）、三个选项的代价、建议，以及**需要定的唯一一件事**。

---

## 1. 这一轮出的实现缺陷

手写的 PDF 解析器（`scripts/pdf-probe-pdf-check.ts`）在第一次面对真实 PDF 时就接连暴露两类缺陷，**都属同一类：某个量由输入决定，却没有上界**。

### 1.1 区间展开没有上限 → 内存被吃光

`bfrange` 的区间可以长达 65536（`<0000> <FFFF>`）。展开成映射表就是几十个字体 × 65536 项，进程被 OOM 杀掉。

**改法**：区间**不展开**，按 `(low, high, base)` 存着，查某个码时再算它落在哪个区间。内存从 O(区间长度 × 字体数) 变成 O(区间条数)。

### 1.2 扫描游标会倒退 → 同一对象被无限重解析

`body` 是文件的一段切片，**它内部的偏移是相对的**；而 `contentStart` 却拿去当 source 的**绝对**下标用。于是 `indexOf('endstream', 相对偏移)` 在文件前部就命中，游标退回到该对象起点之前，下一轮又从那里扫起 → **同一个对象被反复解析**，映射表一路涨到内存爆掉。

这一条比 1.1 隐蔽得多：读代码不容易看出来（两个偏移混用要看得很仔细），**是靠加阶段打印跑一次才定位的**。

**改法**：偏移一律用绝对下标。

### 1.3 补齐的上界

| 位置 | 由输入决定的量 | 上界 |
| --- | --- | --- |
| PDF 解析 | 单流解压后字节数 | 16 MiB |
| PDF 解析 | 全文解压累计 | 64 MiB |
| PDF 解析 | 单个内容流字节数 | 8 MiB |
| PDF 解析 | 记号数量 | 200 万 |
| PDF 解析 | 输入 PDF 字节数 | 64 MiB |
| 日志校验 | 输入日志字节数 | 256 MiB |
| 既有 `check-pdf-file.ts` | 解压输出 | 64 MiB |

## 2. 这一轮出的流程缺陷

**审查被跳过了。** Rust 侧照做了「clippy → 审查 → 测试」，TS 侧却写完直接开跑 ✗。审查本该在第一次运行**之前**——它是唯一能发现"这个循环的上界由文件内容决定"的时机。

**审查缺一个维度。** 前几轮看的是类型、逻辑、命名、契约；没问"**这个数由谁决定、最坏多大**"。只看类型与逻辑，看不出偏移混用这类问题。

已把这条写进[审查与测试规范](../development/review-and-testing.md)：凡"量由输入决定"的地方都要有硬上界；偏移量要统一基准。

## 2.5 先分清两侧：pdf.js 从来不在产出那一侧

| 侧 | 用什么 | pdf.js 在不在场 |
| --- | --- | --- |
| **产出 PDF**（探针打印） | **COM**：`ICoreWebView2_7::PrintToPdf` ✓ | ❌ 不在场——pdf.js 是**读** PDF 的 ✓ |
| **读回核对**（D1d 的检查） | 开发期脚本 ✓ | 只在这一侧被列为候选 ✓ |

它之所以曾被列上，只有一个理由：**它是 JS 里最完整的 PDF 读取器** ✓，直接解 ToUnicode（手写最费劲的部分 ✓），且不需要外部工具 ✓。

## 2.6 平台没有第三条路（这一点决定了推荐的形状）

**Windows 没有 PDF 文字提取的原生 API。**

- `Windows.Data.Pdf`（WinRT）只能把页面**渲染成位图**，取不到字 ✓；
- WebView2 内含 PDFium ✓，但**不暴露它的文字提取接口** ✓；
- 所以"读回 PDF 的正文"在 Windows 上**没有第三条纯原生的路** ✓：要么用工具（poppler ✓），要么自己解析 ✓。

**故方案 A 的形状是平台决定的，不是偏好** ✓。

还有一条看着纯原生、其实只能当人工项的路：**让应用自己把 PDF 打开看** ✓（WebView2 自带阅读器 ✓——**未核**，得在交付宿主上看 ✓）。即便可行 ✓，阅读器的**文本层在阅读器自己的文档里** ✓，页面里的 JS 到不了 ✓ → **拿不到机器可读的文字** ✓。所以它只能给人看 ✓，恰好是**人工项**该待的位置 ✓，不能当机器判据 ✓。

## 3. 三个选项

| | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| **A** | 手写解析器作"永远可用的那一条路" + poppler 作权威对照 | 不挑环境（交付宿主与 CI 都能跑）；两个独立实现互为对照 | 要维护解析器；判定依据有两份，要约定"一致才算过" |
| **B** | 只用 poppler（`pdftotext`/`pdffonts`/`pdfinfo`） | 判据由专用工具给；不必维护解析器 | 每台跑验收的机器都要装它（TBD-13 未授权）；缺件就取不到证据 |
| **C** | 换 pdf.js | 通用、完备 | 浏览器向的库，体量大、要打包配置；为一次开发期验收引入，风险大于收益 |

**C 不推荐**：我们只需要 PDF 里的一小块 ✓，而 pdf.js 的渲染部分还要 canvas ✓。

---

## 4. 建议：选 A

理由有三条：

1. **判据应当由专用工具给。** 方案里 D1d 本来就写着"字体报告依赖 poppler，尚未安装且需另行授权"（TBD-13 ✓）——这是项目自己的设计决定。手写解析器是绕过它，不是取代它。
2. **两个独立实现结论一致才算通过，不一致就是线索。** 这正是日志基座那套"两侧对照"的做法：原生观察 × web 声明 ✓。手写解析器 × poppler 正好构成这样一对 ✓。
3. **不能因环境缺件就取不到证据。** 这也是当初做日志基座的同一个理由 ✓：交付宿主没有 poppler 时，检查仍要能跑。

**A 的具体内容**：

| 件 | 内容 |
| --- | --- |
| 手写解析器 | 保留（`scripts/pdf-probe-pdf-check.ts`），定位是"永远可用的那一条路" ✓ |
| 真实产物回归 | 把 WebView2/Chromium 产出的那份 PDF **归档成夹具**，单测跑它 ✓——手写解析器的每次改动都由真实产物回归 ✓，而不是只靠临时生成的 PDF ✓ |
| 响亮失败 | 遇到不认识的 PDF 形态（对象流 ObjStm、xref 流、加密）要**明确报错**，不能安静地返回"0 页" ✓ |
| 权威对照 | 在有 poppler 的机器上跑 `pdftotext -f N -l N` 与 `pdffonts`，与手写解析器的结论逐项对照 ✓；不一致就记为线索，不放过 ✓ |

---

## 5. 需要定的唯一一件事

**交付宿主那台机器能不能装 poppler。**

- **能** → A 的完整形态：交付宿主上同时跑两套，结论一致才算 D1d 通过 ✓。
- **不能** → A 的降级形态：手写解析器在交付宿主上出结论 ✓，poppler 对照在本机做 ✓（把交付宿主产出的 PDF 拿回来 ✓），并在阶段记录里写明"权威对照不在交付宿主上做过" ✓。

**这不影响现在该做的事**：归档夹具、补单测、明确失败路径 ✓——这三件与 poppler 无关 ✓。

## 6. 手写解析器的已知边界（要写进阶段记录）

| 形态 | 支持情况 |
| --- | --- |
| 对象在顶层、未压缩（Chromium/WebView2 产出即是） | ✅ 支持（已用真实产物验过） |
| 对象流（ObjStm）、xref 流 | ❌ 不支持 → 找不到页面 → **必须响亮失败** ✓ |
| 加密 PDF | ❌ 不支持 ✓ |
| 简单字体 + ToUnicode | ✅ 支持 ✓ |
| Type0/CID 字体（Identity-H，双字节码） | ✅ 支持（按 ToUnicode 解 ✓） |
| Type3 字体 | ✅ 支持（字形是 CharProcs，提取靠 ToUnicode ✓） |
| 文字的 Unicode 码位 | ⚠️ 提取出的中文偶有 CJK 兼容字（如"第⼀章"而非"第一章"）——那是 PDF 的 ToUnicode 映射本身指向兼容字形，**字形对、码位是变体**。故"正文可提取"可机器判定，"提取文本与源文本逐字相同"不可 ✓（ASCII 标记不受影响 ✓） |
